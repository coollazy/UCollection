<a id="v0-1"></a>
### v0.1（2026-09-01）

第1節整體架構總覽拍板：

- **Process 拓樸**：單一 Go binary，內部以常駐 goroutine 執行鏈上監控背景任務，不拆分多 process、不引入 message queue。理由：需求書為單租戶架構、無多副本/高可用要求，docker-compose 一鍵部署精神下越簡單越好。
- **docker-compose 服務組成**：`app`（Go binary）＋ `db`（PostgreSQL）兩個 container，不內建反向代理/TLS 終止（延續進度.md 已定案的技術選型）。
- **路由劃分**：單一 HTTP server、單一 port，依路徑前綴分流成 `/api/v1/...`（API Key+HMAC）、`/admin/...`（Session+2FA）、`/checkout/{orderId}`（無需登入）、`/tron-proxy/...`（同源代理，僅限已登入後台 session）四類。
- **組交易/廣播歸屬**：依 [驗證結論-08](驗證結論-08-嚴格CSP下組交易簽名廣播.md) 對階段03的提醒拍板，組交易與廣播兩個對外呼叫 TronGrid 的動作一律由後端經 `/tron-proxy` 執行，瀏覽器端只做衍生+簽名，不直連 TronGrid 網域，讓 CSP `connect-src 'self'` 可直接套用。
- **內部 package 劃分**：確立 `cmd/ucollection`、`internal/{config,store,hdwallet,order,scanner,tronclient,webhook,api,admin,checkout,consolidation,auth,audit}`、`web/static/js` 的 Go 慣用 layout，作為後續模組討論的檔案歸屬依據。

使用者確認方案可行，無調整。

<a id="v0-2"></a>
### v0.2（2026-09-01）

第2節資料庫 schema 拍板：

- **地址不獨立建表**：因「地址與訂單永久一對一綁定」且地址只在建立訂單當下才依索引衍生，`orders` 表直接帶 `master_wallet_id`／`derivation_index`／`address` 欄位，不另拆 `addresses` 表。
- **表格劃分**：`master_wallets`、`orders`、`order_state_transitions`（訂單完整狀態變更歷史，供5.2手動改判不覆蓋歷史用）、`incoming_transactions`（累加金額判斷用）、`consolidation_batches`/`consolidation_items`（手動歸集，逐筆獨立追蹤廣播結果）、`consolidation_address_book`（歸集地址簿，上限30筆）、`webhook_deliveries`、`api_keys`、`admin_account`、`audit_logs`、`system_params`，共11張表。
- **併發安全**：`master_wallets.last_derived_index` 用 PostgreSQL advisory lock 包住「讀取→+1→寫回→建立訂單」，確保高併發建單不會分配到重複 index。

使用者確認方案可行，無調整。

<a id="v0-3"></a>
### v0.3（2026-09-01）

第3節 HD 地址衍生模組拍板：

- **套件選型**：伺服器端只做「xpub → 地址」公鑰衍生，沿用驗證項目1（[評估-Go打包Docker可行性.md](評估-Go打包Docker可行性.md)）同一套組合：`btcsuite/btcd/btcutil/hdkeychain`（xpub解析與非硬化衍生）、`golang.org/x/crypto/sha3`（Keccak256）、stdlib `crypto/sha256`（checksum）、`btcsuite/btcd/btcutil/base58`（編碼）。
- **刻意不引入** `go-ethereum`／`gotron-sdk`／gRPC：那組依賴是驗證項目2簽名+廣播才需要的，伺服器端不簽名用不到，引入只會不必要拉大 image（純手刻11.3MB vs 含go-ethereum+gRPC 26.1MB）。
- **衍生邏輯**：xpub已編碼到account層級，伺服器再衍生兩層非硬化路徑 `xpub.Derive(0).Derive(index)`；衍生出的公鑰經Keccak256→取後20bytes→前綴0x41→雙SHA256 checksum→Base58編碼得到Tron地址；與第2節advisory lock銜接，分配index、算地址、寫入orders列在同一DB transaction內完成。

使用者確認方案可行，無調整。

<a id="v0-4"></a>
### v0.4（2026-09-01）

第4節鏈上監控模組拍板，過程經過完整討論修正與subagent兩輪審查：

- **原始設計的根本問題**：最初提案讓事件掃描/確認數計算迴圈依「是否有進行中訂單」啟停（回應使用者質疑「無訂單監控意義何在」的初步修正），但subagent第一輪審查指出這個方向本身是錯的——需求書5.3自己說事件掃描的API呼叫成本只跟區塊產生速度有關、不隨地址/訂單數量增加，為了省一個固定成本而啟停，換來一整組冷啟動/尾端漏記的窗口期風險（詳見審查發現1/2/3/6/f），不划算。
- **核心修正**：移除「監督迴圈+session啟停」機制，改為三個永遠常駐的背景任務：任務1（訂單生命週期巡查，純DB查詢）、任務2（事件掃描迴圈）、任務3（確認數計算+reorg檢查）。無進行中訂單時任務2降頻（非停止），checkpoint持續推進。
- **第二輪審查追加修正**：CONFIRMATION_STALLED判定比照EXPIRED加上「任務3已追上」守門條件（原本只修了EXPIRED這條路徑）；task3明確跳過已STALLED的訂單不自動轉回COMPLETED（呼應需求書5.2已定案的手動改判機制）；備援改用TronScan（不同資料源）而非TronGrid另一端點；金額運算全程用int64最小單位；`incoming_transactions`唯一鍵改用`(tx_hash, log_index)`；checkpoint/最新區塊高度查詢皆用`GREATEST()`保證單調；429/5xx指數退避重試；首次部署SOP需等第一筆checkpoint建立才開放接單。
- **明確記錄但不當作本模組bug的缺口**：COMPLETED後偵測到reorg的後續狀態機路徑，留給模組5定義；累加金額不分入帳來源，明講這是TRC20代收系統常態設計非疏漏；5.9「已歸集地址不再監控」與提前歸集進行中訂單的邊界情況，屬需求書措辭層級小缺口。
- **Gate**：驗證項目9結果出爐、checkpoint安全緩衝N值與reorg延伸緩衝期具體數字確定前，本模組不得視為可進入正式開發。

使用者確認方案可行，無調整。

### v0.5（2026-09-01）

討論第4節鏈上監控模組時發現的邏輯漏洞（詳見 [需求書變更紀錄v0.36](開發流程框架-01-需求書變更紀錄.md#v0-36)）連動修訂：v0.4版「確認數達標後再加一段安全緩衝期才停止追蹤reorg」設計，把「商戶自訂確認數」跟「Tron協定自身solidified狀態」當成同一件事，但緩衝期該加多久講不出根據，正是v0.4版Gate卡住的其中一個卡點。拍板改用需求書v0.36已拿掉「確認數」商戶可調參數的方案，一路連動修訂：

- **第2節schema**：`orders`表參數快照欄位從四個減為三個，`confirmations_required`移除；`incoming_transactions`表`confirmations`（數字）欄位改為`confirmed`（boolean，`only_confirmed=true`查詢命中即true）；`system_params`表全域參數清單移除確認數。
- **第4節任務3**：更名為「最終確定（solidified）判定＋reorg檢查」，判斷邏輯從「自算目前區塊高度－交易區塊高度，跟商戶設定值比較」改為「直接以`only_confirmed=true`重新查詢，命中即觸發」；reorg檢查範圍限縮為「`only_confirmed=false`已命中、尚未查到`only_confirmed=true`」這段期間，查到`only_confirmed=true`後即停止追蹤，不再額外加緩衝期。
- **第4節Gate**：兩個卡點簡化為一個——「reorg延伸緩衝期具體數字」隨此決策消失，只剩「checkpoint安全緩衝N值」待驗證項目9完成後校準。
- **第4節「待模組5處理的缺口」**：「COMPLETED後偵測到reorg的後續狀態機路徑未定義」這項缺口一併消失（COMPLETED/OVERPAID現在只會在達Tron協定自身認定的不可逆狀態後才轉入，定義上不會再被reorg打回），標記刪除線保留記錄但註明已解決。
- **新增第5節「訂單狀態機模組」**：正式寫入模組5設計（先前僅為[階段03技術細節暫存.md](階段03技術細節暫存.md)草稿）。核心內容：`SELECT...FOR UPDATE`鎖定+Go端判斷的原子性做法；自動路徑（業務條件不成立則靜默ROLLBACK）與手動改判路徑（只檢查狀態白名單、不重查金額）共用同一骨架；容許誤差用預先算好的`amount_lower_bound`/`amount_upper_bound`兩個BIGINT快照欄位；狀態轉換判斷條件對應模組4任務2/任務3拆兩條查詢（PENDING→CONFIRMING只看下界、CONFIRMING→COMPLETED/OVERPAID看`confirmed=true`累加金額）；不再有COMPLETED/OVERPAID→CONFIRMATION_STALLED的reorg觸發邊，`decision_snapshot`/Webhook payload不需要`previous_status`/`reason`區分欄位。過程中一併套用審查發現的獨立修正：PENDING→CONFIRMING觸發條件原本寫「落在`[lower,upper]`區間才觸發」會導致超額付款卡死在PENDING直到轉EXPIRED（與需求書5.2 EXPIRED語意矛盾），修正為只看下界，上界判斷留給下一步分流。

使用者確認方案可行，無調整。

### v0.6（2026-09-02）

[驗證項目9](驗證結論-09-TronGrid事件掃描保留期限與斷點續掃.md)結果PASS出爐，拍板第4節唯一剩下的Gate卡點——checkpoint安全緩衝N值：

- **發現原文件換算基準用錯**：v0.4/v0.5版寫「N值依驗證項目2量到的索引延遲上限（約60秒）換算」，但驗證項目2實測兩個不同延遲——`only_confirmed=false`約23.4秒、`only_confirmed=true`（solidified）約63.1秒。任務2的checkpoint推進用的正是`only_confirmed=false`查詢，該用23.4秒這個數字，原文件「約60秒」其實誤套用了任務3（確認延遲）的數字。
- **拍板換算**：Tron協定公開出塊時間約3秒/塊，23.4秒實測值（Shasta測試網單次觀察，非官方保證上限）套約2.5倍安全係數後取整數，**N = 20個區塊（≈60秒）**。使用者於三個選項（10/20/30個區塊）中選定20。選擇理由：N值大小對系統幾乎無代價——只影響EXPIRED/STALLED守門判定延後的秒數（相對訂單有效期通常是分鐘級可忽略），不影響金額判斷正確性（`(tx_hash, log_index)`唯一鍵已防重複），故沒有下修的理由。
- **新增防禦性降級告警機制**：依驗證結論09建議——「未證明永久保留，只是沒測到截斷」，補齊掃描連續多個歷史區間都回傳空陣列、且理論上該有資料時，觸發告警／人工複查，不直接信任空陣列＝沒事件，寫入任務2描述。
- **Gate解除**：第4節「最終確定判定」機制、第5節（依賴模組4`confirmed`欄位）皆可進入正式開發（階段05）。
- 同步修正：Process意外中斷重啟段落「停機期間TronGrid是否還查得到」不再標記「取決於驗證項目9（尚未執行）」，改為引用驗證項目9已確認的結論（回溯7.4年無保留期限截斷）。

使用者確認方案可行，無調整。

### v0.7（2026-09-02）

第6節前台收銀頁模組拍板，經subagent兩輪審查修正：

- **草稿初版**：路由 `/checkout/{orderId}`，新增 `orders.public_token` 作為公開URL識別碼（不可用DB主鍵或`merchant_order_no`）、伺服器端QR code產生（僅放地址不編碼金額）、htmx輪詢刷新狀態、基本CSP baseline + noindex。
- **第一輪審查發現兩項高嚴重度問題**：(1) CONFIRMING狀態不受`expires_at`限制轉EXPIRED是模組5已定案規則，但草稿的前端倒數計時邏輯沒接住，會出現「倒數歸零但狀態仍顯示確認中」的矛盾畫面——跟模組4審查抓到的「CONFIRMATION_STALLED判定不對稱」同類問題，規則變了但下游沒同步調整；(2) htmx終態停止輪詢只寫「後端回應帶出信號」沒講具體手段，此端點無登入、無rate limit（丟給商戶反代層），若實作者做錯等於留下可累積資源消耗的漏洞。另有中/低嚴重度發現：路由參數命名`{orderId}`與`public_token`決策自相矛盾（需同步修訂第1節）、CONFIRMATION_STALLED文案被漏列、用戶端時鐘飄移風險、`public_token`未明訂需CSPRNG（`crypto/rand`）、缺Referrer-Policy、token唯一索引衝突未提及重試。
- **修正**：CONFIRMING狀態不顯示倒數、改顯示「確認中」不含時間壓力的狀態指示；終態停止輪詢明訂為「整段替換掉帶`hx-trigger`屬性的容器」；同步修訂第1節路由表`{orderId}`→`{token}`；CONFIRMATION_STALLED與EXPIRED文案方向分開列記；`public_token`明訂用`crypto/rand`產生32 bytes；加`Referrer-Policy: no-referrer`；補上token衝突retry要求。
- **第二輪審查**：確認上述9項修正皆為真實解決、非換句話說，但指出修正過程本身引入一項新缺口——「剩餘秒數」改為伺服器夾帶相對值後，前端如何呈現平滑倒數（純伺服器渲染會隨5秒輪詢間隔階梯式跳動 vs. 加一小段inline JS做每秒本地遞減+定期對齊）未定義。另兩項低嚴重度、非必要立即處理：初始頁面首次渲染若訂單當下已是終態，需直接輸出不含`hx-trigger`版本（自然推論但補上避免遺漏）；`remaining_seconds`到期瞬間與背景任務翻轉狀態間的~5秒既有時序窗口（系統既有特性延伸，非本模組新問題，僅記錄）。
- **最終拍板**：倒數計時採inline vanilla JS方案（`setInterval`每秒本地遞減、每次輪詢回應時用伺服器值重新對齊），不算違反「零Node.js建置鏈」原則（該原則限制建置工具鏈，非禁止少量inline JS）；一併補上初始渲染終態抑制的明文要求。
- **順帶修正模組2 schema既有缺口**：`amount_lower_bound`/`amount_upper_bound`欄位在v0.5新增第5節時已定案存在，但先前未補回第2節`orders`表格清單，本次一併補上。

使用者確認方案可行，但要求兩項調整：(1) 正式文件是給開發看的，兩輪審查的過程敘述對開發沒有幫助、只是雜訊，第6節本文開頭那段「本節經subagent兩輪審查修正...」整段拿掉，完整過程改為只保留在本變更紀錄（即本節）；(2) 「OVERPAID/EXPIRED是否要提示已收到部分/超額款項」這句帶著「列記待確認」字樣的TBD，不該留在正式架構文件裡（比照需求書不留待決狀態的原則），移到進度.md下一步清單第11項追蹤，第6節本文只保留「各狀態文案留待介面設計階段」這句範圍邊界說明。已依此調整。

<a id="v0-8"></a>
### v0.8（2026-09-02）

進度.md「剩餘模組拍板順序」第1項：新增第7節對外API模組（`internal/api`），對應需求書5.6：

- **路由**：`POST /api/v1/orders`（建單）、`GET /api/v1/orders/{id}`、`GET /api/v1/orders?merchant_order_no={xxx}`（查詢）。查詢僅支援單筆，不含列表/分頁——列表屬需求書5.5後台範疇，使用者於討論中確認先只限單筆。
- **認證機制討論**：草案提出API Key+HMAC簽章（Header：`X-API-Key`/`X-Timestamp`/`X-Signature`），但`api_keys`表原本欄位命名`secret_hash`與HMAC機制矛盾——HMAC驗簽是「伺服器用同一把secret重新計算簽章、比對計算結果」，不是單純比對雜湊值，雜湊過的secret無法逆推重算，伺服器必須持有明碼secret才能驗證。這跟密碼(password)驗證不同：密碼驗證是「使用者輸入雜湊後比對」不需要伺服器重算，可以只存雜湊；但HMAC需要重算，本質上做不到。此為HMAC機制本身限制，非設計疏漏，比照AWS/Stripe/GitHub Webhook業界慣例明碼存DB。討論中曾考慮應用層加密（用master key加密secret再入庫）增加防禦深度，但master key仍須放在伺服器啟動時可自動讀取的環境變數，形式意義大於實質防護，且與consolidation模組（人工每次輸入密碼解密助記詞）的加密情境本質不同，不套用同一套邏輯，故不加此層。**拍板**：`api_keys.secret_hash`更名為`secret`，明碼存，同步修正第2節schema表格。
- **建單API欄位討論**：草案僅定義`merchant_order_no`（必填）與`target_amount`（必填）兩欄位，對應需求書5.6明文範圍。曾討論是否比照Stripe新增選填`metadata`欄位（商戶自訂key-value，系統不解讀原樣回傳），若加則需額外決定格式限制、大小上限、以及metadata不同是否算冪等衝突（討論傾向metadata不參與衝突比對，以第一次存的為準）。**拍板不加**：需求書5.6沒有提出這個功能，屬猜測性擴充而非驗證過的真實需求，且商戶自行用`merchant_order_no`當key維護對照表成本很低，若之後商戶端真的反應需要，屬於需求書增修範疇，不在架構設計階段預先加。
- **冪等性衝突判斷討論**：使用者一度誤解「衝突比對用金額」是否代表「兩張不同訂單金額相同就會衝突」。釐清：衝突比對的觸發前提是「同一個`merchant_order_no`」，不是全域金額比對——查無此`merchant_order_no`一律正常建立新訂單，不論金額是否與其他訂單相同；只有查到同一個`merchant_order_no`已存在時，才會比對這次金額與原訂單是否一致，藉此判斷是「網路重試」（相同，回傳原訂單）還是「異常」（不同，409拒絕）。不同`merchant_order_no`的訂單完全互不影響。
- **回應/錯誤格式**：統一`{"error_code","message"}`結構；Rate limiting沿用第1/6節既有決策留給商戶反代層處理，應用層不重複設計。

使用者確認方案可行，無調整。
