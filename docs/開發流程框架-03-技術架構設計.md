## 1. 整體架構總覽

### Process 拓樸

單一 Go binary，內部以常駐 goroutine 執行鏈上監控背景任務，不拆分多 process、不引入 message queue。

**理由**：需求書為單租戶架構、無多副本/高可用要求；docker-compose 一鍵部署精神下，越簡單越好。

**docker-compose 服務組成**：
- `app`（Go binary，內含 API/後台/前台/鏈上監控/同源代理）
- `db`（PostgreSQL）

不內建反向代理/TLS 終止（需求書已定案，見進度.md），商戶自行於前方架設 nginx/Cloudflare 等；系統本身只需監聽一般 HTTP port。

### 單一 HTTP server，依路徑分流

| 路徑前綴 | 用途 | 驗證方式 |
|---|---|---|
| `/api/v1/...` | 商戶外部系統建單/查詢（見需求書 5.6） | API Key + HMAC 簽章 |
| `/admin/...` | 後台管理介面（見需求書 5.5） | Session cookie + 2FA |
| `/checkout/{token}` | 前台收銀頁（見需求書 5.4） | 無需登入 |
| `/tron-proxy/...` | 同源代理，供手動歸集/TRX手續費頁面（見需求書 5.9）呼叫 TronGrid，架構已於驗證項目 8 驗證通過 | 僅限已登入後台 session |

### 組交易與廣播由後端統一發起

依 [驗證結論-08](驗證結論-08-嚴格CSP下組交易簽名廣播.md) 對階段03的提醒拍板：瀏覽器只跟自家後端（同源）溝通，「組交易」與「廣播」兩個對外呼叫 TronGrid 的動作，一律由後端經 `/tron-proxy` 代為執行；瀏覽器端只負責衍生 xpub/私鑰與交易簽名，不直接連線 TronGrid 網域。此設計讓 CSP `connect-src 'self'` 可以直接套用，不必為了遷就直連需求而放寬。

### 內部 package 劃分

```
cmd/ucollection/          — 入口，啟動HTTP server + 背景scanner goroutine
internal/config/          — 環境變數設定
internal/store/           — DB存取層（含migrations）
internal/hdwallet/        — xpub衍生地址邏輯
internal/order/           — 訂單/狀態機
internal/scanner/         — 鏈上事件掃描背景任務
internal/tronclient/      — 封裝呼叫TronGrid（scanner/tron-proxy共用）
internal/webhook/         — 推送/重試
internal/api/             — 對外API handler
internal/admin/           — 後台handler
internal/checkout/        — 前台handler
internal/consolidation/   — 手動歸集後端邏輯
internal/auth/            — 帳號/2FA/session
internal/audit/           — 審計日誌
web/static/js/            — 離線打包的助記詞衍生/簽名JS bundle（給瀏覽器端頁面用）
```

## 2. 資料庫 schema 設計

### 地址不獨立建表，直接併入 orders

需求書「地址與訂單永久一對一綁定」（5.1），且地址只在建立訂單當下才依索引衍生（不是預先產生地址池），兩者生命週期完全同步。`orders` 表直接帶 `master_wallet_id`／`derivation_index`／`address` 三個欄位，不另拆 `addresses` 表。

### 表格清單

| 表 | 用途 | 關鍵欄位 |
|---|---|---|
| `master_wallets` | 代收主錢包（5.1） | `xpub`、`status`(active/inactive)、`last_derived_index`（併發分配地址用，見下） |
| `orders` | 訂單（5.2） | `merchant_order_no`(唯一，建單API冪等性用)、`public_token`（唯一，`crypto/rand`產生32 bytes，供第6節前台收銀頁公開URL識別碼用，不可用主鍵或`merchant_order_no`代替，見模組6）、`master_wallet_id`、`derivation_index`、`address`、`status`、`target_amount`、`amount_lower_bound`／`amount_upper_bound`（容許誤差邊界快照，見模組5）、三個參數快照欄位（`validity_seconds`／`amount_tolerance_percent`／`confirmation_stall_timeout_seconds`；`confirmations_required`已隨v0.36需求書改版移除，訂單是否達確認一律以 Tron 協定自身的 solidified 狀態判斷，見模組4）、`expires_at`、`confirming_at`、`consolidation_status`（從未歸集/已歸集，供手動歸集列表排除已歸集地址用，對應5.9已知限制） |
| `order_state_transitions` | 訂單完整狀態變更歷史（5.2 手動改判需求：曾經歷過的狀態不因改判覆蓋） | `order_id`、`from_status`、`to_status`、`changed_by`(system/商戶手動)、`note`、`created_at` |
| `incoming_transactions` | 地址收到的鏈上入帳（訂單金額累加判斷用，5.2） | `order_id`(=address)、`tx_hash`、`amount`、`confirmed`（boolean，`only_confirmed=true`查詢命中即true，取代原本的數字化`confirmations`欄位，見模組4）、`block_number` |
| `consolidation_batches` / `consolidation_items` | 手動歸集操作紀錄（5.9） | batch: `master_wallet_id`、`destination_address`、`fee_source`(A1/A2)、`created_at`；item: `order_id`、`amount`、`tx_hash`、`broadcast_status`(pending/success/failed)，逐筆獨立追蹤呼應「部分失敗不影響其餘」 |
| `consolidation_address_book` | 歸集地址簿（5.9，上限30筆） | `address`(唯一)、`label`、`created_at` |
| `webhook_deliveries` | Webhook 推送紀錄與重試（5.7） | `order_id`、`event_type`、`payload`、`status`、`attempt_count`、`next_retry_at` |
| `api_keys` | API Key（5.5） | `key_hash`、`secret`（明碼存，HMAC驗簽需伺服器重算，見第7節）、`created_at`、`revoked_at` |
| `admin_account` | 單一管理帳號（5.5） | `username`、`password_hash`、`totp_secret`、`password_changed_at` |
| `audit_logs` | 操作審計日誌（5.5，含設定變更與歸集等交易性操作） | `actor`、`action_type`、`target_type`、`target_id`、`detail`(jsonb)、`created_at` |
| `system_params` | 全域參數設定（5.5，有效期/容許誤差/確認逾時） | 單列 key-value 或單列設定表，新建訂單時讀取寫入快照 |

### 併發安全

`master_wallets.last_derived_index` 用 PostgreSQL advisory lock（`pg_advisory_xact_lock(master_wallet_id)`）包住「讀取目前值→+1→寫回→建立 orders 列」這段，確保高併發建單不會分配到重複 index（此為進度.md 已定案選 PostgreSQL 的理由之一）。

## 3. HD 地址衍生模組（`internal/hdwallet`）

### 套件選型

伺服器端只做「xpub → 地址」的公鑰衍生（不碰私鑰、不簽名），沿用 [評估-Go打包Docker可行性.md](評估-Go打包Docker可行性.md) 驗證項目1同一套組合：

- `github.com/btcsuite/btcd/btcutil/hdkeychain`（v1.2.0）—— 解析 xpub、非硬化路徑公鑰子鑰衍生
- `golang.org/x/crypto/sha3` —— Keccak256（公鑰 → Tron 地址雜湊，Tron 與 Ethereum 同套機制）
- stdlib `crypto/sha256` —— Base58Check checksum（雙重 SHA256 取前4 bytes）
- `github.com/btcsuite/btcd/btcutil/base58` —— Base58 編碼

**特意不引入** `go-ethereum`／`gotron-sdk`／gRPC 相關依賴：該組套件是驗證項目2（簽名+廣播）才需要的，伺服器端衍生地址用不到簽名，引入只會不必要拉大 image（驗證數據：純手刻 11.3MB vs 含go-ethereum+gRPC 26.1MB）。

### 衍生邏輯

1. xpub 本身已編碼到 account 層級（`m/44'/195'/0'`，硬化部分已固定在 xpub 內），伺服器只需再衍生兩層非硬化路徑：`xpub.Derive(0).Derive(index)`（change=0 固定，index 為 `master_wallets.last_derived_index`）。
2. 衍生出的公鑰 → Keccak256 → 取後20 bytes → 前綴 `0x41` → 雙SHA256取前4 bytes當checksum → Base58編碼，得到 Tron `T` 開頭地址。
3. 與第2節 advisory lock 銜接：分配新 index、算出地址、寫入 `orders` 列，於同一個 DB transaction 內完成。

## 4. 鏈上監控模組（`internal/scanner`）

本節經 subagent 兩輪審查修正。第一輪審查指出核心問題：最初設計讓掃描迴圈依「是否有進行中訂單」啟停，但需求書5.3自己說事件掃描的API呼叫成本只跟區塊產生速度有關、不隨地址/訂單數量增加——為了省一個固定成本而啟停，換來一整組窗口期漏記風險，不划算。第二輪審查在此修正基礎上，補上多個「解一半」與「常駐後才浮現」的問題。

### 三個永遠常駐的背景任務

**任務1：訂單生命週期巡查**（純DB查詢，約30秒一次）
- PENDING→EXPIRED：`expires_at < now()` **且**任務2 checkpoint 已追上 `expires_at` 當下對應的區塊高度，才判定（避免 TronGrid 索引延遲導致準時付款卻被誤判過期）。
- CONFIRMING→CONFIRMATION_STALLED：同樣套用「任務3已追上」的守門條件（與EXPIRED對稱，避免系統內部處理延遲被誤判為訂單卡住）。
- **架構取捨要明講**：任務1原本可以是100%自給自足的純DB模組，加上這層守門條件後，其正確性部分依賴任務2/3是否健康，這是用「精確性」換掉「獨立可靠性」的取捨。

**任務2：事件掃描迴圈**（永遠常駐；有進行中訂單時約5秒一次，無進行中訂單時降頻至約30秒——不是停止，只是降頻，checkpoint持續推進，不重新引入窗口期漏洞，同時緩解「商戶自架部署下，7x24小時對自己的TronGrid配額是固定消耗」這個常駐後才浮現的成本維度）
- 呼叫 `GET /v1/contracts/{USDT合約}/events?event_name=Transfer&only_confirmed=false&min_block_timestamp={checkpoint之後}`，對每筆事件 `to` 欄位查 `orders.address`，命中寫入 `incoming_transactions`。
- 單輪結果達200筆上限時用 `meta.fingerprint` 在同一輪內翻頁，直到追上目前區塊高度才算完成。
- checkpoint（`scan_checkpoint.last_block_number`）推進時保留安全緩衝（落後目前查到的最新區塊 **N=20 個區塊**，約60秒@3秒/塊），依據見 [變更紀錄v0.6](開發流程框架-03-技術架構設計變更紀錄.md#v0-6)。不用 `fingerprint` 當持久化checkpoint（其語意是單次查詢分頁游標，非跨重啟續掃斷點）。
- **防禦性降級告警**（[驗證結論-09](驗證結論-09-TronGrid事件掃描保留期限與斷點續掃.md)建議）：補齊掃描連續多個歷史區間都回傳空陣列、且理論上該區間應有資料（可比對其他監控中地址同時段是否有其他事件）時，觸發告警／人工複查，不直接信任空陣列＝真的沒事件——TronGrid未公開保證保留期限，這是對「未來行為可能改變」的防禦性設計，非本次驗證發現實際問題。
- `incoming_transactions` 唯一鍵用 `(tx_hash, log_index)`，防止分頁邊界重複查詢造成金額重複累加，也避免同筆tx多筆log被誤丟棄。
- 對 TronGrid 429/5xx 要有指數退避重試（常駐迴圈才會放大這個問題）。
- **首次部署SOP**：必須等第一筆checkpoint建立後才能開放接單/顯示收款地址，否則殘留縮小版的冷啟動窗口漏洞。

**任務3：最終確定（solidified）判定＋reorg檢查**（永遠常駐）
- 定期以 `only_confirmed=true` 重新查詢 `incoming_transactions` 中尚未標記 `confirmed=true` 的交易（沿用任務2驗證過的同一端點，改帶 `only_confirmed=true` 參數），命中即代表該筆已達 Tron 協定自身認定的 solidified 狀態，寫入 `incoming_transactions.confirmed=true`，觸發訂單狀態機轉換（模組5）判斷 COMPLETED/OVERPAID。**不再自行查目前區塊高度、算「目前高度－交易高度」跟商戶設定值比較**——v0.36需求書改版拿掉「確認數」商戶可調參數後，是否達確認一律直接沿用 TronGrid `only_confirmed=true` 這個布林結果，不需要自己再算一次數字。
- reorg檢查範圍：`only_confirmed=false` 已命中、但尚未查到 `only_confirmed=true` 這段期間內的交易，才需要持續追蹤是否從鏈上消失；一旦查到 `only_confirmed=true`，即代表 Tron 協定自身已認定不可逆，該筆交易停止追蹤 reorg，**不再額外加一段緩衝期**（前版設計「確認數達標後再加安全緩衝期」是為了補足「商戶自訂確認數」與「協定自身最終確定」之間的落差，這個落差已隨確認數改版直接消失，不需要緩衝期）。查證中若發現 `tx_hash` 已從鏈上消失，標記 `status='reorged'`，累加金額計算時排除。
- **明確跳過已是 CONFIRMATION_STALLED（或任何終態）的訂單，不自動轉換回 COMPLETED**——呼應需求書5.2已定案的「系統不主動判斷改判方向，一律由商戶查證後自行決定」，STALLED訂單即使之後查到 `only_confirmed=true`，也只能靠商戶手動改判。

### Process 意外中斷重啟
- 沒有「idle→active」重設邏輯，重啟一律從 `scan_checkpoint.last_block_number` 續掃，不分是否有進行中訂單。
- 停機期間的區塊事件 TronGrid 是否還查得到，已由[驗證項目9](驗證結論-09-TronGrid事件掃描保留期限與斷點續掃.md)確認：回溯7.4年未觀察到保留期限截斷，`fingerprint`分頁跨區塊切分吻合ground truth。

### 部署層級保護
- 明確聲明：任何時候只能有一個process實例在跑這些背景任務，部署流程（含滾動更新）需保證新舊容器不重疊執行，或用DB advisory lock做leader保護。
- `scan_checkpoint`更新用`GREATEST()`保證單調遞增，搭配唯一約束，即使短暫重疊執行也不會讓checkpoint倒退或資料重複累加。

### 備援/降級
- 主要監控=TronGrid事件掃描；備援=**TronScan**（不同資料源，呼應需求書5.3原文「可搭配TronScan等獨立第三方API作為備援」）——若備援只是換TronGrid自己的另一個端點，TronGrid整體故障時主備會同時失效，不是真正異質備援。
- 事件掃描持續失敗時，降級為逐一查詢當下 PENDING/CONFIRMING 訂單地址（範圍有界，需求書5.3已允許）。降級輪詢與主要掃描需要明確的單一擁有者判斷，避免兩者同時寫入造成重複，具體切換機制留待實作階段設計。

### 金額精度
全程用 USDT 最小單位（6位小數）的整數運算（`int64`），禁止用浮點數比較金額，適用於容許誤差範圍比對等所有金額相關邏輯。

### 儀表板可見度
顯示「上次成功同步區塊：X（Y分鐘前）」；落後超過安全緩衝閾值時，需能查到「有N筆訂單卡在守門條件、尚未能判定EXPIRED/STALLED」，不只是被動的同步延遲數字。同時記錄checkpoint異常倒退事件的稽核軌跡，供客訴時追查。

### 待模組5/後續處理的缺口（記錄，非本模組bug）
- ~~COMPLETED後偵測到reorg的後續狀態機路徑未定義~~：v0.36需求書改版拿掉「確認數」商戶可調參數後，此缺口已隨之消失——COMPLETED/OVERPAID 只會在查到 `only_confirmed=true`（Tron協定自身認定不可逆）後才轉入，定義上不會再發生「已COMPLETED又被reorg打回」的情況，不需要模組5額外定義這條路徑。

## 5. 訂單狀態機模組（`internal/order`）

### 原子性做法

放棄「把金額判斷寫進 UPDATE 的 WHERE 子句」這個方向——會踩 SQL 型別/MVCC 細節，且容易誤傷手動改判路徑。改用標準模式：同一個 DB transaction 內，先 `SELECT * FROM orders WHERE id=? FOR UPDATE` 鎖定該筆訂單列，在 Go 程式碼內用鎖定期間讀到的一致資料做判斷、決定 `toStatus`，最後在同一交易內 `UPDATE` 並 `COMMIT`。業務邏輯留在 Go 端，不塞進 SQL。

### 自動路徑 vs 手動改判路徑

兩條路徑共用同一個「鎖定 → 判斷 → UPDATE」骨架，差別只在要不要多檢查業務條件：

- **自動路徑**（任務1/任務3呼叫，見模組4）：鎖定後檢查業務條件，條件不成立就直接 `ROLLBACK` 不寫入，視為正常冪等情況靜默略過。
- **手動改判路徑**（後台呼叫，見需求書5.2「手動改判」）：鎖定後只檢查狀態白名單（來源狀態是否允許改判到目標狀態），**不重新檢查金額子查詢**——操作者的人工查證本來就是要覆蓋系統判斷。

### 回傳契約

鎖定後若狀態不符白名單來源，或（自動路徑）業務條件不成立，一律 `ROLLBACK` 並回傳明確原因，不是含糊的「跳過」。自動任務對「狀態衝突」視為正常冪等情況靜默略過；手動路徑一律把任何失敗轉譯成明確錯誤訊息回給操作者。非法轉換嘗試（不在白名單內）記錄到獨立稽核日誌，不混進 `order_state_transitions`。

### 容許誤差快照

建立訂單當下（跟其餘參數快照同一時機，見模組2），直接算出 `amount_lower_bound`／`amount_upper_bound` 兩個 BIGINT 欄位（USDT 最小單位）寫死存證，運算在 Go 端用 `int64` 一次做好。判斷時只需單純的 `BETWEEN` 比較，不重算百分比（模組2 schema 需補上這兩個欄位）。

### 狀態轉換判斷條件

累加金額判斷拆兩條查詢，對應模組4任務2（即時偵測）與任務3（最終確定判定）：

- **PENDING → CONFIRMING**：`incoming_transactions` 中該地址所有**已偵測到（`only_confirmed=false` 命中，不論是否已達最終確定）**的入帳金額加總，**≥ `amount_lower_bound` 即觸發**（只看下界，不卡上界），同時寫入 `confirming_at`。
  上界判斷刻意留到下一步分流：若在 PENDING 就同時卡上下界，付款人一次匯超過金額上限會導致訂單卡死在 PENDING 直到轉 EXPIRED，跟需求書5.2 EXPIRED「金額仍未達標」的語意矛盾（超額付款明明已達標）。
- **CONFIRMING → COMPLETED/OVERPAID**：該地址所有 `incoming_transactions.confirmed=true`（即模組4任務3查到 `only_confirmed=true`，達 Tron 協定自身最終確定狀態）的入帳金額加總，落在 `[amount_lower_bound, amount_upper_bound]` 範圍內轉 COMPLETED，超過上限轉 OVERPAID。

**不再有 COMPLETED/OVERPAID → CONFIRMATION_STALLED 的 reorg 觸發邊**：v0.36需求書拿掉「確認數」商戶可調參數、改固定沿用 Tron 協定自身 solidified 狀態後，達到 COMPLETED/OVERPAID 的當下即等同協定認定不可逆，不會再發生「已完成又被 reorg 打回」的情況（見模組4「待模組5/後續處理的缺口」段落已標記此缺口消失）。也因此不需要 `decision_snapshot`/Webhook payload 額外設計 `previous_status`/`reason` 欄位去區分「首次進入 STALLED」跟「COMPLETED 被 reorg 打回」——後者已不存在。

### 手動改判寫回資料一致性

「手動重新檢查此地址」（需求書5.2/5.5）查到的鏈上最新資料寫回 `incoming_transactions`（`(tx_hash, log_index)` 唯一鍵防重複，與模組4一致），確保改判後兩張表對得起來。

### 稽核可追溯性

`order_state_transitions` 新增 `decision_snapshot`（JSONB）欄位，記錄觸發轉換當下的聚合金額、目標值、上下界——供一般稽核用途，與 reorg 邊無關，維持不變。

### 驗收要求

這些原子交易（尤其容許誤差邊界判斷）需要真實 PostgreSQL 的整合測試，不能只靠 Go 單元測試打勾——容許誤差的整數除法 bug 正是架構審查階段才抓到的例子（見上方「狀態轉換判斷條件」的上下界拆分修正），Go 端 mock 測試永遠測不出這類問題。模組4任務3需要「反應式觸發」＋「低頻全量重掃」並存，此為模組4文件待補的小幅待辦。

### Gate 已解除

依賴的模組4 Gate已解除（見模組4「Gate 已解除」段落），本模組可進入正式開發。

## 6. 前台收銀頁模組（`internal/checkout`）

### 路由與公開識別碼

- 路徑 `/checkout/{token}`，無需登入（同步修訂第1節路由表，原 `{orderId}` 參數命名易誤導為 DB 主鍵，改名）。
- 新增 `orders.public_token` 欄位（唯一索引，見模組2 schema），用 Go `crypto/rand`（非 `math/rand`）產生 32 bytes、URL-safe base64 編碼，建立訂單時產生。**不可用 `orders.id`**（可枚舉連續整數，任何人改 URL 數字即可瀏覽全部歷史訂單，外洩商業資訊）、**不可用 `merchant_order_no`**（商戶自訂字串，可能有序易猜）——這是本模組唯一的無登入端點防護機制，屬安全關鍵欄位。
- 建單時若撞到 `public_token` 唯一索引衝突（機率極低但非0），需 retry 重新產生。
- token 不存在或格式不符，一律回傳404，不區分「格式錯誤」與「存在但...」，避免探測。

### 顯示內容（對應需求書5.4）

- 收款地址（含QR code）、應付USDT金額（`orders.target_amount`，只顯示目標金額，不顯示 `amount_lower_bound`/`amount_upper_bound` 容許誤差範圍，避免曝露系統內部判定邏輯）、剩餘有效時間、目前訂單狀態。
- **狀態與倒數的顯示邏輯依狀態分流，不是單純套用 `expires_at`**：
  - PENDING：顯示「剩餘有效時間倒數」。
  - CONFIRMING：**不顯示倒數**（呼應模組5「CONFIRMING不受expires_at限制轉EXPIRED」），改顯示「確認中，請耐心等候」等不含時間壓力的狀態指示。
  - COMPLETED/OVERPAID/CONFIRMATION_STALLED/EXPIRED：終態，不顯示倒數，顯示對應結果文字。
- **倒數計時實作**：伺服器每次回應（含初始頁面渲染與每次輪詢）夾帶「剩餘秒數」（相對值，避免用戶端時鐘飄移，不傳絕對時間戳給前端自行計算），前端用一小段 inline vanilla JS（`setInterval` 每秒本地遞減顯示，每次收到新的伺服器回應時用該值重新對齊）呈現平滑倒數，不隨5秒輪詢間隔階梯式跳動；不算違反「零Node.js建置鏈」原則（該原則限制的是建置工具鏈，非禁止少量 inline JS）。
- 各狀態對付款人的具體措辭文案留待介面設計階段，但**CONFIRMATION_STALLED與EXPIRED需分開設計**（前者「已偵測到款項但確認逾時」、後者「有效期內未收到達標金額」，語意不同，不可共用文案）。

### QR code

伺服器端Go函式庫產生（如 `skip2/go-qrcode`），QR內容僅放收款地址本身、不編碼金額（Tron無廣泛採用的payment URI標準，不同於Bitcoin BIP21，多數錢包掃描只認純地址字串）；金額另以文字顯示，要求付款人自行核對後手動輸入轉帳。

### 狀態更新機制

- 前端用htmx輪詢（`hx-get`+`hx-trigger="every Ns"`）拉取局部HTML片段刷新狀態區塊，不引入WebSocket/SSE，呼應「零Node.js建置鏈」精神。
- 輪詢頻率約5秒（貼近模組4任務2掃描頻率）；因checkpoint緩衝（~60秒，見模組4），多數輪詢會是空轉，可接受，非阻塞性問題。
- **終態停止輪詢的具體實作**：後端回應終態時，回傳的HTML片段**整段替換掉原本帶 `hx-trigger="every Ns"` 屬性的容器**，換成不含該屬性的版本，讓htmx物理上不再有輪詢觸發源；**初始頁面首次渲染時，若訂單當下已是終態**（例如連結是付款完成後才被分享/重新打開），**也必須直接輸出不含 `hx-trigger` 的版本**，不可先渲染帶輪詢屬性的容器再等第一次輪詢才修正。不可只靠前端JS邏輯判斷「是否該繼續」，避免實作者遺漏。
- **已知限制**：訪客分頁若已因終態停止輪詢，之後商戶在後台手動改判（如CONFIRMATION_STALLED→COMPLETED，見需求書5.2）不會讓已停輪詢的分頁即時更新，需訪客手動重新整理才看得到最新結果；此為可接受取捨（訪客通常已離開頁面）。
- **已知的~5秒時序窗口**：`remaining_seconds` 即時依 `expires_at - now()` 計算並夾在0，到期瞬間可能短暫出現「顯示剩餘0秒，但 `orders.status` 欄位還沒被任務1翻轉成EXPIRED」的窗口（受限於任務1約30秒/任務2約5秒的背景任務頻率，見模組4），屬系統既有時序特性的自然延伸，非本模組獨有問題，可接受。

### 安全性

- 不涉及助記詞/私鑰，不需套用5.1/5.9同等級嚴格CSP，但建議基本CSP baseline防範XSS。
- 加 `<meta name="robots" content="noindex,nofollow">`，避免搜尋引擎收錄含商戶訂單金額的頁面。
- 加 `Referrer-Policy: no-referrer`（或至少same-origin），因URL帶高熵token，避免經Referer外洩給第三方資源。
- Rate limiting留給商戶自行架設的反向代理層處理（呼應第1節「不內建反向代理」既有決策），應用層不重複設計。

### Schema新增

`orders` 表新增 `public_token` 欄位（唯一索引，`crypto/rand` 產生），與 `amount_lower_bound`/`amount_upper_bound`（模組5已定案但先前未補回模組2表格清單，一併補上）。

## 7. 對外API模組（`internal/api`）

### 路由（沿用第1節 `/api/v1/...` 前綴）

- `POST /api/v1/orders` —— 建單
- `GET /api/v1/orders/{id}` —— 依系統訂單ID查詢
- `GET /api/v1/orders?merchant_order_no={xxx}` —— 依商戶訂單編號查詢

僅支援單筆查詢，不含列表/分頁；列表功能屬需求書5.5後台管理介面範疇，不重複於API層設計。

### 認證：API Key + HMAC 簽章

- Header：`X-API-Key`（明碼key）、`X-Timestamp`（Unix秒）、`X-Signature`（`HMAC-SHA256(secret, timestamp + method + path + body)`）
- 防重放：`X-Timestamp` 與伺服器當下時間差超過 ±5 分鐘即拒絕
- `api_keys.secret` 明碼存資料庫（非雜湊）：HMAC 驗簽需要伺服器用同一把 secret 重新計算簽章比對，雜湊值無法逆推重算，此為 HMAC 機制本身的限制，非設計疏漏，比照 AWS／Stripe／GitHub Webhook 等業界慣例；安全性依賴資料庫存取權限控管，不額外加應用層加密（加密需要的 master key 仍須放在伺服器啟動時可自動讀取的環境變數，形式意義大於實質防護）

### 建單API

Request body：
```json
{
  "merchant_order_no": "string，必填",
  "target_amount": "string，USDT最小單位整數字串，必填"
}
```

冪等性判斷（依需求書5.6）：
- 依 `merchant_order_no` 查詢：不存在 → 正常建立新訂單（依第3節HD衍生流程分配地址）；已存在 → 比對 `target_amount` 是否與原訂單相同：相同視為網路逾時重試，直接回傳原訂單（200）；不同視為衝突，拒絕請求（409，`ORDER_CONFLICT`）
- 比對範圍限定「同一個 `merchant_order_no`」內；不同 `merchant_order_no` 的訂單即使金額相同也互不影響，各自正常建立、各自分配獨立地址

Response：訂單ID、`merchant_order_no`、收款地址、`target_amount`、狀態、`expires_at`、前台收銀頁URL（含 `public_token`，見第6節）

### 查詢API

回傳訂單完整明細：狀態、累計已偵測金額（`incoming_transactions` 中 `only_confirmed=false` 命中總額）、累計已確認金額（`confirmed=true` 總額）、`order_state_transitions` 完整狀態變更歷史

### 錯誤回應格式

統一結構 `{"error_code": "string", "message": "string"}`，例如 `INVALID_SIGNATURE`、`ORDER_CONFLICT`、`ORDER_NOT_FOUND`

### Rate limiting

沿用第1節/第6節既有決策，留給商戶自行架設的反向代理層處理，應用層不重複設計。
