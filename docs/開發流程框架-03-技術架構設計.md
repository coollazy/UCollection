## 1. 整體架構總覽

### Process 拓樸

單一 Go binary，內部以常駐 goroutine 執行鏈上監控背景任務，不拆分多 process、不引入 message queue。

**理由**：需求書為單租戶架構、無多副本/高可用要求；docker-compose 一鍵部署精神下，越簡單越好。

**docker-compose 服務組成**：
- `app`（Go binary，內含 API/後台/前台/鏈上監控/同源代理）
- `db`（PostgreSQL）

不內建反向代理/TLS 終止（需求書已定案，見進度.md），商戶自行於前方架設 nginx/Cloudflare 等；系統本身只需監聽一般 HTTP port。

### 單一 HTTP server，依路徑分流

| 路徑前綴 | 用途 | 驗證方式 |
|---|---|---|
| `/api/v1/...` | 商戶外部系統建單/查詢（見需求書 5.6） | API Key + HMAC 簽章 |
| `/admin/...` | 後台管理介面（見需求書 5.5） | Session cookie + 2FA |
| `/checkout/{token}` | 前台收銀頁（見需求書 5.4） | 無需登入 |
| `/tron-proxy/...` | 同源代理，供手動歸集/TRX手續費頁面（見需求書 5.9）呼叫 TronGrid，架構已於驗證項目 8 驗證通過 | 已登入後台 session **且** 15分鐘內完成過TOTP新鮮驗證（見第9節 Step-up 驗證） |

### 組交易與廣播由後端統一發起

依 [驗證結論-08](驗證結論-08-嚴格CSP下組交易簽名廣播.md) 對階段03的提醒拍板：瀏覽器只跟自家後端（同源）溝通，「組交易」與「廣播」兩個對外呼叫 TronGrid 的動作，一律由後端經 `/tron-proxy` 代為執行；瀏覽器端只負責衍生 xpub/私鑰與交易簽名，不直接連線 TronGrid 網域。此設計讓 CSP `connect-src 'self'` 可以直接套用，不必為了遷就直連需求而放寬。

### 內部 package 劃分

```
cmd/ucollection/          — 入口，啟動HTTP server + 背景scanner goroutine
internal/config/          — 環境變數設定
internal/store/           — DB存取層（含migrations）
internal/hdwallet/        — xpub衍生地址邏輯
internal/order/           — 訂單/狀態機
internal/scanner/         — 鏈上事件掃描背景任務
internal/tronclient/      — 封裝呼叫TronGrid（scanner/tron-proxy共用）
internal/webhook/         — 推送/重試
internal/api/             — 對外API handler
internal/admin/           — 後台handler
internal/checkout/        — 前台handler
internal/consolidation/   — 手動歸集後端邏輯
internal/auth/            — 帳號/2FA/session
internal/audit/           — 審計日誌
web/static/js/            — 離線打包的助記詞衍生/簽名JS bundle（給瀏覽器端頁面用）
```

## 2. 資料庫 schema 設計

### 地址不獨立建表，直接併入 orders

需求書「地址與訂單永久一對一綁定」（5.1），且地址只在建立訂單當下才依索引衍生（不是預先產生地址池），兩者生命週期完全同步。`orders` 表直接帶 `master_wallet_id`／`derivation_index`／`address` 三個欄位，不另拆 `addresses` 表。

| 表 | 用途 | 關鍵欄位 |
|---|---|---|
| `master_wallets` | 代收主錢包（5.1） | `xpub`、`status`(active/inactive)、`last_derived_index`（併發分配地址用，見下） |

### 併發安全

`master_wallets.last_derived_index` 用 PostgreSQL advisory lock（`pg_advisory_xact_lock(master_wallet_id)`）包住「讀取目前值→+1→寫回→建立 orders 列」這段，確保高併發建單不會分配到重複 index（此為進度.md 已定案選 PostgreSQL 的理由之一）。

## 3. HD 地址衍生模組（`internal/hdwallet`）

### 套件選型

伺服器端只做「xpub → 地址」的公鑰衍生（不碰私鑰、不簽名），沿用 [評估-Go打包Docker可行性.md](評估-Go打包Docker可行性.md) 驗證項目1同一套組合：

- `github.com/btcsuite/btcd/btcutil/hdkeychain`（v1.2.0）—— 解析 xpub、非硬化路徑公鑰子鑰衍生
- `golang.org/x/crypto/sha3` —— Keccak256（公鑰 → Tron 地址雜湊，Tron 與 Ethereum 同套機制）
- stdlib `crypto/sha256` —— Base58Check checksum（雙重 SHA256 取前4 bytes）
- `github.com/btcsuite/btcd/btcutil/base58` —— Base58 編碼

**特意不引入** `go-ethereum`／`gotron-sdk`／gRPC 相關依賴：該組套件是驗證項目2（簽名+廣播）才需要的，伺服器端衍生地址用不到簽名，引入只會不必要拉大 image（驗證數據：純手刻 11.3MB vs 含go-ethereum+gRPC 26.1MB）。

### 衍生邏輯

1. xpub 本身已編碼到 account 層級（`m/44'/195'/0'`，硬化部分已固定在 xpub 內），伺服器只需再衍生兩層非硬化路徑：`xpub.Derive(0).Derive(index)`（change=0 固定，index 為 `master_wallets.last_derived_index`）。
2. 衍生出的公鑰 → Keccak256 → 取後20 bytes → 前綴 `0x41` → 雙SHA256取前4 bytes當checksum → Base58編碼，得到 Tron `T` 開頭地址。
3. 與第2節 advisory lock 銜接：分配新 index、算出地址、寫入 `orders` 列，於同一個 DB transaction 內完成。

## 4. 鏈上監控模組（`internal/scanner`）

本節經 subagent 兩輪審查修正。第一輪審查指出核心問題：最初設計讓掃描迴圈依「是否有進行中訂單」啟停，但需求書5.3自己說事件掃描的API呼叫成本只跟區塊產生速度有關、不隨地址/訂單數量增加——為了省一個固定成本而啟停，換來一整組窗口期漏記風險，不划算。第二輪審查在此修正基礎上，補上多個「解一半」與「常駐後才浮現」的問題。

### 三個永遠常駐的背景任務

**任務1：訂單生命週期巡查**（純DB查詢，約30秒一次）
- PENDING→EXPIRED：`expires_at < now()` **且**任務2 checkpoint 已追上 `expires_at` 當下對應的區塊高度，才判定（避免 TronGrid 索引延遲導致準時付款卻被誤判過期）。
- CONFIRMING→CONFIRMATION_STALLED：同樣套用「任務3已追上」的守門條件（與EXPIRED對稱，避免系統內部處理延遲被誤判為訂單卡住）。
- **架構取捨要明講**：任務1原本可以是100%自給自足的純DB模組，加上這層守門條件後，其正確性部分依賴任務2/3是否健康，這是用「精確性」換掉「獨立可靠性」的取捨。

**任務2：事件掃描迴圈**（永遠常駐；有進行中訂單時約5秒一次，無進行中訂單時降頻至約30秒——不是停止，只是降頻，checkpoint持續推進，不重新引入窗口期漏洞，同時緩解「商戶自架部署下，7x24小時對自己的TronGrid配額是固定消耗」這個常駐後才浮現的成本維度）
- 呼叫 `GET /v1/contracts/{USDT合約}/events?event_name=Transfer&only_confirmed=false&min_block_timestamp={checkpoint之後}`，對每筆事件 `to` 欄位查 `orders.address`，命中寫入 `incoming_transactions`。
- 單輪結果達200筆上限時用 `meta.fingerprint` 在同一輪內翻頁，直到追上目前區塊高度才算完成。
- checkpoint（`scan_checkpoint.last_block_number`）推進時保留安全緩衝（落後目前查到的最新區塊 **N=20 個區塊**，約60秒@3秒/塊），依據見 [變更紀錄v0.6](開發流程框架-03-技術架構設計變更紀錄.md#v0-6)。不用 `fingerprint` 當持久化checkpoint（其語意是單次查詢分頁游標，非跨重啟續掃斷點）。
- **防禦性降級告警**（[驗證結論-09](驗證結論-09-TronGrid事件掃描保留期限與斷點續掃.md)建議）：補齊掃描連續多個歷史區間都回傳空陣列、且理論上該區間應有資料（可比對其他監控中地址同時段是否有其他事件）時，觸發告警／人工複查，不直接信任空陣列＝真的沒事件——TronGrid未公開保證保留期限，這是對「未來行為可能改變」的防禦性設計，非本次驗證發現實際問題。
- `incoming_transactions` 唯一鍵用 `(tx_hash, log_index)`，防止分頁邊界重複查詢造成金額重複累加，也避免同筆tx多筆log被誤丟棄。
- 對 TronGrid 429/5xx 要有指數退避重試（常駐迴圈才會放大這個問題）。
- **首次部署SOP**：必須等第一筆checkpoint建立後才能開放接單/顯示收款地址，否則殘留縮小版的冷啟動窗口漏洞。

**任務3：最終確定（solidified）判定＋reorg檢查**（永遠常駐）
- 定期以 `only_confirmed=true` 重新查詢 `incoming_transactions` 中尚未標記 `confirmed=true` 的交易（沿用任務2驗證過的同一端點，改帶 `only_confirmed=true` 參數），命中即代表該筆已達 Tron 協定自身認定的 solidified 狀態，寫入 `incoming_transactions.confirmed=true`，觸發訂單狀態機轉換（模組5）判斷 COMPLETED/OVERPAID。**不再自行查目前區塊高度、算「目前高度－交易高度」跟商戶設定值比較**——v0.36需求書改版拿掉「確認數」商戶可調參數後，是否達確認一律直接沿用 TronGrid `only_confirmed=true` 這個布林結果，不需要自己再算一次數字。
- reorg檢查範圍：`only_confirmed=false` 已命中、但尚未查到 `only_confirmed=true` 這段期間內的交易，才需要持續追蹤是否從鏈上消失；一旦查到 `only_confirmed=true`，即代表 Tron 協定自身已認定不可逆，該筆交易停止追蹤 reorg，**不再額外加一段緩衝期**（前版設計「確認數達標後再加安全緩衝期」是為了補足「商戶自訂確認數」與「協定自身最終確定」之間的落差，這個落差已隨確認數改版直接消失，不需要緩衝期）。查證中若發現 `tx_hash` 已從鏈上消失，標記 `status='reorged'`，累加金額計算時排除。
- **明確跳過已是 CONFIRMATION_STALLED（或任何終態）的訂單，不自動轉換回 COMPLETED**——呼應需求書5.2已定案的「系統不主動判斷改判方向，一律由商戶查證後自行決定」，STALLED訂單即使之後查到 `only_confirmed=true`，也只能靠商戶手動改判。

### Process 意外中斷重啟
- 沒有「idle→active」重設邏輯，重啟一律從 `scan_checkpoint.last_block_number` 續掃，不分是否有進行中訂單。
- 停機期間的區塊事件 TronGrid 是否還查得到，已由[驗證項目9](驗證結論-09-TronGrid事件掃描保留期限與斷點續掃.md)確認：回溯7.4年未觀察到保留期限截斷，`fingerprint`分頁跨區塊切分吻合ground truth。

### 部署層級保護
- 明確聲明：任何時候只能有一個process實例在跑這些背景任務，部署流程（含滾動更新）需保證新舊容器不重疊執行，或用DB advisory lock做leader保護。
- `scan_checkpoint`更新用`GREATEST()`保證單調遞增，搭配唯一約束，即使短暫重疊執行也不會讓checkpoint倒退或資料重複累加。

### 備援/降級
- 主要監控=TronGrid事件掃描；備援=**TronScan**（不同資料源，呼應需求書5.3原文「可搭配TronScan等獨立第三方API作為備援」）——若備援只是換TronGrid自己的另一個端點，TronGrid整體故障時主備會同時失效，不是真正異質備援。
- 事件掃描持續失敗時，降級為逐一查詢當下 PENDING/CONFIRMING 訂單地址（範圍有界，需求書5.3已允許）。降級輪詢與主要掃描需要明確的單一擁有者判斷，避免兩者同時寫入造成重複，具體切換機制留待實作階段設計。

### 金額精度
全程用 USDT 最小單位（6位小數）的整數運算（`int64`），禁止用浮點數比較金額，適用於容許誤差範圍比對等所有金額相關邏輯。

### 儀表板可見度
顯示「上次成功同步區塊：X（Y分鐘前）」；落後超過安全緩衝閾值時，需能查到「有N筆訂單卡在守門條件、尚未能判定EXPIRED/STALLED」，不只是被動的同步延遲數字。同時記錄checkpoint異常倒退事件的稽核軌跡，供客訴時追查。

### 待模組5/後續處理的缺口（記錄，非本模組bug）
- ~~COMPLETED後偵測到reorg的後續狀態機路徑未定義~~：v0.36需求書改版拿掉「確認數」商戶可調參數後，此缺口已隨之消失——COMPLETED/OVERPAID 只會在查到 `only_confirmed=true`（Tron協定自身認定不可逆）後才轉入，定義上不會再發生「已COMPLETED又被reorg打回」的情況，不需要模組5額外定義這條路徑。
- **累加金額不分入帳來源**（任何人都能轉USDT到公開地址，系統一律計入累計總額）——這是TRC20代收系統的常態設計，非疏漏，於此明講避免之後被誤認為漏洞。
- 5.9「已完成歸集地址不再監控」的邊界情況：若商戶對尚未終態的訂單提前手動歸集，掃描邏輯仍會持續比對該地址（只依address查表，不看訂單狀態），不會出問題，但需求書本身沒有明講「歸集只能對終態訂單操作」，屬於需求書措辭層級的小缺口，列記供之後回頭確認。

### Gate 已解除
驗證項目9結果PASS、checkpoint安全緩衝N值（20個區塊）已拍板，見 [變更紀錄v0.6](開發流程框架-03-技術架構設計變更紀錄.md#v0-6)。本模組可進入正式開發。

## 5. 訂單狀態機模組（`internal/order`）

### 原子性做法

放棄「把金額判斷寫進 UPDATE 的 WHERE 子句」這個方向——會踩 SQL 型別/MVCC 細節，且容易誤傷手動改判路徑。改用標準模式：同一個 DB transaction 內，先 `SELECT * FROM orders WHERE id=? FOR UPDATE` 鎖定該筆訂單列，在 Go 程式碼內用鎖定期間讀到的一致資料做判斷、決定 `toStatus`，最後在同一交易內 `UPDATE` 並 `COMMIT`。業務邏輯留在 Go 端，不塞進 SQL。

### 自動路徑 vs 手動改判路徑

兩條路徑共用同一個「鎖定 → 判斷 → UPDATE」骨架，差別只在要不要多檢查業務條件：

- **自動路徑**（任務1/任務3呼叫，見模組4）：鎖定後檢查業務條件，條件不成立就直接 `ROLLBACK` 不寫入，視為正常冪等情況靜默略過。
- **手動改判路徑**（後台呼叫，見需求書5.2「手動改判」）：鎖定後只檢查狀態白名單（來源狀態是否允許改判到目標狀態），**不重新檢查金額子查詢**——操作者的人工查證本來就是要覆蓋系統判斷。

### 回傳契約

鎖定後若狀態不符白名單來源，或（自動路徑）業務條件不成立，一律 `ROLLBACK` 並回傳明確原因，不是含糊的「跳過」。自動任務對「狀態衝突」視為正常冪等情況靜默略過；手動路徑一律把任何失敗轉譯成明確錯誤訊息回給操作者。非法轉換嘗試（不在白名單內）記錄到獨立稽核日誌，不混進 `order_state_transitions`。

`UPDATE` 成功、`COMMIT` 前，若 `toStatus` 為終態（COMPLETED/OVERPAID/CONFIRMATION_STALLED/EXPIRED），同一 transaction 內順帶 INSERT 一筆 `webhook_deliveries`，觸發 Webhook 通知（見第8節）。

### 容許誤差快照

建立訂單當下（跟其餘參數快照同一時機，見模組2），直接算出 `amount_lower_bound`／`amount_upper_bound` 兩個 BIGINT 欄位（USDT 最小單位）寫死存證，運算在 Go 端用 `int64` 一次做好。判斷時只需單純的 `BETWEEN` 比較，不重算百分比（模組2 schema 需補上這兩個欄位）。

### 狀態轉換判斷條件

累加金額判斷拆兩條查詢，對應模組4任務2（即時偵測）與任務3（最終確定判定）：

- **PENDING → CONFIRMING**：`incoming_transactions` 中該地址所有**已偵測到（`only_confirmed=false` 命中，不論是否已達最終確定）**的入帳金額加總，**≥ `amount_lower_bound` 即觸發**（只看下界，不卡上界），同時寫入 `confirming_at`。
  上界判斷刻意留到下一步分流：若在 PENDING 就同時卡上下界，付款人一次匯超過金額上限會導致訂單卡死在 PENDING 直到轉 EXPIRED，跟需求書5.2 EXPIRED「金額仍未達標」的語意矛盾（超額付款明明已達標）。
- **CONFIRMING → COMPLETED/OVERPAID**：該地址所有 `incoming_transactions.confirmed=true`（即模組4任務3查到 `only_confirmed=true`，達 Tron 協定自身最終確定狀態）的入帳金額加總，落在 `[amount_lower_bound, amount_upper_bound]` 範圍內轉 COMPLETED，超過上限轉 OVERPAID。

**不再有 COMPLETED/OVERPAID → CONFIRMATION_STALLED 的 reorg 觸發邊**：v0.36需求書拿掉「確認數」商戶可調參數、改固定沿用 Tron 協定自身 solidified 狀態後，達到 COMPLETED/OVERPAID 的當下即等同協定認定不可逆，不會再發生「已完成又被 reorg 打回」的情況（見模組4「待模組5/後續處理的缺口」段落已標記此缺口消失）。也因此不需要 `decision_snapshot`/Webhook payload 額外設計 `previous_status`/`reason` 欄位去區分「首次進入 STALLED」跟「COMPLETED 被 reorg 打回」——後者已不存在。

### 手動改判寫回資料一致性

「手動重新檢查此地址」（需求書5.2/5.5）查到的鏈上最新資料寫回 `incoming_transactions`（`(tx_hash, log_index)` 唯一鍵防重複，與模組4一致），確保改判後兩張表對得起來。

### 稽核可追溯性

`order_state_transitions` 新增 `decision_snapshot`（JSONB）欄位，記錄觸發轉換當下的聚合金額、目標值、上下界——供一般稽核用途，與 reorg 邊無關，維持不變。

### 驗收要求

這些原子交易（尤其容許誤差邊界判斷）需要真實 PostgreSQL 的整合測試，不能只靠 Go 單元測試打勾——容許誤差的整數除法 bug 正是架構審查階段才抓到的例子（見上方「狀態轉換判斷條件」的上下界拆分修正），Go 端 mock 測試永遠測不出這類問題。模組4任務3需要「反應式觸發」＋「低頻全量重掃」並存，此為模組4文件待補的小幅待辦。

### Gate 已解除

依賴的模組4 Gate已解除（見模組4「Gate 已解除」段落），本模組可進入正式開發。

## 6. 前台收銀頁模組（`internal/checkout`）

### 路由與公開識別碼

- 路徑 `/checkout/{token}`，無需登入（同步修訂第1節路由表，原 `{orderId}` 參數命名易誤導為 DB 主鍵，改名）。
- 新增 `orders.public_token` 欄位（唯一索引，見模組2 schema），用 Go `crypto/rand`（非 `math/rand`）產生 32 bytes、URL-safe base64 編碼，建立訂單時產生。**不可用 `orders.id`**（可枚舉連續整數，任何人改 URL 數字即可瀏覽全部歷史訂單，外洩商業資訊）、**不可用 `merchant_order_no`**（商戶自訂字串，可能有序易猜）——這是本模組唯一的無登入端點防護機制，屬安全關鍵欄位。
- 建單時若撞到 `public_token` 唯一索引衝突（機率極低但非0），需 retry 重新產生。
- token 不存在或格式不符，一律回傳404，不區分「格式錯誤」與「存在但...」，避免探測。

### 顯示內容（對應需求書5.4）

- 收款地址（含QR code）、應付USDT金額（`orders.target_amount`，只顯示目標金額，不顯示 `amount_lower_bound`/`amount_upper_bound` 容許誤差範圍，避免曝露系統內部判定邏輯）、剩餘有效時間、目前訂單狀態。
- **狀態與倒數的顯示邏輯依狀態分流，不是單純套用 `expires_at`**：
  - PENDING：顯示「剩餘有效時間倒數」。
  - CONFIRMING：**不顯示倒數**（呼應模組5「CONFIRMING不受expires_at限制轉EXPIRED」），改顯示「確認中，請耐心等候」等不含時間壓力的狀態指示。
  - COMPLETED/OVERPAID/CONFIRMATION_STALLED/EXPIRED：終態，不顯示倒數，顯示對應結果文字。
- **倒數計時實作**：伺服器每次回應（含初始頁面渲染與每次輪詢）夾帶「剩餘秒數」（相對值，避免用戶端時鐘飄移，不傳絕對時間戳給前端自行計算），前端用一小段 inline vanilla JS（`setInterval` 每秒本地遞減顯示，每次收到新的伺服器回應時用該值重新對齊）呈現平滑倒數，不隨5秒輪詢間隔階梯式跳動；不算違反「零Node.js建置鏈」原則（該原則限制的是建置工具鏈，非禁止少量 inline JS）。
- 各狀態對付款人的具體措辭文案留待介面設計階段，但**CONFIRMATION_STALLED與EXPIRED需分開設計**（前者「已偵測到款項但確認逾時」、後者「有效期內未收到達標金額」，語意不同，不可共用文案）。

### QR code

伺服器端Go函式庫產生（如 `skip2/go-qrcode`），QR內容僅放收款地址本身、不編碼金額（Tron無廣泛採用的payment URI標準，不同於Bitcoin BIP21，多數錢包掃描只認純地址字串）；金額另以文字顯示，要求付款人自行核對後手動輸入轉帳。

### 狀態更新機制

- 前端用htmx輪詢（`hx-get`+`hx-trigger="every Ns"`）拉取局部HTML片段刷新狀態區塊，不引入WebSocket/SSE，呼應「零Node.js建置鏈」精神。
- 輪詢頻率約5秒（貼近模組4任務2掃描頻率）；因checkpoint緩衝（~60秒，見模組4），多數輪詢會是空轉，可接受，非阻塞性問題。
- **終態停止輪詢的具體實作**：後端回應終態時，回傳的HTML片段**整段替換掉原本帶 `hx-trigger="every Ns"` 屬性的容器**，換成不含該屬性的版本，讓htmx物理上不再有輪詢觸發源；**初始頁面首次渲染時，若訂單當下已是終態**（例如連結是付款完成後才被分享/重新打開），**也必須直接輸出不含 `hx-trigger` 的版本**，不可先渲染帶輪詢屬性的容器再等第一次輪詢才修正。不可只靠前端JS邏輯判斷「是否該繼續」，避免實作者遺漏。
- **已知限制**：訪客分頁若已因終態停止輪詢，之後商戶在後台手動改判（如CONFIRMATION_STALLED→COMPLETED，見需求書5.2）不會讓已停輪詢的分頁即時更新，需訪客手動重新整理才看得到最新結果；此為可接受取捨（訪客通常已離開頁面）。
- **已知的~5秒時序窗口**：`remaining_seconds` 即時依 `expires_at - now()` 計算並夾在0，到期瞬間可能短暫出現「顯示剩餘0秒，但 `orders.status` 欄位還沒被任務1翻轉成EXPIRED」的窗口（受限於任務1約30秒/任務2約5秒的背景任務頻率，見模組4），屬系統既有時序特性的自然延伸，非本模組獨有問題，可接受。

### 安全性

- 不涉及助記詞/私鑰，不需套用5.1/5.9同等級嚴格CSP，但建議基本CSP baseline防範XSS。
- 加 `<meta name="robots" content="noindex,nofollow">`，避免搜尋引擎收錄含商戶訂單金額的頁面。
- 加 `Referrer-Policy: no-referrer`（或至少same-origin），因URL帶高熵token，避免經Referer外洩給第三方資源。
- Rate limiting留給商戶自行架設的反向代理層處理（呼應第1節「不內建反向代理」既有決策），應用層不重複設計。

### Schema新增

`orders` 表新增 `public_token` 欄位（唯一索引，`crypto/rand` 產生），與 `amount_lower_bound`/`amount_upper_bound`（模組5已定案但先前未補回模組2表格清單，一併補上）。

## 7. 對外API模組（`internal/api`）

### 路由（沿用第1節 `/api/v1/...` 前綴）

- `POST /api/v1/orders` —— 建單
- `GET /api/v1/orders/{id}` —— 依系統訂單ID查詢
- `GET /api/v1/orders?merchant_order_no={xxx}` —— 依商戶訂單編號查詢

僅支援單筆查詢，不含列表/分頁；列表功能屬需求書5.5後台管理介面範疇，不重複於API層設計。

### 認證：API Key + HMAC 簽章

- Header：`X-API-Key`（明碼key）、`X-Timestamp`（Unix秒）、`X-Signature`（`HMAC-SHA256(secret, timestamp + method + path + body)`）
- 防重放：`X-Timestamp` 與伺服器當下時間差超過 ±5 分鐘即拒絕
- `api_keys.secret` 明碼存資料庫（非雜湊）：HMAC 驗簽需要伺服器用同一把 secret 重新計算簽章比對，雜湊值無法逆推重算，此為 HMAC 機制本身的限制，非設計疏漏，比照 AWS／Stripe／GitHub Webhook 等業界慣例；安全性依賴資料庫存取權限控管，不額外加應用層加密（加密需要的 master key 仍須放在伺服器啟動時可自動讀取的環境變數，形式意義大於實質防護）

### 建單API

Request body：
```json
{
  "merchant_order_no": "string，必填",
  "target_amount": "string，USDT最小單位整數字串，必填"
}
```

冪等性判斷（依需求書5.6）：
- 依 `merchant_order_no` 查詢：不存在 → 正常建立新訂單（依第3節HD衍生流程分配地址）；已存在 → 比對 `target_amount` 是否與原訂單相同：相同視為網路逾時重試，直接回傳原訂單（200）；不同視為衝突，拒絕請求（409，`ORDER_CONFLICT`）
- 比對範圍限定「同一個 `merchant_order_no`」內；不同 `merchant_order_no` 的訂單即使金額相同也互不影響，各自正常建立、各自分配獨立地址

Response：訂單ID、`merchant_order_no`、收款地址、`target_amount`、狀態、`expires_at`、前台收銀頁URL（含 `public_token`，見第6節）

### 查詢API

回傳訂單完整明細：狀態、累計已偵測金額（`incoming_transactions` 中 `only_confirmed=false` 命中總額）、累計已確認金額（`confirmed=true` 總額）、`order_state_transitions` 完整狀態變更歷史

### 錯誤回應格式

統一結構 `{"error_code": "string", "message": "string"}`，例如 `INVALID_SIGNATURE`、`ORDER_CONFLICT`、`ORDER_NOT_FOUND`

### Rate limiting

沿用第1節/第6節既有決策，留給商戶自行架設的反向代理層處理，應用層不重複設計。

## 8. Webhook 通知模組（`internal/webhook`）

### 觸發整合

模組5「鎖定→判斷→UPDATE→COMMIT」骨架於 UPDATE 成功、COMMIT 前新增一步：若 `toStatus` 為終態（COMPLETED/OVERPAID/CONFIRMATION_STALLED/EXPIRED，含手動改判重新進入終態），同一 transaction 內 INSERT 一筆 `webhook_deliveries`。觸發點涵蓋模組4任務1（PENDING→EXPIRED、CONFIRMING→CONFIRMATION_STALLED）、任務3（CONFIRMING→COMPLETED/OVERPAID），與需求書5.2手動改判規則（STALLED→COMPLETED/OVERPAID/EXPIRED、EXPIRED→COMPLETED/OVERPAID）。採 transactional outbox 模式，不引入 message queue（呼應第1節既有決策），把「狀態轉換」與「網路推送是否成功」解耦。

### Schema（取代第2節 `webhook_deliveries` 原定義）

- `webhook_deliveries`（投遞邏輯單位）：`event_id`（Go `crypto/rand` 應用層產生，比照 `public_token` 慣例，INSERT 前先產生）、`order_id`（無唯一約束，允許同一訂單因改判產生多筆）、`event_type`、`payload`（TEXT，寫入當下固定，重試不變動）、`status`（awaiting_config/pending/sending/delivered/failed）、`attempt_count`（只反映自動重試次數，手動重發不影響）、`next_retry_at`、`updated_at`
- `webhook_delivery_attempts`（逐次嘗試明細，append-only）：`delivery_id`、`attempt_no`、`http_status`、`response_body`（截斷存）、`attempted_at`、`triggered_by`（auto/manual）
- `system_params` 新增 `webhook_url`、`webhook_secret`：與本表其餘欄位（有效期/容許誤差等，訂單建立時讀取寫入快照）性質不同，這兩欄一律於**發送當下**讀取最新值，不做快照

### at-least-once 語意

系統為 at-least-once：process 重啟等情況可能重複推送同一 event，商戶端須依 payload 內 `event_id` 自行去重，不保證恰好一次。

### Worker 取件與逾時回收

```sql
SELECT id FROM webhook_deliveries
WHERE (status='pending' AND next_retry_at<=now())
   OR (status='sending' AND updated_at < now() - interval '2 minutes')
ORDER BY next_retry_at LIMIT N FOR UPDATE SKIP LOCKED
```

取得後立即 UPDATE `status='sending', updated_at=now()` 才送出 HTTP，避免部署重疊實例搶到同一筆；`sending` 超過2分鐘未更新視為異常（process 在 HTTP 完成前當機），會被同一段查詢重新撿回，避免永久卡死。主佇列輪詢頻率10秒一次。

### webhook_secret 產生/測試/輪替

後台可選「系統產生」（`crypto/rand`，全文可見供複製）或手動輸入。「測試」用 `event_type=TEST_PING` 同步打一次、不落地 `webhook_deliveries`、不消耗重試額度（已知限制：若商戶端對 `event_type` 做嚴格白名單驗證，可能拒絕未知值，測試結果需結合 HTTP 狀態碼判讀）。輪替無過渡期：換 secret 立即套用到所有尚未送達的排隊記錄，後台變更頁面須顯示警語提醒商戶同步更新驗簽端設定。

### 未設定 URL/secret 的邊界

`webhook_url` 或 `webhook_secret` 任一未設定，寫入 `status='awaiting_config'`（不消耗 `attempt_count`），每小時檢查一次是否已補齊兩者，補齊後轉入 `pending` 開始正常倒數。

### HMAC 簽章

沿用第7節API模組同一套HMAC-SHA256設計，用商戶在後台設定的**獨立** `webhook_secret`（不與 `api_keys.secret` 共用）。Header：`X-Webhook-Timestamp`+`X-Webhook-Signature`（`HMAC-SHA256(webhook_secret, timestamp+body)`），一律在實際發送當下即時運算；金額欄位用字串型態（呼應第7節precedent）。

### Payload

```json
{
  "event_id": "...",
  "event_type": "ORDER_COMPLETED | ORDER_OVERPAID | ORDER_CONFIRMATION_STALLED | ORDER_EXPIRED",
  "order_id": "...",
  "merchant_order_no": "...",
  "status": "COMPLETED",
  "target_amount": "...",
  "total_confirmed_amount": "...",
  "occurred_at": "ISO8601"
}
```

### 重試策略

delay=1分鐘起每次倍增、封頂6小時，自第一次失敗起累計**24小時**後停止自動重試並標記 `status='failed'`，之後只能靠後台手動重發。

### 手動重發

不受狀態限制、隨時可觸發，寫入 `webhook_delivery_attempts`（`triggered_by='manual'`），不影響 `attempt_count` 與既有 `next_retry_at` 排程；成功→`delivered`；失敗→維持原 `status` 不變。

### 被動可見度

後台Dashboard摘要顯示「失敗中/待重試」與「待設定（awaiting_config）」兩類筆數，商戶主動查看時可見；此為被動顯示，不違反需求書5.5「本版不做Webhook持續失敗的自動偵測與主動通知」的既有決策。

### HTTP細節

不follow重新導向（redirect視為失敗）、`Content-Type: application/json`、固定`User-Agent`、逾時10秒、2xx視為成功。

## 9. 帳號安全模組（`internal/auth`）

### 帳號模型

- 單一 `admin_account` 資料表（第2節已定義：`username`、`password_hash`、`totp_secret`、`password_changed_at`；本節新增 `last_totp_step`，見下方TOTP重放防護）。App 啟動時檢查該表是否已有記錄；若無，從環境變數（如 `ADMIN_USERNAME`/`ADMIN_PASSWORD`）一次性建立唯一一筆記錄。之後即使環境變數仍存在也不會再次覆蓋既有記錄，避免部署重啟時把商戶已自行變更的密碼打回原始值。
- 密碼雜湊：`golang.org/x/crypto/bcrypt`，cost=12。
- 密碼格式規則（依需求書5.5拍板）：僅檢查長度 ≥ 12 碼，不做大小寫/數字/符號複雜度檢查，前後端規則一致。

### 登入流程（兩階段：密碼 → TOTP）

1. `POST /admin/login`：驗證 username + password（`bcrypt.CompareHashAndPassword`）。成功後於 `admin_sessions` 建立一筆 `status='pending_2fa'` 的暫時 session（token 用 `crypto/rand` 32 bytes 產生，資料庫僅存 SHA-256 雜湊、不存明碼，比照密碼不可逆保存的精神；cookie 帶原始 token），`expires_at = now() + 5分鐘`。密碼錯誤則不建立任何 session 列。
2. 若 `admin_account.totp_secret IS NULL`（首次登入、尚未設定2FA）：`pending_2fa` 階段導向強制設定頁——用 `pquerna/otp`（純 Go 實作 RFC6238，離線運算不依賴外部服務）產生新 secret，寫入該筆 session 列的 `pending_totp_secret` 欄位（明碼存，原因同 `api_keys.secret`：驗證當下需要用同一把 secret 重算 TOTP 碼比對，雜湊值無法逆推重算），顯示 QR code（沿用第6節已選定的 `skip2/go-qrcode`）與手動輸入碼備援。`POST /admin/login/totp-setup` 收到商戶輸入的驗證碼後：先用 `UPDATE admin_account SET totp_secret=$1 WHERE totp_secret IS NULL` 帶條件寫入（若這期間已被其他並行 `pending_2fa` session 搶先完成設定，此 UPDATE 影響列數為0，回傳明確錯誤「2FA已由其他session完成設定」，該 session 需改走步驟3一般TOTP登入，不得再用自己手上的 `pending_totp_secret`）；寫入成功才將該筆 session 轉為 `active` 並清空自己的 `pending_totp_secret` 欄位。**寫入 `admin_account.totp_secret` 是唯一能讓此欄位從 NULL 變成有值的路徑**，沒有其他管道可繞過或重設（呼應需求書5.5「不提供應用層級2FA救援機制」，遺失後只能資料庫層級操作，等同把此欄位重設回NULL、重新走一次此流程）。
3. 若已設定：`pending_2fa` 階段要求輸入 TOTP code，`POST /admin/login/totp` 驗證通過後（驗證細節見下方TOTP驗證參數），將該筆 session 列更新為 `status='active'`、`expires_at=now()+12小時`、`last_totp_verified_at=now()`。
4. 兩階段任一步驟失敗，皆計入下方登入限流與per-session嘗試次數上限。`pending_2fa` session 超過5分鐘未完成第二階段即自然過期（下次請求時因 `expires_at` 已過視同未登入），須從步驟1重新開始。

### TOTP 驗證參數

- 時間步長：標準30秒一期；接受視窗 ±1 期（即實際可接受前後各30秒，共90秒），涵蓋伺服器與手機時鐘的合理漂移，不額外擴大（過寬會放大可猜中組合空間）。
- **重放防護**：`admin_account` 新增 `last_totp_step`（bigint，記錄最近一次驗證成功所在的時間步序號）。驗證成功時若計算出的時間步 ≤ `last_totp_step`，判定為「碼已被使用」（區別於下方「碼錯誤」，見登入限流段落），回覆明確錯誤訊息（例如「此驗證碼已被使用，請等待新一組驗證碼後再試」），**不計入 `totp_attempt_count`**；驗證通過（碼正確且未被使用過）才更新 `last_totp_step` 為本次時間步。此欄位是帳號層級單一值（非per-session），因為 TOTP secret 本身也是帳號層級單一份。
  - **已知取捨**：單一帳號同時有兩個瀏覽器分頁各自需要TOTP驗證（例如一個在完成登入、另一個因閒置15分鐘觸發`/admin/reverify-totp`）、且管理者把手機上同一組當前碼分別貼進兩邊，較晚送達的那個請求會因為碼已被先送達的請求消耗掉而判定為「已被使用」，須等待下一組新碼（最多30秒）才能完成。這是帳號層級單一 `last_totp_step` 換取「防止密碼外洩後codeleak被另一個不同session重放」這個真正安全目的的必然代價，發生機率低（需要巧合的雙分頁同時操作）且不計入嘗試次數、有明確錯誤訊息引導，判定為可接受。

### Session 模型（`admin_sessions` 表，第2節新增）

- 欄位：`id`、`token_hash`（SHA-256 hex，唯一索引；碰撞機率密碼學上趨近於零，不比照 `public_token` 設計retry邏輯）、`status`（pending_2fa/active）、`pending_totp_secret`（僅首次設定2FA流程使用，見上方）、`totp_attempt_count`（本筆session的TOTP驗證連續失敗次數，含登入第二階段與下方step-up重驗證，任一次驗證成功即歸零，詳見登入限流段落）、`created_at`、`expires_at`、`last_seen_at`、`last_totp_verified_at`。
- **`expires_at` 是唯一過期判斷依據**，不額外用 `created_at` 動態推算：`pending_2fa` 建立時設為 `now()+5分鐘`；轉 `active` 時設為 `now()+12小時`（即絕對上限，此後不再隨活動延長）。`RequireSession` middleware 每次請求檢查 `status='active'` **且** `now() < expires_at` **且** `now()-last_seen_at < 30分鐘`，三者皆成立才放行（三者任一不成立即視為過期或未完成登入，清除cookie、刪除該筆session列，導向登入頁）；成立則更新 `last_seen_at=now()`。**明確排除 `pending_2fa` 狀態的session存取除登入流程本身以外的任何 `/admin/...` 路由**——`pending_2fa` session 若被拿去打其他後台路由，因 `status≠'active'` 一律被拒，不構成繞過2FA的漏洞。
- Cookie 屬性：`HttpOnly`、`SameSite=Strict`；`Secure` 是否附加由環境變數（如 `COOKIE_SECURE`，預設 `true`）控制——呼應第1節「不內建反向代理/TLS」既有決策，正式部署預期前方有HTTPS反代（`Secure` 看的是瀏覽器與其直接連線端之間的協定，預設開啟即可）；若商戶在無TLS的測試環境直接連線 `app` container，需自行關閉此旗標才能完成登入，此點須寫入部署文件。
- 理由（30分鐘閒置＋12小時絕對上限）：後台非高頻操作介面，30分鐘閒置逾時平衡可用性與憑證外洩風險；12小時絕對上限確保即使 session token 外洩，攻擊者可用窗口有界，且強制每天至少完整驗證一次2FA。
- 允許同帳號多組並行有效 session（例如同時用電腦與手機），不做「新登入踢掉舊session」限制，需求書未要求此限制，不額外設計。
- Logout（`POST /admin/logout`）：刪除當前session列＋清cookie。
- 密碼變更成功時：刪除該帳號**所有** session 列（含發起變更的當前session），前端導回登入頁要求重新完整登入（含TOTP）。理由：變更密碼的常見情境之一是「懷疑帳號已外洩」，若保留當前session視為安全，攻擊者若竊得的正是那個當前session token則變更密碼形同無效；一律全清、強制重新完整驗證，邏輯簡單且沒有安全死角。
- 過期/已刪除session列清理：`internal/auth` 自行開一個獨立的輕量30秒ticker goroutine執行 `DELETE FROM admin_sessions WHERE expires_at < now()`，不搭載在模組4任務1（該任務職責明確限定於訂單狀態機的PENDING/CONFIRMING守門判斷，見第4節），比照第8節webhook worker「主佇列輪詢頻率10秒一次」的獨立ticker先例，保持package職責邊界乾淨。即使短暫沒清到也不影響安全性（過期session天然被 `RequireSession` 拒絕），純屬資料庫health考量，不需要模組4那種多process重疊保護等級的嚴謹度（單純DELETE，非狀態機推進，重複執行無副作用）。

### 高風險操作 Step-up 驗證（`/tron-proxy/...`）

- `/tron-proxy/...` 請求先過 `RequireSession`（一般後台登入即可存取，未過即拒絕），通過後才疊加 `RequireTOTPCode`：**每次送出都要求當下輸入TOTP驗證碼，不設新鮮度窗口**（[ADR-0016](adr/0016-高風險操作每次要求TOTP不設新鮮度窗口.md) 推翻本節原訂的15分鐘新鮮度窗口）。GET頁面（例如歸集簽名頁）每次造訪皆導向 `POST /admin/reverify-totp`（明確定義的路由，非匿名步驟）要求輸入TOTP碼（不需重新輸入密碼）才能看到頁面內容；POST/DELETE寫入端點的驗證碼欄位內建在觸發該操作的表單/請求本身裡，與其他欄位一起在同一次送出中一併驗證，驗證通過即在同一次請求內直接完成，不需額外跳轉頁面。`last_totp_verified_at` 保留在 `admin_sessions`，但只作為「最近一次成功驗證時間」的稽核記錄，不再用於gating判斷。驗證碼本身沿用登入流程同一套TOTP驗證參數（時間步窗口、`last_totp_step`重放防護、失敗計入 `totp_attempt_count`）。
- **批次寬限例外（`RequireTOTPCodeOrRecentStepUp`）**：手動歸集簽名頁一次處理一批多筆項目時，`page.js`對每個項目都各自呼叫prepare+broadcast兩個`/tron-proxy/...`端點——若比照上述「每次都要」字面套用，N筆批次要輸入2N次驗證碼，操作上不可行。這4條`/tron-proxy/...`端點改用`RequireTOTPCodeOrRecentStepUp`：批次內第一次呼叫仍要求新鮮、未重放的驗證碼，成功後`admin_sessions.last_totp_verified_at`被更新，同一session在`batchStepUpWindow`（15分鐘，供處理大批次的合理時間）內的後續呼叫免驗證碼即可通過。此例外**僅適用這4條路由**，不適用GET頁面、也不適用其餘9條`RequireTOTPCode`路由，範圍刻意narrow，不是恢復ADR-0011舊有的全站15分鐘寬限（見[ADR-0016](adr/0016-高風險操作每次要求TOTP不設新鮮度窗口.md)「批次寬限」修訂）。
- 理由：手動歸集涉及實際資金轉出，風險等級比一般後台瀏覽操作高一個量級；若後台 session cookie 遭竊但2FA裝置未同時失竊，此機制讓攻擊者完全無法在不具備即時TOTP碼的情況下完成任何一次高風險操作。
- **威脅模型邊界**：此機制設計目標是防禦「session cookie/token外洩、但2FA裝置未同時外洩」這類情境（例如cookie經網路層或日誌意外外洩，攻擊者不具備操控管理者瀏覽器本身的能力）。若攻擊面是管理者瀏覽器本身已淪陷（例如惡意瀏覽器擴充套件即時劫持管理者自己剛完成的TOTP驗證狀態），`RequireTOTPCode` 並非為此設計、無法提供有效保護；此類威脅屬於商戶自身裝置資安責任（同需求書5.9免責提醒的既有原則），不在本模組防護範圍內。
- 具體要套用在哪些子路由（例如是否含「顯示待歸集地址列表」這類唯讀頁面，或僅限「輸入助記詞/簽署/廣播」這類會動用資金的步驟），留待下一個拍板的歸集模組決定；本節先定義好可重用的通用 middleware 機制。
- **此為本節在需求書5.5既有定義之上新增的機制**：需求書未明文要求高風險操作要額外驗證，是本模組依「手動歸集涉及實際資金移動、風險量級高於一般後台瀏覽」評估後主動加上的防禦深度，已拍板採用，同步修訂第1節路由表 `/tron-proxy/...` 一列。
- **修改密碼（`POST /admin/password`）比照同等敏感度，同樣要求 `RequireTOTPCode`**：見下方「修改密碼」段落。

### 修改密碼（`POST /admin/password`）

- 依需求書5.5「後台提供『修改密碼』功能」。路由掛 `RequireSession` + `RequireTOTPCode`（每次送出都要求輸入當下驗證碼，見[ADR-0016](adr/0016-高風險操作每次要求TOTP不設新鮮度窗口.md)）。
- Request body：`current_password`、`new_password`。先用 `bcrypt.CompareHashAndPassword` 核對 `current_password` 與現存 `password_hash` 相符（即使已通過session驗證，仍要求再次輸入目前密碼，防止「session cookie被竊但攻擊者不知道密碼」的情境下被直接改密碼鎖死原owner）；`new_password` 套用同一套長度規則（≥12碼）。
- 皆通過才更新 `password_hash`、`password_changed_at=now()`，並觸發上方「密碼變更成功時」的全session清除。任一檢查失敗回傳明確錯誤，不清除任何session。

### 登入限流（暴力破解防禦）

兩層機制疊加：

1. **IP層級**（process記憶體內，不落地DB，符合單一process常駐假設，重啟後計數器歸零可接受）：同一IP在15分鐘滑動視窗內，`/admin/login`、`/admin/login/totp`、`/admin/login/totp-setup`、`/admin/reverify-totp` 四個端點失敗次數合計超過10次，該IP暫時鎖定15分鐘（回傳429）。
2. **per-session層級**：`admin_sessions.totp_attempt_count` 記錄「連續」失敗次數——**任一次TOTP驗證成功（含setup/login/reverify）即歸零重置為0**，「碼已被使用」（見上方TOTP重放防護）不視為失敗、不累加也不歸零。達5次連續失敗，該筆session立即失效並刪除——不論原本是 `pending_2fa` 或 `active`。使用者須從 `POST /admin/login` 密碼驗證重新開始（`active` session因此被強制登出，即使原本在12小時效期內）。此機制讓「已知正確密碼、只是在猜TOTP碼」的攻擊者無法無限次嘗試：每連續猜錯5次就要付出一次完整密碼驗證（bcrypt cost=12，非常規則不可批次平行化繞過）的代價，疊加IP限流，即使攻擊者輪換來源IP規避第1層，仍受第2層per-session計數約束，不因換IP而重置；「歸零於成功」的設計避免管理者在12小時效期內因多次操作間偶發手滑累積達到誤傷上限。
- 刻意**不做帳號層級永久鎖定**（例如連續失敗N次後鎖住 `admin_account` 一段時間不論哪個session）：本系統只有單一管理帳號，帳號名稱本質上不算秘密（部署時人為決定，實務上易被猜到），帳號級鎖定等於任何外部人士只要願意持續嘗試錯誤密碼，就能讓商戶自己也登不進後台，構成阻斷服務攻擊面；上述兩層（IP+per-session）已提供足夠的防禦深度而不引入這個代價。
- **已知限制**：per-session層級機制本身有一個小滋擾面——若攻擊者已取得某個 `active` session 的cookie（但未取得TOTP裝置，無法真正接管帳號），可對該session連續送出5次錯誤的 `/admin/reverify-totp` 觸發它被強制刪除，造成管理者被迫重新完整登入一次的騷擾。這不會讓攻擊者取得任何實質存取權限（session刪除後攻擊者一樣需要密碼才能再拿到新的`pending_2fa` session、仍卡在TOTP這關），純屬可用性層面的滋擾，非機密性/完整性風險，判定可接受，不額外設計對策。

### CSRF 防護

`SameSite=Strict` cookie 已阻絕絕大多數跨站請求自動帶cookie的情境（比 `Lax` 更嚴格，後台管理介面不需要「從外部連結點進來仍保持登入」這種可用性考量）；所有會產生副作用的操作一律走 POST/PUT/DELETE，不允許用GET觸發狀態變更。額外新增環境變數 `PUBLIC_ORIGIN`（例如 `https://pay.merchant.com`，部署時由商戶依自己對外網域填寫，比照 `ADMIN_USERNAME` 等其他必填部署變數）：App 啟動時若未設定此變數即fail-fast拒絕啟動；`RequireSession` middleware 檢查請求 `Origin` header（若存在）是否等於此值，不符即拒絕（403）。兩者疊加已足夠涵蓋CSRF情境，不引入額外CSRF token機制。

### 稽核整合

登入成功/失敗、TOTP驗證成功/失敗（含setup與reverify）、2FA首次設定完成、密碼變更、登出、session因per-session嘗試次數上限被強制清除，皆寫入 `audit_logs`（沿用第2節既有表，`actor='admin'`、`action_type` 區分上述事件、`detail` 含來源IP，不含密碼/TOTP碼/`pending_totp_secret`本身明碼）。

### Schema新增（第2節）

- `admin_account` 新增欄位：`last_totp_step`（bigint，nullable，TOTP重放防護）。
- 新增 `admin_sessions` 表：`id`、`token_hash`、`status`、`pending_totp_secret`（與 `admin_account.totp_secret` 同等敏感度，需同等保護規格，明碼存的理由亦相同）、`totp_attempt_count`、`created_at`、`expires_at`、`last_seen_at`、`last_totp_verified_at`。

## 10. 手動歸集模組（`internal/consolidation`）

### 頁面權限分級（回應第9節留下的待辦）

第9節將「哪些子路由要套用 `RequireTOTPCode`」留給本模組決定，拍板如下，區分「唯讀查詢」與「助記詞輸入/簽名/廣播」兩類：

| 路由 | 說明 | 驗證 |
|---|---|---|
| `GET /admin/consolidation` | 選代收主錢包、待歸集地址列表 | `RequireSession` |
| `GET /admin/consolidation/address-book` | 歸集地址簿查詢 | `RequireSession` |
| `POST/DELETE /admin/consolidation/address-book` | 歸集地址簿新增/改名/刪除 | `RequireSession` + `RequireTOTPCode` |
| `GET /admin/consolidation/sign` | 助記詞輸入頁（含TRX手續費頁面，離線bundle＋嚴格CSP） | `RequireSession` + `RequireTOTPCode` |
| `POST /tron-proxy/consolidation/prepare`、`/broadcast` | 組交易／廣播（USDT歸集） | `RequireSession` + `RequireTOTPCodeOrRecentStepUp` |
| `POST /tron-proxy/fee-topup/prepare`、`/broadcast` | 組交易／廣播（A1/A2 TRX手續費） | `RequireSession` + `RequireTOTPCodeOrRecentStepUp` |
| `POST /admin/consolidation/fee-estimate` | 手續費即時精算（唯讀：查 `energy_used`/`getEnergyFee` 計算建議 TRX） | `RequireSession` |
| `POST /admin/consolidation/trx-balance` | 查指定地址原生 TRX 餘額（唯讀：設定頁確認來源錢包餘額、扣除子地址現有 TRX） | `RequireSession` |
| `POST /tron-proxy/consolidation/transaction-info` | 查交易上鏈狀態（唯讀：簽名頁編排輪詢，等 TRX/首筆 USDT 上鏈確認） | `RequireSession` |

**理由**：待歸集列表與地址簿查詢的即時資料由後端 handler 內部直接呼叫 `internal/tronclient`（同第4節 scanner 共用的封裝）取得、渲染進回傳的 HTML，瀏覽器不需要、也不會直接呼叫外部 API——`/tron-proxy` 這層存在的目的是「給瀏覽器端 JS 一個同源端點打」，純後端渲染的唯讀頁面用不到它，也就不必疊加 step-up，降低不必要的操作摩擦。**地址簿的新增/改名/刪除則需要 step-up**：地址簿存在的目的正是讓商戶在後續歸集操作中直接「選取既有項目」以降低重複手動輸入的手誤風險（見需求書5.9），這意味著商戶對地址簿項目的信任度天生高於臨時手動輸入的地址；若攻擊者僅取得 session cookie（未取得2FA裝置，即第9節「威脅模型邊界」界定的情境）就能寫入一筆貼著看似合理名稱的惡意地址，商戶之後選取時，步驟4的分段顯示＋全字串核對防呆機制原本設計用來攔「手誤/貼錯剪貼簿」這類無意錯誤，並不必然能攔住「商戶因信任地址簿而降低核對戒心」這種情境——兩者是不同的威脅來源，不能互相替代，因此地址簿寫入比照助記詞/簽名頁面同等級疊加 step-up，僅查詢維持 `RequireSession`。真正涉及助記詞輸入、私鑰衍生、簽名、廣播的頁面與其對應的 `/tron-proxy/...` 端點，同樣是本系統風險最高的操作，全部疊加 step-up。本次新增的三個唯讀查詢端點（`fee-estimate` 精算、`trx-balance` 餘額、`transaction-info` 交易狀態）不轉出資金、不改任何商戶可見的財務數字，僅回計算/查詢結果，故只掛 `RequireSession`；prepare/broadcast 維持 step-up，其批次寬限窗於手動歸集編排流程延長至 30 分鐘（僅限此流程，見 [ADR-0016](adr/0016-高風險操作每次要求TOTP不設新鮮度窗口.md)/[0017](adr/0017-手動歸集流程重構自動編排與精省手續費.md)）。

### 待歸集地址列表

依需求書5.9流程步驟1、2：

1. 選擇代收主錢包（若系統僅有一個使用中/曾用過的代收主錢包可省略此步驟）；使用中或已停用皆可選。
2. 查詢範圍：`orders WHERE master_wallet_id=? AND consolidation_status='never'`（第2節既有欄位，語意「從未歸集」）。**不限制訂單狀態**——需求書本身未要求歸集只能對終態訂單操作（見進度.md模組4「待模組5/後續處理的缺口」第3點），拍板：允許對任何狀態（含PENDING/CONFIRMING）的地址發起歸集。理由：掃描邏輯只依 `address` 比對、不看訂單狀態（見第4節），提前歸集不影響後續入帳的累加金額判斷；商戶對自己名下地址的資金有完全裁量權，系統不代為限制。
3. 對查詢範圍內的每個地址，即時呼叫 `internal/tronclient` 查詢 TronGrid 的 USDT 餘額（`GET /v1/accounts/{address}/` 解析 TRC20 餘額欄位），與 `orders.target_amount` 並列顯示；`only_confirmed` 概念在此不適用（顯示的是「目前鏈上實際餘額」這個即時值，不是入帳累加金額）。**只顯示餘額 > 0 的地址**（需求書5.9步驟2「列出有餘額的衍生地址」）。
4. 若訂單狀態為 COMPLETED 但查得餘額 > `target_amount`，標示「餘額超出訂單原定金額」提醒（依需求書5.9步驟2）。
5. **此為有界查詢，非第4節已否決的「逐一輪詢所有地址」**：範圍限定在單一代收主錢包底下 `consolidation_status='never'` 的地址，天然隨著商戶持續歸集而收斂，不會像「監控所有歷史地址」那樣隨訂單量無上限累積（呼應需求書5.9步驟2下方「已知風險與限制」段落的設計取捨，也是為何不做已歸集地址的持續監控）。
6. **`consolidation_status` 是永久性旗標**：一旦某地址對應的 `consolidation_items` 廣播成功，`orders.consolidation_status` 立即改為 `'consolidated'` 並永久排除在此列表之外，即使之後該地址又收到新入帳也不會重新出現（逐字對應需求書5.9步驟2下方的已知限制段落，此為需求書已定案的行為，非本節新增）。

### 目的地地址與歸集地址簿（`internal/consolidation`，`/admin/consolidation/address-book`）

- CRUD：新增（格式驗證用 `tronWeb.isAddress()`，見[階段03技術細節暫存.md](階段03技術細節暫存.md)；地址已存在則拒絕新增並提示）、編輯（僅限改名，地址值本身不可修改）、刪除。上限30筆，達上限後新增（含下方「歸集成功自動存檔」）一律跳過但不影響歸集操作本身，皆依需求書5.9「歸集地址簿」段落逐字落實。
- 歸集成功後，若該次目的地地址是**手動輸入的新地址**（非從地址簿選取）且該地址不在簿中，自動存入，預設名稱格式 `{建立日期} 新增（...{地址末4碼}）`；已存在則不重複新增、保留原名稱。
- 地址簿項目刪除/改名不影響歷史稽核日誌（`audit_logs.detail` 已於歸集當下記錄地址原文與名稱快照）。
- **前端 Address Poisoning 防呆呈現**（沿用[階段03技術細節暫存.md](階段03技術細節暫存.md)已調查的技術背景，落實需求書5.9「地址正確性防呆機制」）：無論從地址簿選取或手動輸入，確認頁一律以每4碼加空格的分段格式完整顯示目的地地址全字串，要求商戶核對整串而非僅頭尾；「小額測試」是純 UI 文案引導（見需求書），系統不強制分階段簽名/廣播。

### TRX 手續費與歸集的整合流程（A1/A2）

USDT 歸集是 `TriggerSmartContract`，執行需消耗能量；子地址預設無 TRX。需求書5.9（[v0.38](開發流程框架-01-需求書變更紀錄.md#v0-38)）將「補 TRX 手續費（A. 支付 TRX）」與「USDT 歸集」整合為單一操作流程，由前端在簽名頁自動編排先後順序（本模組據此推翻先前「兩組獨立批次、系統不做順序把關、不預估能量成本」的簡化取捨，完整決策與被否決方案見 [ADR-0017](adr/0017-手動歸集流程重構自動編排與精省手續費.md)）：

- **A1/A2 採完全相同的技術機制（已拍板）**：需求書5.9原文「A1由代收主錢包簽名」暗示要動用代收主錢包（xpub）底下某個具體地址，但xpub本身無「餘額」概念、不能直接收TRX，必須先指定一個具體地址才有私鑰可簽名——而 index 0 是需求書5.1明定「系統不賦予任何用途、後台也不特別顯示」的保留地址，若把它固定挪用為A1的TRX來源，等於系統賦予其具體用途，與需求書5.1字面直接衝突。**拍板不動用 index 0，A1與A2一律比照同一套「商戶自行指定地址」機制**：商戶指定一個地址（可以是代收主錢包HD樹以外的任意地址，也可以是商戶自己另外持有的地址），輸入其助記詞或直接輸入私鑰，由該地址簽名批次轉出TRX——**A1與A2在本架構下技術上完全一致，差異僅剩 `fee_source` 稽核欄位這個商戶自選的分類標記**（A1＝商戶自認與代收主錢包相關的資金來源；A2＝商戶自認完全獨立的錢包），系統操作流程、簽名/廣播邏輯、頁面元件不做任何區分，只在稽核記錄上依商戶選擇分別記錄。
- **地址與金鑰輸入**：不受本系統HD樹管轄，前端支援輸入助記詞（依相同衍生路徑`m/44'/195'/0'/0/0`衍生單一地址，供商戶用既有HD錢包但不想動用代收主錢包助記詞的情境）或直接輸入私鑰 hex（單一地址場景不需要HD衍生），比照代收主錢包「方式1」的風險等級套用同一嚴格CSP頁面。**私鑰輸入的格式防呆比照代收主錢包「方式1」助記詞格式驗證的同等精神**：前端先檢查是否為64碼合法十六進位字元、且數值落在 secp256k1 曲線合法私鑰範圍內，不合法立即拒絕並顯示明確錯誤、不繼續衍生對應地址；商戶可修改後重新送出，次數不限——與需求書5.9代收主錢包「驗證不過則拒絕並顯示明確錯誤，不繼續衍生」的防呆邏輯對等，僅驗證規則因輸入型態（助記詞 vs 私鑰hex）不同而異。簽名頁同時輸入代收主錢包助記詞與 TRX 來源錢包助記詞/私鑰**兩把金鑰**；**簽完 TRX 補款批次後即刻將 TRX 來源金鑰從記憶體清除**，把兩把金鑰共存窗口壓到最短（代收主錢包金鑰因 USDT 交易有時效、須逐筆臨時簽，留到流程結束，見 [ADR-0017](adr/0017-手動歸集流程重構自動編排與精省手續費.md)）。
- **系統自動編排 TRX 補款與 USDT 歸集的順序**：前端在簽名頁依序執行——(1) 對各勾選子地址補足 TRX（首筆較多、其餘較少，見下方「補充金額」），(2) 等補入的 TRX 上鏈（查 `gettransactioninfobyid` 見 `blockNumber`），(3) 先廣播**首筆** USDT 歸集、等其 `receipt.result==="SUCCESS"`（歸集目的地因此完成首次收款，後續筆能量較低），(4) 再廣播其餘 USDT 歸集。順序由前端 pipeline 的 `await` 保證，**後端仍逐筆獨立、不加資料庫層級的前後置互鎖**（沿用下方既有廣播安全模型，不新增後端狀態機）。
- **失敗停下 ＋ 可重入**：任一步失敗即停止後續、清楚回報現況（哪些完成、哪些未動、目的地是否已啟用）；商戶重新發起時，系統依鏈上現況（子地址 TRX/USDT 餘額、目的地是否已收過該 USDT、`orders.consolidation_status`）即時重算並只執行尚未完成的部分——不新增流程表持久化編排狀態（最小持久化，見下方 Schema 段落）。
- **補充金額——即時精算**：設定頁提供「手續費試算」，後端對「子地址→歸集目的地」的 USDT `transfer()` 呼叫 `triggerconstantcontract` 取 `energy_used`、呼叫 `getchainparameters` 取 `getEnergyFee`，相乘得所需 TRX。能量不受轉帳金額影響，唯一變因是目的地是否首次收到該 USDT（首次含 storage 初始化的較高能量），故分「首筆（較高）」與「其餘筆（較低）」兩個值、依勾選筆數加總即時顯示；有填目的地用真實模擬值，未填用保守（首次）值。**緩衝 +10%、向上取整到 0.1 TRX**，商戶可於簽名頁覆寫。落地前以真實 Shasta 驗證 `energy_used`/`energy_penalty`/`getEnergyFee` 回應格式。
- **轉入前扣除子地址現有 TRX**：呼叫 `getaccount` 查子地址現有可用 TRX，實補 = max(0, 所需 − 現有)，≤0 則跳過該筆補款。設定頁另提供「查 TRX 來源地址餘額」按鈕，供商戶確認來源錢包 TRX 是否足夠。
- 簽名/廣播流程與下方「組交易與廣播」共用同一套機制，差別在 TronGrid 端點為 `createtransaction`（`TransferContract`）而非 `triggersmartcontract`，且廣播結果判斷條件不同（見下方「廣播結果判斷」）。
- Schema：獨立於 USDT 歸集的 `consolidation_batches`/`consolidation_items`，新增 `fee_topup_batches`（`id`、`master_wallet_id`、`fee_source` enum(A1/A2)、`fee_source_address`、`created_at`）／`fee_topup_items`（`id`、`batch_id`、`order_id`（轉入的目標子地址）、`amount`、`tx_hash`、`broadcast_status`、`error_detail`、`created_at`、`updated_at`）——與 USDT 歸集分開建表，不共用一張表疊加大量 nullable 欄位，理由同第8節 `webhook_deliveries`/`webhook_delivery_attempts` 分表的判斷：兩種操作的欄位語意（單一目的地 vs 單一來源、觸發時機）不同，分開較乾淨。

### 助記詞輸入與私鑰衍生（`/admin/consolidation/sign`）

- 套用需求書5.9「輸入助記詞頁面的強化要求」：不引入第三方腳本/CDN/分析工具、簽名函式庫離線打包（`web/static/js`，見第1節）、嚴格CSP（`script-src 'self'; connect-src 'self'`，無 inline `<script>`，同[驗證結論-05](驗證結論-05-離線打包與嚴格CSP相容性.md)/[驗證結論-08](驗證結論-08-嚴格CSP下組交易簽名廣播.md)已驗證的規格）。
- 函式庫組合沿用[驗證結論-06](驗證結論-06-瀏覽器端TRC20轉帳組建簽名廣播.md)/[驗證結論-08](驗證結論-08-嚴格CSP下組交易簽名廣播.md)已驗證的 `bip39`+`hdkey`+`@noble/curves`+`@noble/hashes`+`bs58check`，`esbuild` 打包成 `polyfill.bundle.js`+`bundle.js` 兩個依序載入的獨立 script（沿用既有踩雷紀錄，`window.process` 賦值時機問題）。
- 商戶輸入助記詞後，前端本地衍生 xpub，與該代收主錢包已存的 `master_wallets.xpub`（公鑰，非機密，可直接嵌入頁面資料）逐字比對，不符則拒絕並提示重新輸入（依需求書5.9步驟5、5.1「與手動歸集的關聯」）；比對邏輯完全在前端本地完成，不需要打後端驗證端點——此為需求書5.9步驟5「系統」驗證的落地方式：離線打包隨系統部署的前端JS本身即屬系統交付程式碼（非商戶自行編寫），與後端驗證同屬「系統」範疇，僅執行位置不同。**此步驟並非唯一防線**：若此比對遭繞過（例如惡意瀏覽器擴充套件竄改頁面邏輯，屬第9節「威脅模型邊界」同類商戶裝置資安範疇，非本系統程式碼可防範），用錯誤代收主錢包助記詞衍生出的私鑰並不對應該筆訂單地址的實際私鑰，下方「組交易與廣播」步驟4「簽名後自我核對」會因反推出的地址與預期付款方地址不符而攔截中止、不送出廣播；即使該步驟也被繞過送出上鏈，Tron 節點驗證交易簽名時仍會因簽名與該帳戶實際持有的公鑰不匹配而拒絕該筆交易（帳戶模型下，動用資產需帳戶自身私鑰簽署，錯誤私鑰簽出的交易不具備該帳戶的支配權限，不會造成資金移轉錯誤或遺失）。因此本步驟的資金安全邊界並非完全依賴前端比對本身，而有簽名核對與鏈上驗證兩層兜底。
- 相符後，對每個勾選地址依 `derivation_index` 走完整路徑 `m/44'/195'/0'/0/{index}`（含硬化 account 層，需從助記詞→seed 重新衍生，非從 xpub 往下衍生——xpub 無法做硬化衍生，此為 BIP32 性質）還原私鑰，供下方簽名使用；私鑰全程只存在於該分頁記憶體，不落地、不上傳。

### 組交易與廣播（同源代理，`/tron-proxy/consolidation/...`、`/tron-proxy/fee-topup/...`）

依第1節既有原則（[驗證結論-08](驗證結論-08-嚴格CSP下組交易簽名廣播.md)已驗證），組交易與廣播兩個對外呼叫 TronGrid 的動作皆由後端代為執行：

1. **prepare**：前端對每個勾選地址呼叫 `POST /tron-proxy/consolidation/prepare`（USDT歸集）或 `/tron-proxy/fee-topup/prepare`（TRX手續費）。後端**當下重新查詢一次即時鏈上餘額**（USDT歸集場景下，轉出金額＝當下實際餘額，全額轉出以清空地址；不是用列表頁面幾秒/幾分鐘前顯示的舊值，避免用戶端資料過時造成金額誤差），呼叫 TronGrid `triggersmartcontract`／`createtransaction` 取得 unsigned `raw_data_hex` 與 `txID`，回傳給前端。
2. **本地重算 txID 核對**：前端用 `@noble/hashes` 的 `sha256` 對 `raw_data_hex` 重新計算，比對是否等於後端回傳的 `txID`，不一致則中止（[驗證結論-06](驗證結論-06-瀏覽器端TRC20轉帳組建簽名廣播.md)/[08](驗證結論-08-嚴格CSP下組交易簽名廣播.md)驗證過的必要步驟，非可選）。
3. **簽名**：對 `txID` 做 ECDSA 簽名（`prehash:false`——`txID` 本身已是 `SHA256(raw_data)`，不可再雜湊一次；`{format:'recovered'}` 取得 `recovery(1 byte)||r(32 bytes)||s(32 bytes)`，需手動重排成 tronweb 慣用的 `r||s||v(v=recovery+27)` 佈局——[驗證結論-06](驗證結論-06-瀏覽器端TRC20轉帳組建簽名廣播.md)記錄過的兩個地雷，正式開發沿用同一套已驗證邏輯，不重踩）。
4. **簽名後自我核對（必做，非可選防呆）**：本地用簽名+txID反推公鑰、算出地址，確認等於預期的付款方地址，不符則中止不送出（[驗證結論-06](驗證結論-06-瀏覽器端TRC20轉帳組建簽名廣播.md)/[08](驗證結論-08-嚴格CSP下組交易簽名廣播.md)證明成本低、有效的防呆層）。
5. **broadcast**：前端把簽名結果 POST 給 `/tron-proxy/consolidation/broadcast`／`/tron-proxy/fee-topup/broadcast`，後端呼叫 TronGrid `broadcasttransaction`，寫入對應的 `consolidation_items`／`fee_topup_items`（見下方廣播結果判斷）。
6. **等上鏈確認（整合流程的編排等待）**：TRX 補款批次、以及首筆 USDT 歸集廣播後，前端呼叫 `POST /tron-proxy/consolidation/transaction-info`（唯讀，後端包 `gettransactioninfobyid`）輪詢——TRX 看 `blockNumber`、USDT 看 `receipt.result==="SUCCESS"`——確認上鏈成功後才續作下一步（見上方「自動編排」）。這是編排流程中的**主動等待**，與下方 lazy reconcile（頁面載入時**被動**收斂殘留 `broadcasting` 項目）互補、不衝突。

### 廣播結果判斷與部分失敗（呼應需求書5.9步驟6「逐筆獨立追蹤」）

- `broadcast_status` 狀態機：`pending`（已 prepare，尚未送出簽名結果）→ `broadcasting`（後端已呼叫 TronGrid，等待明確結果）→ `success`／`failed`。
- **`fetch`/HTTP層失敗不等於交易未發生**（[驗證結論-06](驗證結論-06-瀏覽器端TRC20轉帳組建簽名廣播.md)觀察4的真實踩雷：一次因誤判導致同一筆交易被重複廣播兩次）：後端呼叫 `broadcasttransaction` 若網路層逾時/連線失敗，**不可直接標記 `failed`**，維持 `broadcasting` 狀態；`GET /admin/consolidation`（待歸集列表，不限特定批次）每次載入時，後端一併查詢**該代收主錢包底下所有 `broadcast_status='broadcasting'`** 的 `consolidation_items`/`fee_topup_items`，用已持有的 `tx_hash`（簽名階段已算出，broadcast API本身呼叫與否不影響其存在）主動查詢 `gettransactioninfobyid` 核對鏈上是否已存在該筆交易，才決定最終 `success`／`failed`——刻意不侷限於「商戶重新打開當初那個批次的結果頁」，因為商戶更可能只記得回來看歸集列表、未必會特地找回某個舊批次頁面（不需要常駐背景ticker，手動歸集是低頻人工操作，採「開啟列表頁時觸發一次核對」的 lazy reconcile 即可，不比照第8節webhook worker那種永久輪詢）。**殘留已知限制**：若商戶此後永久不再打開 `/admin/consolidation`（例如整個代收主錢包已停用、不再操作），該筆 `broadcasting` 狀態會永久停滯不被回收；但這不構成資金風險——該筆交易若實際已上鏈成功，資金已在目的地地址，僅系統內部的 `broadcast_status` 記錄未同步更新，屬於記錄層面的已知限制，不影響資金安全，故不列入待確認問題。**尚未選定代收主錢包時的查詢範圍**：若商戶名下有多個代收主錢包、進入 `/admin/consolidation` 當下尚未點選特定一個（見下方「待歸集地址列表」步驟1），此時頁面本身還不到「待歸集列表」狀態、無單一 `master_wallet_id` 可供 lazy reconcile 查詢範圍收斂；此情況下查詢範圍改為**商戶名下所有代收主錢包**（單一租戶架構下代收主錢包數量有限，即使全掃描其 `broadcasting` 項目，成本仍遠低於常駐輪詢，不違反本機制刻意不做背景ticker的設計初衷）；商戶選定特定代收主錢包、進入該錢包的待歸集列表後，查詢範圍才依上述描述收斂為該錢包底下。
- **廣播結果判斷條件依合約類型分流**（[驗證結論-06附加測試](驗證結論-06-瀏覽器端TRC20轉帳組建簽名廣播.md)記錄的差異）：USDT歸集（`TriggerSmartContract`）檢查 `receipt.result === "SUCCESS"`；TRX手續費（`TransferContract`）該欄位不存在，改檢查 `blockNumber` 是否存在且無錯誤欄位。
- `success` 時，同一交易內把對應 `orders.consolidation_status` 更新為 `'consolidated'`（僅USDT歸集項目觸發此更新；TRX手續費成功不影響 `consolidation_status`，那只是前置步驟）。**與 prepare 步驟的已知交互風險**：prepare 查得的即時餘額本身受 TronGrid 索引延遲影響，可能導致極少數情況下全額轉出後仍有殘留差額、且該地址已永久退出監控——已評估拍板接受，不加額外機制，完整說明見下方「已知限制」。
- **部分失敗的重試，直接沿用一般歸集流程，不設計獨立的「重試」端點**：失敗的地址其 `consolidation_status` 維持 `'never'`，且下次載入待歸集列表時即時查詢的鏈上餘額仍會反映真實現況（不論是「真的失敗、餘額未變」或「其實已成功但先前誤判為failed、餘額已歸零」），商戶重新勾選該地址走一次正常流程即可——**餘額已歸零的地址因為列表只顯示「餘額>0」而自然不會再出現、不會被誤導重複廣播**，這是本設計不需要額外設計「防止重複廣播」鎖定機制的核心原因：金額永遠取「當下即時鏈上餘額」而非快取值，天然規避了重複轉出風險。
- **已知的良性競態**：允許同帳號多組並行 session（第9節既有決定），若兩個分頁同時對同一地址發起歸集，先上鏈的一筆成功、後上鏈的一筆會因餘額不足在合約執行時 REVERT（[驗證結論-08](驗證結論-08-嚴格CSP下組交易簽名廣播.md)過程中真實出現過 `SafeMath: subtraction overflow` 這種失敗），不構成資金風險或重複扣款，只是浪費一筆已消耗的手續費，判定可接受，不特別設計併發鎖定機制。
- **查詢某地址目前是否有正在處理中的歸集**：`order_id` 與地址雖是1:1綁定，但 `consolidation_items`/`fee_topup_items` 允許同一 `order_id` 隨時間累積多筆列（每次歸集嘗試皆為新增一筆，從不改寫既有列，例如失敗後重試會產生第二筆）。查詢某地址「目前」狀態，一律取**該 `order_id` 在對應表中 `created_at` 最新的一筆**之 `broadcast_status`（`pending`/`broadcasting` 視為處理中，`success` 已完成，`failed` 視為未處理、可重新發起），不需要、也不應該掃描該地址歷史所有列做聚合判斷——歷史列僅供稽核追溯（見上方稽核整合段落）。上方 lazy reconcile（篩選 `broadcast_status='broadcasting'`）與待歸集列表（篩選 `orders.consolidation_status`）兩處查詢已隱含遵循此原則，本段落補充明文化，避免後續維護者誤以為需要額外設計跨列聚合邏輯。

### 本機加密儲存（IndexedDB，`web/static/js`）

沿用[驗證結論-07](驗證結論-07-本機加密儲存IndexedDB.md)已驗證的技術棧，不引入任何第三方加密函式庫：

- KDF：`PBKDF2`，`SHA-256`，鹽16 bytes（`crypto.getRandomValues`）；**迭代次數正式拍板 600,000**（依 OWASP Password Storage Cheat Sheet 對 PBKDF2-HMAC-SHA256 的建議下限，驗證用的300,000僅為測試參數，見驗證結論07備註）。
- 加密：`AES-GCM`，256 bits，IV 12 bytes（每次加密重新產生）；認證標籤驗證失敗（密碼錯誤）直接 `OperationError`，不會靜默解出錯誤內容（已驗證行為）。
- **索引鍵採 `master_wallet_id`**（系統內部穩定主鍵，非 xpub 字串本身，但語意等同需求書「以代收主錢包識別碼／xpub當索引鍵」——不同代收主錢包各自獨立一筆 IndexedDB 記錄，互不覆蓋）；歸集頁面需明確顯示「目前這台裝置上已儲存的是哪一個代收主錢包的助記詞」（依需求書5.9，取代收主錢包建立日期＋xpub末幾碼供辨識）。
- 加密密碼為商戶自訂、與後台登入密碼無關的獨立一組密碼，加解密全程在前端完成，後端不涉及、不接觸。
- 沿用同一頁面的嚴格CSP：`crypto.subtle`／`indexedDB` 為瀏覽器原生API，已驗證不受 `script-src 'self'` 影響（見驗證結論07）。

### 稽核整合

依需求書5.9步驟7，每次歸集操作（含選取的代收主錢包、地址、目的地地址、金額、結果）與每次TRX手續費操作，皆寫入 `audit_logs`（`actor='admin'`、`action_type` 區分 `CONSOLIDATION`/`FEE_TOPUP`、`detail` 含批次/明細，不含助記詞/私鑰本身）。

### 已知限制（承接需求書5.9與驗證結論06/08，非本模組bug）

- 已歸集地址（`consolidation_status='consolidated'`）不會被重新排入「待歸集地址列表」（永久排除，`ListPendingConsolidation` 查詢範圍不變），也不會被系統自動轉出或自動改判訂單狀態。但之後若該地址又收到新入帳，系統會比照模組11「COMPLETED訂單晚到confirmed金額」的既有機制（`logLateFinalityConfirmation`）標示為異常、寫入稽核紀錄供商戶查證——[ADR-0015](adr/0015-已歸集地址晚到入帳可見度.md) 推翻了原本「系統不主動偵測/標示/通知」的需求書舊決策。
- 手續費補充金額改由設定頁**即時精算**並**扣除子地址現有 TRX**（見上方「TRX 手續費與歸集的整合流程」），取代先前「廣播前不預先估算、直接嘗試廣播、失敗才記錄」的簡化設計（[ADR-0017](adr/0017-手動歸集流程重構自動編排與精省手續費.md)）。精算為輔助、商戶可覆寫，且鏈上實際能量/單價可能與精算時點有落差，故廣播失敗仍會記錄於 `error_detail` 供查證。
- TronGrid帳戶餘額聚合欄位有索引延遲（[驗證結論-06](驗證結論-06-瀏覽器端TRC20轉帳組建簽名廣播.md)觀察約15秒），列表頁面/廣播完成後的即時查詢可能短暫顯示未更新的餘額，屬已知延遲特性。
- **上述索引延遲與永久鎖定疊加的殘留金額風險（已評估拍板接受）**：若入帳剛好落在 prepare 查詢前的15秒索引延遲窗口內，prepare 會以偏低的舊餘額全額轉出，廣播成功後 `consolidation_status` 立即永久轉為 `'consolidated'`。殘留差額之後若又收到入帳，會透過上方「已歸集地址晚到入帳」機制標示為異常供商戶查證（[ADR-0015](adr/0015-已歸集地址晚到入帳可見度.md)），但系統仍不會自動處置。需同時滿足「入帳卡在延遲窗口內」與「商戶剛好此時歸集」兩個低機率巧合才觸發，殘留金額仍安全存在鏈上可自行取回，評估後拍板不加二次覆核/緩衝等待機制，維持設計簡單性。

### Schema新增/修正（第2節）

- `orders.consolidation_status`：第2節原表已列為欄位，本節定案語意與時機——`'never'`/`'consolidated'` 二值，僅於對應 `consolidation_items` 廣播 `success` 時轉為 `'consolidated'`，永久不回退。
- `consolidation_batches`：`id`、`master_wallet_id`、`destination_address`、`created_at`（不含 `fee_source`——與TRX手續費分表後不再需要此欄位；第2節表格清單已同步更新，不再是本節單獨的修正說明）。
- `consolidation_items`：`id`、`batch_id`、`order_id`、`amount`、`tx_hash`、`broadcast_status`（pending/broadcasting/success/failed）、`error_detail`（text）、`created_at`、`updated_at`。
- 新增 `fee_topup_batches`：`id`、`master_wallet_id`、`fee_source`（A1/A2，商戶自選分類標記，見上方「TRX手續費」段落）、`fee_source_address`、`created_at`。
- 新增 `fee_topup_items`：`id`、`batch_id`、`order_id`、`amount`、`tx_hash`、`broadcast_status`、`error_detail`、`created_at`、`updated_at`。
- **最小持久化、靠鏈上現況推導（[ADR-0017](adr/0017-手動歸集流程重構自動編排與精省手續費.md)）**：整合流程不新增「流程表」持久記錄編排狀態；「還要不要補 TRX、哪筆當首筆、哪筆已歸集」一律由鏈上現況即時推導（子地址 TRX/USDT 餘額、目的地是否已收過該 USDT、`orders.consolidation_status` 永久旗標），確保重入時 DB 不與鏈上不一致。既有 `fee_topup_batches/items`、`consolidation_batches/items` 結構不需為此新增流程關聯或首筆欄位。

本模組整合前面所有模組的管理介面，對應需求書 5.5。除本節新定義的路由外，第9節（帳號安全）`RequireSession`／`RequireTOTPCode` middleware、第10節手動歸集頁面（`/admin/consolidation/...`）、第8節 Webhook 投遞機制皆直接沿用。

### 代收主錢包導引 Gate（`RequireMasterWallet`）

依需求書5.5：系統尚無任何 `status='active'` 的 `master_wallets` 記錄時，`RequireMasterWallet` middleware 攔截「建立訂單」（本節手動建單 `POST /admin/orders`、第7節API `POST /api/v1/orders`，見下方「同步修正第7節」）與「手動歸集」中實際涉及特定代收主錢包的路由（第10節 `GET /admin/consolidation`、`GET /admin/consolidation/sign`、`POST /tron-proxy/consolidation/...`、`POST /tron-proxy/fee-topup/...`）——回應明確錯誤（後台導向代收主錢包設定頁；API回傳 `503`、`error_code: NO_ACTIVE_MASTER_WALLET`）。**歸集地址簿（`/admin/consolidation/address-book`）不受此限制**：地址簿是與特定代收主錢包無關的通用清單（商戶可在完成代收主錢包設定前，先把已知的歸集目的地地址存起來），鎖住它沒有實質防護效果，只增加不必要的操作摩擦。除上述被攔截的路由外，其餘後台頁面（含本節查詢類頁面）不受此限制，商戶可先瀏覽儀表板/設定頁再回頭完成代收主錢包設定。具體引導畫面留待介面設計階段（需求書5.5原文已註明）。

### 儀表板

依需求書5.5「總收款金額、待處理訂單數、異常訂單數等統計」，三項統計定義：

- **總收款金額**：全站所有 COMPLETED／OVERPAID 訂單的 `incoming_transactions.confirmed=true` 累加金額總和（全時間範圍，不做期間篩選——商戶若需要期間數據，用下方CSV/Excel匯出篩選查看，儀表板不重複做圖表化篩選，避免過度設計）。
- **待處理訂單數**：PENDING + CONFIRMING 狀態訂單數（尚在自動監控流程中，非異常，僅表示「還在走」）。
- **異常訂單數**：OVERPAID + CONFIRMATION_STALLED + **EXPIRED 且已入帳金額 > 0**（即需求書5.2「到期時累計金額仍未達標，不論是完全沒收到任何入帳，還是收到部分金額」兩種情況中的後者），三者皆需商戶人工判斷處理。**判準是「是否需要商戶查證/處理」，不是「是否為終態」**：完全沒收到任何款項的EXPIRED訂單（多數情況，付款人單純未付款）是正常結束路徑、不需商戶採取任何行動，不計入異常；但已收到部分款項卻未達標的EXPIRED訂單，資金已卡在該地址，與OVERPAID/STALLED同樣需要商戶查證處理，若整類排除會讓商戶從儀表板完全看不到這類需關注的訂單。
- 同一頁面沿用第4節已定案的「上次成功同步區塊」可見度區塊（不重複設計，見第4節「儀表板可見度」）與第8節被動可見度摘要（失敗中/待重試、待設定筆數，見第8節）。

### 訂單列表與明細（`/admin/orders`）

- **列表篩選**：狀態（可複選）、`merchant_order_no`（模糊查詢）、`address`（精確比對，供客訴查證用）、代收主錢包、建立時間範圍；預設依 `created_at` 降冪排序，offset+limit 分頁（訂單量體不需要 cursor 分頁複雜度）。
- **明細頁**：訂單全部欄位、`order_state_transitions` 完整狀態變更歷史（含手動改判前曾經歷過的狀態，依需求書5.2/5.5）、`incoming_transactions` 列表、對應 `webhook_deliveries`／`webhook_delivery_attempts`（該訂單的通知記錄，供客服對照）、`consolidation_status` 與若已歸集則附對應 `consolidation_items` 記錄、若該地址曾被儲值過TRX手續費則附對應 `fee_topup_items` 記錄（`order_id` 語意為「轉入的目標子地址」，見第10節）。

### 手動建單（`POST /admin/orders`）

依需求書5.2「後台亦提供手動建單功能，方便測試與人工收款情境」：

- 與第7節建單API共用同一內部訂單建立函式（`internal/order` 提供的 create 服務層），本節僅是另一個呼叫端，不重複實作HD衍生/參數快照邏輯。
- Request 欄位：`merchant_order_no`（選填）、`target_amount`（後台UI用**小數USDT**輸入，貼近人類操作習慣，如 `100.50`；送到 create 服務層前換算成最小單位整數，**超過6位小數一律拒絕送出並提示錯誤，不做四捨五入或截斷**，避免UI顯示金額與資料庫實際存入值有無法預期的落差；換算後仍全程用 `int64` 運算，不影響第4節「金額精度」既有原則——此為後台呈現層的單位轉換，非底層運算方式改變）。
- **瀏覽器表單路徑的冪等保護**：`merchant_order_no` 留空時，自動編號（格式 `MANUAL-{yyyyMMddHHmmss}-{4碼隨機}`）須於**表單頁面首次載入當下**產生並以隱藏欄位隨表單送出，而非於送出當下才產生——若在送出當下才產生，每次送出（含網路重試、雙擊）都會拿到不同編號，等於每次都被冪等機制視為「編號不存在」而各自建立新訂單、各自消耗一個HD衍生地址索引。改為表單載入時產生並固定於隱藏欄位後，同一次表單的重複送出會帶著相同編號，可正常沿用「編號已存在→比對金額→相同則回傳原訂單」的既有冪等規則擋下。
- **非瀏覽器呼叫（例如直接對此端點發request的腳本）的行為，刻意不強制冪等**：上述隱藏欄位機制僅是後台頁面本身的前端行為，本端點的後端邏輯**不強制** `merchant_order_no` 必填——留空的請求一律視為建立新訂單（不做冪等比對，每次呼叫皆各自新建）。此為刻意的簡化取捨：本端點定位是需求書5.2「方便測試與人工收款情境」，非第7節那種需要嚴格防重試冪等保證的對外整合API；呼叫方若需要冪等保護，只需自行帶入固定的 `merchant_order_no` 即可套用下方共用的冪等判斷邏輯，與瀏覽器表單走的是同一段程式碼、同一組規則，差別只在「有沒有提供編號」。
- 冪等性判斷邏輯與第7節API共用同一段程式碼：若請求提供了 `merchant_order_no`（不論來自手動指定、腳本呼叫、或表單隱藏欄位）且與既有訂單衝突，比照API規則處理（金額相同回傳原訂單、不同拒絕並提示衝突）。

### 手動重新檢查此地址（`POST /admin/orders/{id}/reverify`）

依需求書5.2「手動重新檢查此地址」，任何狀態訂單皆可觸發（含PENDING/CONFIRMING，雖然這兩個狀態已被第4節任務2/3持續掃描、reverify對它們而言多半是重複查詢，但為求邏輯一致不特別排除）：

- **沿用第4節任務2/3完全相同的端點與資料結構**（`GET /v1/contracts/{USDT合約}/events?event_name=Transfer`），不改用其他帳戶層級端點——理由：其他端點（如 `/v1/accounts/{address}/transactions/trc20`）(a) 回傳該地址收到的**所有** TRC20 代幣轉帳，非僅 USDT，若不過濾合約位址，惡意/垃圾代幣轉入該公開收款地址時會被誤計入累加金額；(b) 其回應結構是否含有可對應到 `log_index` 的欄位、與任務2/3使用的合約事件端點是否語意一致，未經任何驗證項目確認，貿然假設兩者可共用同一去重鍵有風險。沿用同一端點可讓 reverify 天然只查USDT合約事件、且與任務2/3寫入同一張表時語意/欄位完全一致。
- **查詢範圍**：`min_block_timestamp` 固定為該訂單 `created_at`（地址是建立訂單當下才衍生，更早不可能有入帳）；**`max_block_timestamp` 一律用 `now()`，不論訂單是否已進入終態**——「手動重新檢查此地址」存在的核心理由正是需求書5.2/5.9反覆強調的「地址永久有效，隨時可能收到延遲到帳的款項」（例如商戶收到STALLED通知後付款人才補款、或EXPIRED之後才延遲到帳），若上界鎖在終態轉換當下，等於查不到這個功能原本要服務的最典型情境，改用 `now()` 才站得住腳。此區間下界仍受訂單 `created_at` 天然限制，非任意久遠的全量掃描。
- 對此區間內的事件結果在應用層過濾 `to == 該訂單地址`（與任務2/3對整個合約事件流做的過濾邏輯相同，只是額外加了時間窗與單一地址過濾）。**沿用任務2的分頁規則**：此查詢仍是對USDT合約全域事件流查詢（`to`過濾在應用層做，非伺服器端過濾），時間窗短不代表事件筆數少（鏈上當下整體轉帳量大時仍可能單頁超過200筆），單輪結果達200筆上限時同樣用 `meta.fingerprint` 在同一輪內翻頁，直到查完整個時間窗為止，不可只取第一頁就視為查詢完成。
- 查得結果依第4節既有 `(tx_hash, log_index)` 唯一鍵合併寫入 `incoming_transactions`（與任務2/3寫入同一張表、同一去重規則、同一資料結構，無相容性疑慮）；同樣分別以 `only_confirmed=false`／`only_confirmed=true` 查詢一次，取得全部入帳與已達最終確定的子集。
- **本操作本身不觸發任何自動狀態轉換**（不呼叫模組5自動路徑）：僅刷新資料供商戶查看最新累計金額，避免reverify與背景任務2/3的自動路徑產生非預期的雙重觸發競態；商戶查看更新後的數據，若判斷需要變更狀態，另行呼叫下方「手動改判」端點。

### 手動改判（`POST /admin/orders/{id}/override-status`）

依模組5「手動改判路徑」（`SELECT...FOR UPDATE`鎖定 → 檢查狀態白名單 → UPDATE，**不重查金額子查詢**）。此路徑無伺服器端金額驗證防線、且成功即觸發真實終態Webhook，故疊加 `RequireTOTPCode`（見上方權限分級理由判準(3)）：

- Request 欄位：`to_status`、`note`（必填，改判理由，寫入 `order_state_transitions.note`）。
- 白名單（依需求書5.2定案）：`CONFIRMATION_STALLED → {COMPLETED, OVERPAID, EXPIRED}`；`EXPIRED → {COMPLETED, OVERPAID}`。不在白名單內的請求回傳明確錯誤，並依模組5既有規則記錄到獨立稽核日誌（`audit_logs`，`action_type='ILLEGAL_STATE_TRANSITION'`）。
- 改判成功比照任何終態轉換，同一transaction內觸發第8節 Webhook（`webhook_deliveries` INSERT）。

### 代收主錢包設定（`/admin/master-wallets`）

- **列表**：顯示所有歷史代收主錢包，`xpub` 僅顯示末幾碼＋建立日期（比照第10節IndexedDB辨識慣例，不需要在列表頁完整顯示xpub全文）、狀態（使用中／已停用，狀態旁輔以說明文字，依需求書5.5避免商戶誤解已停用代表資金不安全）、已分配索引數。
- **新增（`GET/POST /admin/master-wallets/new`、`/admin/master-wallets`）**：頁面沿用第10節已定案的離線打包`web/static/js`（`bip39`+`hdkey`，本頁僅需衍生到xpub層級，不需要`@noble/curves`等簽名相關函式庫，但共用同一bundle不另外拆包，降低維護成本）與嚴格CSP規格。依需求書5.1提供方式1（輸入既有助記詞，衍生前顯示風險提示）與方式2（產生新錢包，依序點選重建驗證備份）兩種路徑，皆在瀏覽器本地算出xpub後，只把xpub本身（公鑰，非機密）POST給後端，助記詞不落地不上傳。**此頁面本身不需要 `/tron-proxy`**：xpub衍生是純本地BIP32運算，不查詢TronGrid，與第10節歸集簽名頁（需要組交易/廣播查詢鏈上）不同。
- 後端收到xpub後：比對是否與任一歷史代收主錢包完全相同（重複則拒絕，提示改用「恢復使用中」，依需求書5.1防呆機制）；不重複則新增一筆 `status='active'`、`last_derived_index=0`（保留index 0，第3節衍生邏輯從1開始分配），同一transaction內把原本使用中的那筆改為 `inactive`。
- **恢復使用中（`POST /admin/master-wallets/{id}/reactivate`）**：沿用既有xpub記錄，不需重新輸入助記詞，同一transaction內切換使用中/已停用狀態，`last_derived_index` 維持原值續用（依需求書5.1「接續原本用到的地方繼續往上加」）。**目標本身已是使用中時，回傳明確錯誤**（「此代收主錢包已是使用中，無需操作」），不做靜默放行，避免商戶誤以為觸發了一次有效的狀態切換。
- 兩個寫入操作前端皆需彈出確認對話框（依需求書5.1「確認提示」，說明目前使用中的代收主錢包將轉為已停用）。

### API Key 管理（`/admin/api-keys`）

- **單一使用中API Key**（呼應單一管理帳號的簡化設計哲學，需求書5.5未要求多組並存）：`POST /admin/api-keys/regenerate` 產生新的一組 `key`+`secret`，同一transaction內把既有記錄 `revoked_at=now()`、新增一筆記錄。
- **一次性顯示原則**：`key` 與 `secret` 皆僅於產生當下的HTTP回應中明碼回傳一次，頁面提示「請立即複製，離開此頁面後將不再以明碼顯示」；資料庫僅存 `key_hash`（`SHA-256`，供 `X-API-Key` 查找比對用）與明碼 `secret`（第7節既有決策，HMAC重算需要）。**即使 `secret` 技術上可從DB明碼撈回，後台列表頁仍不常態明碼顯示**——比照 `key` 一次性顯示的原則統一處理，降低螢幕外流/瀏覽器快取風險，列表頁僅顯示建立時間、狀態（使用中/已作廢）。
- **`RequireTOTPCode`理由**：重新產生會讓商戶既有API串接的舊key立即失效，且新key/secret一旦外洩即可冒用商戶身分呼叫建單/查詢API，風險量級同代收主錢包切換。

### Webhook 端點設定（`/admin/webhook-config`）

後台路由整合第8節已定案的機制：

- `GET /admin/webhook-config`：查看目前設定，`RequireSession` 即可。
- `POST /admin/webhook-config`：設定/變更 `webhook_url`，`RequireTOTPCode`——風險不只是「URL本身外洩」（那確實影響有限），而是「URL被竄改重導向」：webhook_secret不變的情況下，若URL被改到攻擊者的伺服器，之後所有訂單終態通知（含金額、`merchant_order_no`）會被合法簽章、原封不動送到攻擊者手上，商戶自己的端點則靜默收不到任何通知，直到商戶自行發現對帳異常為止，風險量級同代收主錢包切換。
- `POST /admin/webhook-config/secret`：產生（系統`crypto/rand`）或手動輸入 `webhook_secret`，沿用第8節「輪替無過渡期」規則，變更後頁面顯示警語提醒商戶同步更新驗簽端設定；比照API Key，`RequireTOTPCode`——secret外洩可用於偽造Webhook通知（例如偽造 `ORDER_COMPLETED` 詐騙商戶誤判已收款），風險同代收主錢包/API Key。
- `POST /admin/webhook-config/test`：觸發第8節已定案的 `TEST_PING`（`RequireSession`，僅送一次同步測試請求，不落地不消耗重試額度）。

### 參數設定（`/admin/params`）

- `GET /admin/params`：一次讀出訂單有效期（秒）、金額容許誤差百分比、確認等待逾時時間三欄顯示。
- `POST /admin/params`：訂單有效期（秒）、確認等待逾時時間（可留空，留空時UI提示「預設沿用訂單有效期」，依需求書5.2）。寫入 `system_params`（第2節既有表），只SET這兩欄。`RequireSession` 即可：變更或觸發的對象僅限系統內部行為判斷、不改變之後訂單自動判定範圍。
- `POST /admin/params/tolerance`：金額容許誤差百分比（獨立表單、獨立路由，階段07全系統審查發現，見「權限分級理由」判準(4)）。`RequireSession` + `RequireTOTPCode`——調高此值會讓之後新訂單的短付更容易被系統自動判定為COMPLETED。
- 兩者皆僅影響之後新建立的訂單（依模組2/5既有快照機制），頁面需顯示提示文字避免商戶誤以為會回頭套用到進行中訂單。

### 通知歷史查詢與手動重發（`/admin/notifications`）

後台路由整合第8節已定案的機制，本節僅新增查詢介面：

- 列表可依訂單、`event_type`、`status`（awaiting_config/pending/sending/delivered/failed）篩選，顯示 `webhook_delivery_attempts` 逐次嘗試明細（HTTP狀態碼、回應內容截斷、觸發來源）。
- `POST /admin/notifications/{id}/resend`：呼叫第8節已定案的手動重發邏輯（不受狀態限制、不影響 `attempt_count`）。

### 稽核日誌查詢（`/admin/audit-logs`）

依需求書5.5「操作審計日誌：記錄商戶所有操作歷程」：

- 列表可依 `actor`、`action_type`、`target_type`、時間範圍篩選；`detail`（jsonb）於明細展開顯示。
- **`action_type` 涵蓋範圍**（彙整各模組既有定案＋本節新增，供實作對照）：第4節（`SCAN_CHECKPOINT_ANOMALY`，checkpoint異常倒退事件，見第4節「儀表板可見度」）、第9節（`LOGIN_SUCCESS`/`LOGIN_FAILED`/`TOTP_*`/`PASSWORD_CHANGED`/`LOGOUT`/session因嘗試次數上限被清除）、第10節（`CONSOLIDATION`/`FEE_TOPUP`/`CONSOLIDATION_BATCH_CREATED`/`FEE_TOPUP_BATCH_CREATED`/`ADDRESS_BOOK_ENTRY_CREATED`/`ADDRESS_BOOK_ENTRY_RENAMED`/`ADDRESS_BOOK_ENTRY_DELETED`，後五項為階段07全系統審查補上的缺漏，見[技術架構設計變更紀錄v0.13](開發流程框架-03-技術架構設計變更紀錄.md#v0-13)）、模組5（`ILLEGAL_STATE_TRANSITION`）、本節新增（`MASTER_WALLET_CREATED`/`MASTER_WALLET_REACTIVATED`/`ORDER_MANUAL_CREATED`/`ORDER_MANUAL_OVERRIDE`/`ORDER_MANUAL_REVERIFY`/`API_KEY_REGENERATED`/`WEBHOOK_URL_CHANGED`/`WEBHOOK_SECRET_ROTATED`/`PARAMS_CHANGED`/`AMOUNT_TOLERANCE_CHANGED`（同上v0.13新增）/`NOTIFICATION_MANUAL_RESEND`/`EXPORT_ORDERS`）。**Webhook URL變更與secret輪替拆成兩個獨立action_type**（`WEBHOOK_URL_CHANGED`／`WEBHOOK_SECRET_ROTATED`），不共用單一 `WEBHOOK_CONFIG_CHANGED`：後者被本節判定為與代收主錢包切換、API Key重新產生同等敏感（見上方權限分級理由），比照 `API_KEY_REGENERATED` 給予獨立可篩選的action_type，避免事後稽核追查secret是否曾被輪替時，被淹沒在單純URL變更的紀錄裡。**匯出（`EXPORT_ORDERS`）與重新查證（`ORDER_MANUAL_REVERIFY`）皆須記錄，即使兩者僅掛 `RequireSession`**：匯出可批次取得全站交易明細，重新查證會寫入 `incoming_transactions`，皆屬「記錄商戶所有操作歷程」字面要求涵蓋的操作，不因驗證等級較低而略過稽核。
- **不做自動清除/保留期限**：稽核日誌屬合規/追溯用途，append-only、無上限累積，非本版範圍需要處理的維運議題（若未來量體造成問題，屬部署/維運層級決策，非架構設計階段需要預先解決的假設性問題）。

### CSV/Excel 交易明細匯出（`GET /admin/export/orders`）

依需求書5.8：

- 匯出範圍：訂單列表（可套用與 `/admin/orders` 相同的篩選條件，避免另建一套篩選邏輯），欄位含訂單ID、`merchant_order_no`、地址、代收主錢包、目標金額、已確認累計金額、狀態、建立/完成時間。
- CSV：stdlib `encoding/csv`，UTF-8 with BOM（確保Excel開啟中文不亂碼），逐列串流寫入HTTP回應（不一次性把全部符合條件的訂單載入記憶體組字串），避免商戶未加篩選條件、匯出全站歷史訂單時造成記憶體壓力。
- Excel：`github.com/xuri/excelize/v2`（純Go實作，無CGO依賴，社群採用度高）提供的 `StreamWriter` API 產生 `.xlsx`，同樣採串流寫入，不一次性載入全部資料。
- 單次匯出**上限10萬筆**：超過此筆數，回傳明確錯誤要求商戶先縮小篩選範圍（時間區間/狀態）再重新匯出，不做無上限匯出。
- `RequireSession` 即可：內容為金額/狀態等營運資訊，不含私鑰/密碼等機密材料，權限等級同訂單列表本身。

### 同步修正第7節（對外API模組）

`RequireMasterWallet` Gate（見上方）新增建單API的前提條件，第7節「錯誤回應格式」既有清單（`INVALID_SIGNATURE`、`ORDER_CONFLICT`、`ORDER_NOT_FOUND`）補上第四個錯誤碼 `NO_ACTIVE_MASTER_WALLET`（HTTP 503）：系統尚無使用中代收主錢包時，`POST /api/v1/orders` 一律回傳此錯誤，不嘗試建立訂單。

### Schema 新增/修正（第2節）

本節無新增/修正欄位，沿用第2節既有 `orders`／`api_keys`／`audit_logs`／`system_params`／`master_wallets` 定義。
