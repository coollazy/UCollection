  - v0.10 變更：**地址正確性防呆機制拍板**。先市調 Tron 地址編碼機制與業界防呆做法（結論：Tron 地址是 Base58Check 編碼、內嵌 4-byte checksum，讀 TronWeb 官方原始碼確認 `isAddress()` 真的有做 checksum 驗證，理論抓錯率約 1-1/2³²，能擋掉幾乎所有打錯字/漏字類手誤；但抓不到「格式合法但認錯地址」這類錯誤，Tron/USDT-TRC20 生態有真實的 **Address Poisoning（地址下毒）**攻擊——攻擊者用頭尾相似的假地址零元轉帳污染交易紀錄，誘使受害者之後複製到錯誤地址，已有 5000萬美元真實損失案例，這也是「只核對頭尾幾碼」這種常見習慣特別危險的原因；比對業界機制（二次輸入比對／QR掃描／地址簿白名單延遲生效／Jazzicon視覺指紋）發現大多與我們「商戶單人操作、臨時輸入」的場景錯位或效益太低；機構級託管商Fireblocks文件顯示連小額測試轉帳+白名單這類機制都有已知漏洞，沒有純技術手段能完全根除「格式正確但認錯人」這個問題）。**拍板**：(1) 前端呼叫 TronWeb `isAddress()` 做即時checksum驗證，不合法立即拒絕；(2) UI完整地址分段顯示、要求核對全字串而非頭尾；(3) 提供「先轉小額測試」可選（非強制）流程，供商戶自行核對入帳。二次輸入比對／QR掃描／地址簿白名單延遲生效／視覺指紋等機制皆不採用（與情境錯位或效益過低）。已寫入需求書5.9流程步驟4。
  - v0.11 變更（**修正 v0.10 的一項決定**）：v0.10 原定案「歸集目的地地址不預先於後台設定/儲存」，重新考量後改為**新增歸集地址簿**：後台可新增/編輯（含改名）/刪除多筆地址；5.9歸集手動輸入的新地址只要廣播成功即自動存入地址簿，預設系統產生名稱，商戶事後可再改名（不要求歸集當下命名）；商戶仍可選擇不用地址簿、每次都手動輸入新地址，系統不強制。地址簿項目刪除/改名不回溯影響過去審計日誌（日誌保留當次送出時的地址原文與名稱快照）。小額測試機制同步簡化：不需要系統做分階段廣播，就是「商戶自己先發起一次只勾一個小額地址的歸集操作、確認到帳後，再發起第二次歸集操作處理其餘地址」，直接沿用步驟2、3既有的地址勾選能力，不是新技術機制。已寫入需求書5.9流程步驟4、5.5後台功能。

### 階段 03 技術選型（已與使用者確認，不受本次新增驗證項目影響）

- **開發語言：Go**（三項可行性驗證用 Go 重做全部一次通過，image 最小、純靜態連結、無相容性問題；相較 Swift 踩了兩個 Linux 相容性坑、image 378MB）
- **資料庫：PostgreSQL**（比較 PostgreSQL／MySQL／SQLite 後定案，關鍵考量：地址分配的併發安全用 advisory lock 處理最直觀、JSONB 適合審計日誌明細、長期報表擴充性夠）
- **前端：Go `html/template` + htmx**（零 Node.js 建置鏈，僅高風險頁面單獨 vendor 對應函式庫離線打包）
- **不內建反向代理/自動 HTTPS**（假設商戶自行架設 nginx/Cloudflare 等前方 TLS 終止；系統只需監聽一般 HTTP port；未來要加不難，之後在 docker-compose 多掛一個 container 擋在前面即可，不需改動現有程式碼）

- **鏈上監控用語需修正**：之前草擬 CLAUDE.md 內容時寫成「禁止逐一輪詢地址列表」，範圍寫過頭了。需求書 5.3 原文是：此限制僅適用於**主要監控**（即時、持續、覆蓋所有進行中訂單），**備援/降級監控情境不在此限**（例如寬限期低頻監控、主要資料源掛掉切備援時），逐一查詢地址在這些情境下並非不可行。正確寫法應是「主要監控以事件掃描為主，備援/降級情境可接受輪詢」，不是絕對禁止。
- **xpub 取得方式，曾考慮但排除／未採用的做法**（供之後寫 ADR 時參考，避免之後重新討論一輪）：
  - 伺服器端一次性生成 xpub（後端生成助記詞、算完 xpub 就從記憶體清除、不落地）——**已排除**，因為即使不落地，助記詞仍短暫進過伺服器記憶體，違反「伺服器全程不接觸私鑰」原則，风险面比瀏覽器端生成大（crash dump、swap、日誌框架意外印出等）。
  - 商戶自行在既有錢包「新增帳戶」產生一批地址、匯出清單匯入系統（不透過 xpub／HD 即時衍生）——**考慮過但未採用**，可行但地址是有限批次不是無限衍生，商戶要記得補；並非本次選定的三種方式之一，如果之後三種方式在實務上卡關，這條路可以重新拿出來討論。
  - 固定地址 + 金額尾數區分訂單（放棄「每筆訂單獨立地址」）——**未採用**，直接牴觸需求書 5.1「地址與訂單永久一對一綁定」，屬於要重新打開需求書範圍的討論，不是單純技術選型。
  - 方式 1（商戶直接輸入既有 xpub）——**已廢除**（v0.5），原本列為三種取得方式之一並寫入 v0.3 需求書，後經市調（見下方市場調查筆記）發現市場上查無任何主流 Tron 錢包支援匯出帳戶層級 xpub，此選項實務上無法使用，予以移除。過程中衍生的「xpub有效性驗證」「與5.9歸集路徑一致性」等問題（問題清單第1、4點）隨方式1移除一併消失，不必再花力氣解。
  - 用智能合約（CREATE2/Forwarder模式）批次生成收款地址，取代xpub HD衍生——**評估後未採用**。討論5.1時發現PayRam的Tron/EVM鏈用的是智能合約架構而非xpub，一度考慮跟進評估。深入評估後結論：(1) 合約無法自己醒來執行歸集，需要一把**常駐operator私鑰**觸發sweep，私鑰曝險頻率比我們原規劃「助記詞僅5.9手動歸集時瀏覽器端短暫現形」更高，不是更貼近「伺服器全程不接觸私鑰」原則；(2) 歸集需額外一次「部署+自毀合約」開銷，成本比純位址衍生+TRC20轉帳更高；(3) 完全沒解決5.9歸集需要TRX/能量的問題，只是把簽名者從商戶助記詞換成常駐熱錢包；(4) 增加reentrancy、合約升級、稽核等純HD衍生不用面對的複雜度與風險。且查到業界逆向訊號：Kraken近期反而把EVM存款從智能合約地址改回標準EOA地址（[Kraken說明](https://support.kraken.com/articles/how-to-transition-to-unified-evm-deposit-methods-technical-overview-for-api-users)），方向相反。PayRam是閉源產品，合約細節無法查證，可能只是把類似HD邏輯包裝在合約UI底下，不代表業界公認更優解。技術參考：CREATE2在TVM上可行（[TVM vs EVM文件](https://developers.tron.network/docs/tvm-vs-evm)），Tron部署一個標準合約約消耗58~150 TRX（[Contract Development Cost](https://developers.tron.network/v3.7/docs/benchmark)），ERC-2802提案（[討論串](https://github.com/ethereum/EIPs/issues/2802)）明確指出sweep一定要外部帳戶發交易觸發。**維持xpub HD衍生路線**。
  - 商戶端「送出前驗證xpub是否正確」的UX機制（例如顯示地址預覽供商戶自行核對）——**評估後未採用**（問題清單第3點）。商戶現實中不會真的去核對，且若問題出在衍生邏輯本身有bug，商戶也無從比對出「正確答案」，加UX步驟未必有實質防護效果。改用工程手段：驗證項目4已用雙函式庫交叉比對確認結果一致（PASS），**階段04開發時須搭配自動化測試持續守住這件事**，不做成商戶端功能。

### 市場調查筆記（討論 5.1 時查證，供之後參考，避免重查）

- **xpub 衍生地址這個架構本身有市場先例，不是我們自己想像的做法，但 PayRam 對 Tron/EVM 鏈其實走的是不同技術路線，不是 xpub 衍生**：商業自架收款閘道 **PayRam**（UAE 公司，閉源）先前筆記寫「伺服器只握 xpub」，是根據其行銷文案「PayRam uses a read-only xPub」下的推論，經查官方 onboarding 文件（[Wallet Integration](https://docs.payram.com/onboarding-guide/wallet-integration)）後發現這句話**只適用於 Bitcoin**：Bitcoin 流程是商戶把 12 字助記詞貼進 PayRam 自己提供的工具算出 xpub（工具端「generate addresses」後助記詞即丟棄，貼近我們方式2/3 的精神，但流程是先在獨立工具算好、再把 xpub 貼進 `config.yaml`，不是即時串接的後台表單）。**Tron/EVM 鏈完全是另一套架構**：商戶用瀏覽器錢包（TronLink/MetaMask）直接連接一個商戶自己握私鑰的「主錢包」帳戶，輸入歸集目的地（冷錢包地址，規定須與主錢包不同），按下部署後在錢包簽名確認一筆鏈上交易——**主錢包部署一個智能合約，由合約負責批次生成充值地址**（「PayRam 生成一批充值地址，在客戶到達前處於未分配狀態」），主錢包需持有原生代幣（Tron上即TRX）支付部署與後續交易的手續費。也就是說 PayRam 用**智能合約**繞開了「帳戶模型鏈不支援匯出xpub」的限制，而不是像我們一樣硬用BIP44標準路徑做HD衍生。
  - 注意：這只是從官方文件片段查到的架構線索，**CREATE2/deterministic address、合約掃清（sweep）機制、gas精確處理方式、合約升級/重放風險等技術細節都沒有深入驗證**，不能當作我們可以直接照搬的完整方案，僅供架構方向參考。
  - 對我們的啟示：我們原本一直在細修的「xpub取得方式方式1（既有xpub）」在市場上本來就是稀有情境（連做法最貼近我們的PayRam，Tron這端都沒有真的用xpub），這是促成後續深入市調、最終決定廢除方式1的第一條線索（見下方另兩則市調筆記與上方「曾考慮但排除」清單）。
- **但開源圈子裡沒找到跟我們完全一樣做法的**：實際翻原始碼確認——
  - **SHKeeper**（`vsys-host/tron-shkeeper`）：每個地址是**伺服器生成的全新隨機私鑰**，加密後存資料庫，付款/歸集時解密使用——私鑰會經過伺服器，跟我們「伺服器全程不碰私鑰」是不同等級的安全設計。
  - **UPay**（`UPay-USDT/USDT-Payment-Gateway`）：**固定地址池輪詢分配**給訂單，不是 xpub 無限衍生，這正是進度.md 上面「曾考慮但排除」筆記裡提過的替代方案，證實市場上真的有人這樣做。
  - 結論：我們的 xpub-only 架構比市場上查到的開源方案都更嚴格，可能因為「這件事本身很難做對」+「不是 Tron 生態原生慣例（見下）」+「多數開源專案圖省事」三個原因疊加，不代表這條路有問題（六項技術驗證已用真實測試網廣播＋獨立查鏈證實可行）。
- **Tron 官方原生的多帳戶衍生慣例（TIP-01：`m/44'/195'/x'`，三層全硬化）跟我們用的 BIP44 標準五層路徑不同**——TIP-01 沒有非硬化 change/index 層，無法只靠 xpub 衍生多個地址，這解釋了為什麼「主流 Tron 錢包普遍不支援匯出可用 xpub」：不是市場剛好沒做，是 Tron 原生慣例的技術模型跟「xpub 衍生」這件事本身不相容。我們用標準 BIP44 五層路徑是滿足「伺服器不碰私鑰」需求唯一可行的選擇，不是選錯。
- **帳戶模型鏈（Ethereum、Tron）普遍不支援匯出 xpub，UTXO 鏈（Bitcoin）普遍支援**：查證 MetaMask（以太坊最主流錢包）也不支援匯出 xpub，跟 Tron 錢包狀況一致，是整個帳戶模型鏈家族的通例，不是 Tron 特例。
- **USDT 在 Tron 上是主流中的主流**：Tron 上 USDT 市值約 890 億美元、佔全體 USDT 市值 47%（所有鏈最高），小額（<$1000）零售支付市佔更高達 52%，需求書鎖定 USDT-TRC20 這個切角選對了市場。
- **Binance Pay / Bitfinex Pay 不是好的參考架構**：兩者主要走內部帳本（off-chain ledger），只有同平台會員互轉才免手續費，跟「開放式接受任何外部錢包付款」是不同題目，不適合拿來比對我們的收款地址設計（雖然 Bitfinex Pay 有支援外部錢包付款，但公開文件沒寫清楚那條路徑的地址怎麼產生，沒有深入查證）。
- **市場上唯一真實存在過的「Tron xpub HD衍生收款」實例已停運5年，且用非標準路徑**：`go-faast/tron-payments`（已停運交易所Faast的自用套件，`@faast/tron-payments`，libraries.io顯示最後發布約5年前，GitHub已封存）用Bitcore實作BIP32/44，路徑`m/44'/195'/0'/0/n`（非硬化change/index層），架構與我們規劃的完全一致。但這條路徑跟TronLink、imToken等官方錢包走的TIP-01（全硬化）路徑不相容——商戶若拿官方錢包助記詞給這套邏輯衍生，算出的地址官方錢包自己看不到、對不上帳，這正是此類方案在市場上幾乎絕跡的原因：不是密碼學做不到，是跟主流錢包生態兜不起來。Tron官方自己有提案想做這件事（[TIP-102](https://github.com/tronprotocol/tips/blob/master/tip-102.md)，路徑刻意設計成非硬化change/index層），但2019年提出至今仍是"Last Call"狀態、無任何錢包或交易所實作。業界對此的標準表述是「帳戶模型鏈（Tron/EVM）只需要地址，UTXO鏈才需要xpub」。
- **BIP32非硬化衍生有已知的洩露風險，但這是整個BIP32/44生態的通例，非我們架構特有**：BIP32官方規範明文警告「知道父層xpub加上任何一個非硬化衍生的私鑰，等同於知道父層完整的xprv（因此該父層底下過去和未來所有的公私鑰都會曝光）」，這是純橢圓曲線代數性質，跟鏈是UTXO還是帳戶模型無關；Tron官方TIP-01全硬化路徑正是在落實這條BIP32官方建議。但**這個風險不構成放棄xpub衍生架構的理由**——Bitcoin主流硬體/軟體錢包（Ledger、Trezor、Electrum）同樣是「帳戶層以上全硬化、change/index層非硬化」的結構，全球用戶每天都活在同一個風險假設下。光有xpub推不出任何私鑰，要出事必須**另外**發生一次子私鑰外洩的獨立事故（簽名環境中毒、惡意腳本、備份外流），不是正常操作會自動觸發的事。真正值得留意的是「歸集簽名環境的資安等級」——我們的5.9手動歸集是在商戶一般瀏覽器裡衍生私鑰簽名，風險等級接近Electrum這類軟體錢包（而非Ledger/Trezor等硬體錢包，私鑰衍生在晶片內完成、外洩面更小），但這仍是非託管錢包生態普遍接受的等級，不算特例。我們既有的「離線打包、嚴格CSP、無第三方腳本」規格，正是在對這個風險做緩解，架構設計階段應持續強化，但不需要因此放棄xpub-based架構。
- **沒有現成的瀏覽器插件能幫我們做掉「助記詞→xpub」這件事**：查證TronLink等錢包插件注入API（`window.tronLink`/`tronWeb`），只暴露「地址+簽名」方法，沒有任何方法能建立帳戶或匯出xpub/公鑰，協定設計上就不開放，程式化呼叫也繞不過去（[TronLink Docs](https://docs.tronlink.org/plugin-wallet/active-requests/)）。WalletConnect類協定規格同樣沒有xpub這個概念，本質是「請求簽名」不是「請求金鑰資料」（[WalletConnect Specs](https://specs.walletconnect.com/2.0/specs/clients/sign/namespaces)）。唯一「有機會」的路是Ledger硬體錢包WebUSB/WebHID直連瀏覽器，`@ledgerhq/hw-app-trx`在特定參數下會回傳`publicKey`+`chainCode`（私鑰不離開裝置），理論上可自行拼出xpub，但仍要自己寫BIP32序列化邏輯，且前提是商戶要有Ledger硬體，商業上不能取代現有方案。**結論：維持自建離線頁面路線，沒有插件可以省下來**。
- **iancoleman/bip39這類獨立BIP39/BIP32開發者工具，不建議讓商戶跳轉過去操作再貼回來，但可以引用其MIT授權的衍生邏輯**：查證iancoleman/bip39（純前端單一HTML+JS檔案，MIT授權，內建Tron/coin type 195選項，可直接輸出xpub，功能上完全符合需求）。但這工具因知名度高，**多次被釣魚仿冒**（GitHub issue [#437](https://github.com/iancoleman/bip39/issues/437)、[#556](https://github.com/iancoleman/bip39/issues/556)、[#444](https://github.com/iancoleman/bip39/issues/444)、[#269](https://github.com/iancoleman/bip39/issues/269)，假網域透過廣告排名超前真站，已有使用者助記詞被盜的真實案例）；若讓商戶跳轉到外部網站操作，等於把「商戶會不會跑錯網域」這個風險完全交給商戶自己判斷，比我們自建「離線打包+嚴格CSP」（助記詞永遠只在商戶已信任的自家系統網域下運作）安全等級明顯更差；且xpub是100+字元字串，複製貼上容易出錯，商戶也可能選錯幣別。**MIT授權允許自由修改再散布商用**，建議架構設計/開發階段直接把iancoleman/bip39處理BIP32/Tron xpub衍生的核心邏輯引入自己的離線打包+CSP頁面，同時拿到「被廣泛驗證過的程式碼」與「網域自主可控」兩個優點，優於完全自己從零刻或叫商戶跳轉外部工具。
