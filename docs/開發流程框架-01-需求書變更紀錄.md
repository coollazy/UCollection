### v0.5（2026-08-28）
5.1 xpub 取得方式廢除「商戶直接輸入既有 xpub」選項。背景：Tron 是帳戶模型鏈，主流 Tron 錢包普遍不支援匯出帳戶層級 xpub（與 Bitcoin 生態的 Trezor/Ledger/Electrum 不同）；地址、一般格式私鑰皆無法反推出 xpub（缺少必需的 chain code），能穩定推出可用 xpub 的來源僅有助記詞（或風險等級相同的擴充私鑰 xprv／原始 seed，實務上商戶僅會操作助記詞）。市場上查無「商戶直接輸入既有 xpub」的實務可行取得管道（詳見 [進度.md](進度.md)），因此廢除此選項，僅保留「輸入既有助記詞」與「產生新錢包」兩種方式。

### v0.21（2026-08-31）
獨立完整度審查發現 5.2 訂單狀態機缺口：CONFIRMING 狀態沒有逾時/失敗規則，理論上可能因確認數設太高、鏈上資料來源異常、或該筆交易後續從鏈上消失而無限期卡住，商戶完全無感知。**拍板**：新增獨立可調參數「確認等待逾時時間」（商戶未特別設定時，預設值與「訂單有效期」相同）；超過此時間仍未達確認數，訂單轉為新增異常狀態 CONFIRMATION_STALLED，停止自動等待、Webhook 通知商戶，交由商戶於後台人工處理（比照 UNDERPAID/OVERPAID 既有精神）。同時明文寫出原本只隱含在狀態機圖裡的規則：「訂單進入 CONFIRMING 後不再受訂單有效期限制轉為 EXPIRED」。已寫入需求書 5.2、5.5。

<a id="v0-22"></a>
### v0.22（2026-08-31）
**5.2 訂單狀態機重新設計，狀態數從 9 個收斂為 6 個**：(1) 金額判斷改採累加制——系統累加同一收款地址、該筆訂單監控期間內所有已達確認數的入帳金額，不再只看單一筆交易；(2) CONFIRMING 重新定義為「累計金額已達目標容許誤差範圍」才進入，不是「偵測到任一筆入帳」就進入；(3) 原本 UNDERPAID（CONFIRMING 底下金額不足的分支）拿掉，語意併入 EXPIRED，用訂單本來就有的「已收金額」欄位區分 0 元或部分金額，不再是獨立狀態；(4) **拍板不設寬限期**：訂單有效期到期、累計金額未達標，一律直接轉為 EXPIRED 終態，系統停止自動監控，不再有寬限期低頻輪詢這個階段，因此 LATE_PAYMENT_DETECTED、CLOSED 兩個狀態一併拿掉；後台仍永久保留「手動重新檢查此地址」功能，商戶可自行查詢、決定後續操作。最終狀態機收斂為 PENDING／CONFIRMING／COMPLETED／OVERPAID／CONFIRMATION_STALLED／EXPIRED 共 6 個狀態。(5) **Webhook 通知規則明確化**：COMPLETED／OVERPAID／CONFIRMATION_STALLED／EXPIRED 四個終態各保證觸發恰好一次通知，不因終態原因不同而省略、也不會重複發送；CONFIRMING 不觸發通知。已寫入需求書 5.1、5.2、5.3、5.5、5.7。

### v0.23（2026-08-31）

### v0.24（2026-08-31）
處理中嚴重度 **M2（COMPLETED 後同地址又收到入帳）**。討論釐清這其實分兩種情境：(1) 訂單完成、**尚未歸集過**前又收到額外入帳——5.9「待歸集地址列表」補上顯示訂單原定目標金額，COMPLETED 訂單若實際餘額超過目標金額則標示提醒，商戶做歸集時自然會看到；(2) 訂單**已完成歸集**（餘額歸零）後才又收到新入帳——評估後確認**技術上無法用符合規模化原則的方式主動偵測**（比對所有歷史地址需要放棄事件掃描的規模化優勢，回頭逐一查詢地址，隨訂單量增長不現實；但若改用內部旗標判斷該不該查，旗標在歸集完成後不會被重新觸發，一樣接不到）。**拍板**：不做主動偵測，此情境列為已知風險/限制明文寫入需求書，資金仍安全於鏈上但系統不主動示警，商戶需自行查證。已寫入需求書 5.9。

### v0.28（2026-08-31）
改寫第1節產品定位。原文開頭用「白牌 USDT(TRC20) 代收軟體」，語感偏向完整系統，沒點出商戶需要拿它跟自己既有訂單系統整合這件事。討論措辭：先提「套件」，但套件通常暗示嵌入商戶程式碼的 library/SDK；而 UCollection 實際上是打包成 **Docker image** 獨立部署運行、商戶透過 API 呼叫，語意上更接近「服務」。最終**拍板**用「**代收服務套件**」——保留「套件」呼應原本賣斷交付、商戶自行部署的定位，同時用「服務」點出它是獨立運行、透過 API/Webhook 整合的架構型態，不誤導成 library。內容新增一段說明商戶需將 UCollection 與自身訂單系統整合（透過 API 建單、接收 Webhook），UCollection 專責代收流程本身、商戶商品/交易邏輯不在範圍內；核心設計原則新增「僅負責代收功能面」一條。「賣斷」交付模式、「單租戶架構」原有定位維持不變。已寫入需求書第1節。

### v0.33（2026-09-01）
重啟階段03前再次通讀需求書做完整度檢查，發現 5.2 訂單狀態機缺口：**手動改判**規則原本只能將 `CONFIRMATION_STALLED` 改判為 `COMPLETED` 或 `OVERPAID`（往「錢有到」的方向），但訂單進入 `CONFIRMING` 後已不受訂單有效期限制轉 `EXPIRED`（5.2 CONFIRMING 階段規則既有拍板），若商戶用「手動重新檢查此地址」查證後發現該筆卡住等待確認的交易其實已從鏈上消失、根本沒收到達標金額，原文沒有任何路徑可以把這筆訂單結案，會永久卡在 `CONFIRMATION_STALLED`。

討論確認：解法不做成系統依時間自動轉判——系統無法分辨「這筆真的從鏈上消失了」與「只是確認數設太高、實際上會晚一點確認上」，兩者表面現象相同，自動轉判可能誤殺後者，且會牴觸 5.2 既有設計原則「系統不主動判斷根本原因，一律先標記異常交由商戶決定」。**拍板**：比照既有「手動改判」機制，把 `CONFIRMATION_STALLED` 的改判目標從「只能改到 COMPLETED/OVERPAID」擴增為「也可依查證結果改判為 EXPIRED」，維持一律由商戶人工查證後決定、系統不自動判斷的既有精神。已寫入需求書 5.2（手動改判）、5.7（Webhook 觸發規則同步涵蓋此改判方向）。

另外，過程中討論到訂單內部「累積金額」在此類異常情境下的計算方式（例如採即時重新查鏈的算法，或只增不減的累加計數器，兩者在交易因鏈重組消失時的正確性不同）——此為 HOW 層級的實作選擇，不寫入需求書，記錄提醒於 [進度.md](進度.md)「下一步」，供階段03架構設計參考。

5.5 帳號安全補上密碼格式規則：討論修改密碼功能時發現，需求書只寫了「有修改密碼功能」，未定義系統該接受/拒絕什麼樣的密碼，QA 無法據此寫驗收案例。**拍板**：僅設長度下限（最短 12 碼），不強制大小寫/數字/符號組合。理由：現代資安趨勢（NIST SP 800-63B）認為長度比複雜度組合更有效，複雜度規則常逼使用者用可預測的變形規避（例如 Password1! → Password2!），反而降低實際安全性。已寫入需求書 5.5。

**5.9 流程段落改寫**（設定頁＋簽名頁）：
- 設定頁：待歸集列表支援單選與全選；選歸集目的地；選手續費支付方式（分大類，本版僅「支付 TRX」，為未來能量方案預留分類）並填 TRX 來源地址、可查該地址 TRX 餘額；可按「手續費試算」依目的地是否首次收款與勾選筆數即時估算第一筆/其餘筆能量與 TRX 並加總。
- 簽名頁：單頁同時輸入代收主錢包助記詞、TRX 來源錢包助記詞/私鑰、TOTP；系統自動依序完成——對各子地址扣除現有可用 TRX 後補足所需（首筆多、其餘少）→ 等 TRX 上鏈 → 先廣播第一筆 USDT 歸集使目的地首次收款啟用 → 等其上鏈成功 → 再廣播其餘。任一筆失敗即停止、回報現況，商戶可重新發起，系統依鏈上現況只執行尚未完成的部分（可重入）。
