### 情境E詳細發現：晚到的confirmed金額不會讓已終結的訂單重新判定

**測試方式**：order 205先轉入精確100（觸發CONFIRMING），在CONFIRMING觸發後立刻（約10秒內）追加轉入20，測試finality判定是否會重新加總所有已確認入帳。

**實際結果**：
- 訂單最終卡在**COMPLETED**（`order_state_transitions`只有一筆PENDING→CONFIRMING→COMPLETED的紀錄，沒有第二次轉換）
- 但`incoming_transactions`真實加總（`detected_total`＝所有已偵測入帳，`confirmed_total`＝已最終確認入帳）最終雙雙來到**120000000**（120 USDT），超過上界100.5
- Webhook實際送出的payload：`{"status":"COMPLETED","target_amount":"100000000","total_confirmed_amount":"100000000",...}`——**回報給商戶的金額是錯的，少報了20 USDT**
- App log找到明確證據：`2026/09/06 00:56:56 scanner: finality task: handle event 90c53508...: order: current status not in allowed-from whitelist: order 205 is COMPLETED, allowed from [CONFIRMING]`——第二筆的最終確認事件因為訂單已經是COMPLETED終態而被系統**靜默拒絕**，只寫進app log（不是audit log、不會出現在後台任何畫面、不會觸發任何提醒）

**根本原因**：`internal/scanner/task_finality.go`的`scanFinalityOnce`用迴圈逐一處理每個鏈上事件，每個事件各自「先標記confirmed=true、再呼叫`EvaluateFinal`判定」，不是「先把這批事件全部標記完、才統一判定一次」。如果同一筆訂單有兩筆分開的入帳，且第二筆的最終確認（`only_confirmed=true`）比第一筆的判定時間點晚（即使只晚幾秒），第一筆就會先把訂單鎖定為COMPLETED終態；第二筆之後才確認時，`EvaluateFinal`因為訂單已經不是CONFIRMING狀態而被白名單擋下，這個判定結果就永久遺失，不會重新評估、也不會有任何人看得到這個落差。

**影響評估**：資金本身沒有損失（consolidation模組之後歸集是直接讀鏈上真實餘額，不是讀`orders`表的`confirmed`欄位），但**商戶端收到的Webhook與後台看到的訂單記錄會低報實際收到的金額**，且沒有任何機制能讓商戶或系統自己發現這個落差——除非事後手動比對鏈上餘額與訂單記錄。這符合CLAUDE.md「錯了會默默壞掉、不會報錯」的高風險模式，即使不在CLAUDE.md明列的金鑰/簽名/廣播範圍內，仍呈報給使用者決定。

**修正（2026-09-06，使用者已核准並完成）**：範圍限定「補稽核記錄讓問題可見」，**不修改**`internal/order`的`manualWhitelist`（COMPLETED是否該開放人工改判是獨立、更大的決策，留待之後另外討論，見`.claude/plans/cuddly-snacking-orbit.md`「後續」章節的完整取捨說明）。
