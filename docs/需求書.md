## 1. 產品定位

UCollection 是一套**白牌 USDT(TRC20) 代收軟體**，以「賣斷」方式交付給個別商家/企業買家自行部署使用，而非由開發方營運的雲端服務。

核心設計原則：

- **不經手資金、不儲存私鑰**：系統僅使用商戶提供的錢包 **xpub（擴充公鑰）**，以 HD（分層確定性）方式為每筆訂單衍生獨立收款地址，全程無法動用商戶資金。
- **單租戶架構**：一套部署對應一個商戶，不做多租戶/子商戶管理。
- **純軟體工具定位**：不內建 KYC/AML、不代為處理法幣結算，合規責任由使用本軟體的商戶自行承擔（見第 9 節免責事項）。

## 3. 系統範圍

**In scope**
- USDT-TRC20 單一鏈別的收款地址生成、鏈上入帳監控、訂單狀態判定
- 對外 API（供商戶自身系統整合建單）＋ 後台手動建單
- Webhook 通知（含簽章、重試、查詢、手動重發）
- 前台收銀頁、後台管理介面（單一帳號 + 2FA）
- 報表、CSV/Excel 匯出、操作審計日誌
- Docker/docker-compose 一鍵部署
- **手動歸集功能**：瀏覽器端簽名協助商戶將分散於各衍生地址的 USDT 集中到歸集錢包（詳見 5.9），伺服器全程不接觸私鑰

**Out of scope（本版不做）**
- 多租戶/子商戶架構
- **伺服器端私鑰託管、自動化背景歸集**（歸集僅限手動觸發＋瀏覽器端簽名，見 5.9）
- **代商戶對外之出款/提領/代付功能**：即代商戶將資金付給非商戶自己所有之第三方錢包。（商戶將收款地址資金歸集回自己歸集錢包的手動操作，受益人始終是商戶本人，性質為內部資金管理，**不屬於此排除項**，已於 5.9 列為 in-scope）
- 法幣金額換算、匯率風控
- KYC/AML 身分驗證、風控名單篩查
- License Key 防盜版機制（已確認不做）
- 除 TRC20 以外的鏈別
- **系統監控告警**：鏈上監控中斷、輪詢異常、Webhook 持續失敗等情況本版不做自動偵測與主動通知，商戶需自行透過後台查看狀態（已確認不做，可留作 Phase 2 待辦）
- **資料備份與復原機制**：本版不內建備份/還原工具，資料保護（含防止硬碟損毀導致地址-訂單對應遺失）由商戶自行於部署環境負責（已確認不做，可留作 Phase 2 待辦）

## 4. 使用者與角色

- **商戶（單一管理帳號）**：登入後台，可設定代收主錢包、查看/建立訂單、調整參數、查通知紀錄、匯出報表、查審計日誌。登入需 2FA（TOTP）。
- **商戶的外部系統**：透過 API Key + HMAC 簽章呼叫建單/查詢 API，接收 Webhook 通知。
- **付款人**：無帳號，透過前台收銀頁完成付款，不接觸後台。

> 本版不設多角色權限分級（無老闆/財務/客服之分），單一管理帳號即可。

## 5. 功能需求

### 5.1 收款地址管理
- 商戶於後台設定**一個代收主錢包**（技術上即一組 xpub，用來衍生每筆訂單的收款地址；下稱「代收主錢包」，UI 與商戶溝通一律用此名稱，不直接顯示 xpub 字樣）。
- 系統依 BIP32/44 規則，針對代收主錢包的下一個索引衍生新地址；索引**只增不減、不重複使用**。
- **索引從 1 開始分配給訂單，index 0 永遠不分配給任何訂單，不論代收主錢包是透過下方哪一種方式取得。** 因為 index 0（`.../0/0`）是業界慣例上任何標準錢包工具匯入同一組助記詞都會顯示的「預設地址」——對方式 1（商戶既有助記詞）而言，這個地址很可能是商戶原本就在使用、已有真實餘額與交易紀錄的日常地址；對方式 2（系統產生新錢包）而言，這個地址則是任何工具事後查詢都會顯示的預設位置。若拿去當某張訂單的收款地址，會與商戶原有的資金活動混淆，或造成不同工具看到的地址身分衝突。index 0 保留但用途未定案。
- 地址與訂單為**永久一對一綁定**，即使訂單已結束/逾時，該地址永遠不會分配給其他訂單。

#### 代收主錢包取得方式

v0.2 未定義商戶實際上如何取得代收主錢包（xpub）。背景說明：Tron 是帳戶模型鏈，主流 Tron 錢包普遍不支援匯出帳戶層級 xpub（這點與 Bitcoin 生態不同，Trezor/Ledger/Electrum 等 Bitcoin 錢包普遍支援匯出 xpub）。地址、一般格式的私鑰皆無法反推出 xpub（缺少 xpub 必需的 chain code），唯一能穩定推出可用 xpub 的來源是**助記詞**。

v0.5 變更：原方式 1（商戶直接輸入既有 xpub）**已廢除**（市場上查無實務可行的取得管道，詳見 [進度.md](進度.md)）。因此後台的「新增代收主錢包」功能僅提供以下兩種方式：

1. **商戶於瀏覽器端輸入既有助記詞**：由系統前端在瀏覽器本地計算出對應 xpub，助記詞**不上傳、不經過後端、不落地**。輸入後系統先驗證**助記詞格式合法性**（字數符合 BIP39 規範、每個字皆在 BIP39 字典內、checksum 位元正確），驗證不過則拒絕並顯示明確錯誤，不繼續衍生。
2. **商戶使用系統提供的「產生錢包」功能**：瀏覽器端隨機產生一組新助記詞，顯示一次供商戶抄下。顯示後，比照 TronLink 做法，要求商戶依序點選重建完整助記詞以驗證備份正確；驗證通過才計算 xpub 送給後端，助記詞同樣**不上傳、不落地**；驗證不通過可返回重新查看助記詞再試一次。

方式 1、2 共用以下安全規格（與 5.9 手動歸集頁面相同等級，非獨立另訂規則）：
- 此頁面不引入任何第三方腳本/CDN/分析工具。
- 使用的助記詞/xpub 衍生函式庫需離線打包隨系統一併部署，不於執行時從外部來源載入。
- 套用嚴格 CSP，限制頁面可執行的腳本來源。
- 選擇方式 1（輸入既有助記詞）時，需先顯示明確風險提示：「此助記詞的安全性將與本系統綁定，建議使用專門的收款用助記詞，避免使用日常錢包的助記詞」，商戶確認後才可繼續輸入。

#### 代收主錢包變更

商戶可於後台變更代收主錢包（見 5.5）。變更語意採**「舊代收主錢包停止分配新訂單，但不代表舊地址／資金失效」**（市調 BTCPay Server、Blockonomics 皆採此語意：換 xpub 是解除追蹤關係，非讓舊地址作廢，詳見 [進度.md](進度.md) 市場調查筆記）：

- 系統記錄商戶每一個曾經設定過的代收主錢包（xpub 值、狀態：使用中／已停用、啟用/停用時間）。同一時間只有一個「使用中」，新訂單一律綁定使用中的那個。**代收主錢包與商戶的「歸集錢包」（歸集目的地帳戶，見 5.9）是不同概念，不可混用**：代收主錢包是「系統依何組公鑰衍生訂單地址」的來源，歸集錢包是「歸集後資金最終去向」。
- 每張訂單記錄其收款地址衍生自哪一個代收主錢包。
- 商戶送出新代收主錢包後，原本使用中的那個轉為「已停用」，但**已停用代收主錢包底下已分配的地址持續受 5.3 鏈上監控**，直到其下所有訂單皆走到終態（完成/逾時/寬限期結束）為止，確保變更當下的進行中訂單不受影響。
- 已停用代收主錢包底下地址若仍有餘額，商戶仍可透過 5.9 手動歸集取回，不因停用而失去存取能力（只要商戶保留對應助記詞）。
- 5.9 手動歸集操作**一次只能對應一個代收主錢包**（不論使用中或已停用）：商戶先選擇要歸集哪一個代收主錢包底下的地址，輸入對應助記詞後，系統驗證衍生出的 xpub 與該代收主錢包相符才放行，避免混淆助記詞或跨代收主錢包混合歸集（降低多組助記詞同時暴露於同一瀏覽器 session 的風險）。

### 5.2 訂單管理
**建立方式**
- 商戶外部系統可呼叫建單 API（金額以 USDT 直接指定，不做法幣換算）。
- 後台亦提供手動建單功能，方便測試與人工收款情境。

**訂單狀態機**

```
PENDING（等待付款，全速監控）
  → CONFIRMING（偵測到鏈上交易，等待達到確認數）
    → COMPLETED（達確認數，金額在容許誤差內）
    → UNDERPAID（金額不足，超出誤差範圍 → 人工處理）
    → OVERPAID（金額超過，超出誤差範圍 → 人工處理）
  → EXPIRED（逾期未收到款，進入寬限期低頻監控）
    → LATE_PAYMENT_DETECTED（寬限期內偵測到入帳 → 標記異常，通知商戶）
    → CLOSED（寬限期結束仍無入帳，停止自動監控）
```

- **確認數、訂單有效期（逾時時間）、金額容許誤差百分比**皆為可調參數，商戶後台有獨立的參數設定頁，可設全域預設值。
- 逾期後進入**寬限期監控**（預設 24 小時，可調），以較低頻率持續追蹤該地址，避免遺漏延遲到帳的付款。
- 寬限期結束後，系統停止自動輪詢，但後台**永久保留「手動重新檢查此地址」功能**（因區塊鏈地址本身永久有效，隨時可能收到款項）。
- 超付/少付訂單**不自動退款或補收**，系統僅標記異常狀態並通知商戶，由商戶自行於後台人工處理。

### 5.3 鏈上監控
- 資料來源：**Tron 官方維運的公開閘道（如 TronGrid）為主，可搭配 TronScan 等獨立第三方 API 作為備援**，不提供自架全節點選項（降低商戶部署門檻）。
- 監控頻率分兩階段：訂單有效期內全速輪詢；逾期後轉低頻寬限期輪詢；寬限期後停止，改為手動觸發。
- **主要監控**須採**區塊/事件掃描**（掃描 USDT 合約的轉帳事件，比對是否命中系統中的訂單地址），**不得**採「逐一輪詢每個地址」的方式。原因：後者的 API 呼叫量會隨監控中地址數量線性增加，訂單量一大就容易超出第三方 API 的免費/速率額度，前者的呼叫量只跟區塊產生速度有關，與地址數量無關，具備規模化能力。
- 此限制僅適用於主要監控（即時、持續、覆蓋所有進行中訂單）。**備援/降級監控情境不在此限**，因當下需輪詢的僅為進行中訂單（有界集合），且可接受降頻，逐一查詢地址並非不可行，實際方式屬技術設計階段決定。

### 5.4 前台（付款人收銀頁）
- 顯示：收款地址、對應 QR code、應付 USDT 金額、剩餘有效時間倒數、目前訂單狀態。
- 無需付款人登入或提供個資。

### 5.5 後台（商戶管理介面）
- 儀表板：總收款金額、待處理訂單數、異常訂單數等統計。
- 訂單列表：查詢、篩選、明細檢視。
- 代收主錢包設定：設定/變更代收主錢包，並可查看歷史所有代收主錢包與其狀態（變更語意見 5.1）。
- 參數設定頁：確認數、訂單逾時時間、金額誤差容許百分比、寬限期時長。
- 通知紀錄查詢與手動重發（見 5.7）。
- 操作審計日誌：記錄誰在何時變更了哪些設定。
- 交易明細 CSV/Excel 匯出。
- 單一管理帳號登入，強制 2FA（TOTP）。

### 5.6 API（供商戶外部系統整合）
- 建單 API、訂單查詢 API。
- 認證方式：**API Key + HMAC 簽章**（與 Webhook 簽章機制一致）。

### 5.7 Webhook 通知
- 訂單狀態變更（COMPLETED / UNDERPAID / OVERPAID / LATE_PAYMENT_DETECTED 等）主動推送給商戶指定端點。
- 使用 **HMAC 簽章**讓商戶端可驗證來源真偽。
- 推送失敗時**自動重試（exponential backoff）**。
- 後台提供**通知歷史查詢**與**手動重發**功能，商戶可自行排查串接問題，不需依賴開發方協助。

### 5.8 報表與稽核
- 儀表板統計、CSV/Excel 交易明細匯出、操作審計日誌（見 5.5）。

### 5.9 手動歸集（Manual Fund Consolidation）

由於各訂單地址皆為獨立衍生地址，USDT 會分散在大量地址中，商戶需要一個方式將其集中到自己的歸集錢包。設計原則：**伺服器端全程不接觸、不儲存私鑰**，簽名動作在商戶自己的瀏覽器內完成。

**流程**
1. 商戶先選擇要歸集哪一個代收主錢包底下的地址（使用中或已停用皆可，見 5.1 代收主錢包變更；若系統僅有一個代收主錢包可省略此步驟直接帶入）。
2. 後台顯示該代收主錢包底下「待歸集地址列表」：列出有餘額的衍生地址、對應索引、餘額金額。
3. 商戶勾選欲歸集的地址（支援批次多選，僅限同一個代收主錢包底下的地址）。
4. 商戶於同一頁面**輸入助記詞/私鑰**，由前端 JavaScript（如 TronWeb SDK）在瀏覽器記憶體中衍生出 xpub，系統先驗證是否與步驟 1 選擇的代收主錢包相符，不符則拒絕並提示重新輸入；相符後才依相同的衍生路徑逐一還原私鑰並完成交易簽名——助記詞/私鑰**不傳送至後端伺服器**，後端資料庫與日誌都不會出現此資料。
5. 瀏覽器將已簽名的交易（可一次多筆）送給後端，後端**僅負責透過第三方 API 廣播上鏈**，並追蹤每筆廣播結果、更新歸集狀態。
6. 每次歸集操作（含選取的代收主錢包、地址、金額、結果）皆記入操作審計日誌。

**助記詞是否留存於瀏覽器**
- 預設**不留存**：每次歸集皆需重新輸入，用畢即由該分頁記憶體清除，將本系統自身程式碼的風險暴露面降到最低。
- 提供商戶**可自行選擇**的「本機加密儲存」選項，UI 以 **checkbox** 呈現（例如「記住此裝置上的助記詞（加密儲存）」），**預設不勾選**；勾選前需彈出明確風險提示（等同將長期金鑰存放責任留在商戶自己的裝置上），商戶確認後才會以自訂密碼加密存於瀏覽器 IndexedDB。

**TRX 手續費（能量/頻寬）處理**
USDT 為 TRC20 智能合約代幣，轉出需消耗「能量」，而各衍生地址預設僅收過 USDT、沒有 TRX 可支付手續費，需商戶自行選擇下列其一（後台皆提供）：
- **手動儲值 TRX**：方向與歸集相反（商戶歸集錢包 → 各子地址），但適用**同一套瀏覽器端簽名原則**——後台提供批次儲值工具，商戶勾選待儲值的子地址、輸入儲值金額，由前端在瀏覽器內用商戶**歸集錢包**的私鑰簽名（同樣不留存於伺服器，留存選項與風險提示邏輯同上），一次可對多個地址送出。
- **串接能量租賃/委託服務**（如 JustLend、TronNRG 等第三方）：向該服務短期租用能量委派給指定地址，免除地址自身持有 TRX 的需求，此方式不涉及商戶私鑰簽名。

> 免責提醒：本功能僅為「輔助簽名與廣播」的工具性設計，商戶助記詞/私鑰之保管、瀏覽器與裝置的資安（防毒、防惡意擴充套件、防釣魚頁面）皆為商戶自身責任，不在本系統防護範圍內（見第 7 節）。

**輸入助記詞頁面的強化要求**
由於此頁面是全系統風險最高的單一頁面（助記詞會直接輸入其中），需盡可能降低頁面本身被植入惡意程式碼的機率：
- 不引入任何第三方腳本、分析工具、CDN 資源。
- 簽名函式庫（如 TronWeb）採離線打包隨系統一併部署，不於執行時從外部來源載入。
- 套用嚴格的 CSP（Content Security Policy），限制頁面可執行的腳本來源。

> 說明：此為降低風險機率的強化措施，無法做到「完全不可能被攻破」，商戶裝置本身的資安仍是其自身責任（見上方免責提醒）。
