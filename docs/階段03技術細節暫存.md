## 開發語言與部署形式：Go + Docker image

**背景**：這不是本次討論才新出現的技術細節，而是階段02技術可行性驗證期間已經拍板、記錄在 [進度.md](進度.md)「階段03 技術選型」的既有決策，這裡整理一份摘要＋具體驗證數據，方便階段03開始時直接引用，不用回頭翻驗證文件。

- **開發語言：Go**。決策依據：[技術可行性驗證.md](技術可行性驗證.md) 定義的三項核心技術假設（HD地址衍生、助記詞/私鑰硬化衍生、TronGrid事件掃描），連同後續新增的驗證項目，都用 Go 在 Docker(Linux) 容器裡重做過一次確認可行，詳見 [評估-Go打包Docker可行性.md](評估-Go打包Docker可行性.md)。相較之下 Swift 路線踩到兩個 Linux 相容性坑、image 高達 378MB。
- **產出形式：Docker image**，multi-stage Dockerfile（builder: `golang:1.25`，runtime: `gcr.io/distroless/static-debian12`），純靜態連結、無 cgo、零系統依賴：
  - 純手刻邏輯（HD地址衍生、助記詞硬化衍生）：image 約 **11.3～11.5MB**
  - 引入 `go-ethereum`（簽名）＋ gRPC 相關依賴（如使用 `gotron-sdk` 這類功能完整的第三方 SDK）：image 約 **26.1MB**，仍屬輕量，權衡點在於「功能完整的SDK」vs「image大小」，選型時需一併考量
- **已知風險**：`golang.org/x/crypto` 等第三方套件的最新版本可能要求較新的 Go 工具鏈版本（實測曾遇到 `golang:1.23` 因套件要求 `go >= 1.25.0` 而建置失敗，換 `golang:1.25` 才成功）——正式環境的 CI/建置環境版本需留意跟進，不能固定用專案起始時的版本
- **amd64 架構尚未驗證**：既有三項驗證都只測過 arm64（開發機架構），若正式環境是 amd64，建議在階段04骨架建置前補驗（此點已記錄在進度.md下一步清單，這裡重複標記避免遺漏）
- 資料庫（PostgreSQL）、前端（Go `html/template` + htmx）、反向代理（不內建）等其餘技術選型的決策依據，維持記錄在 [進度.md](進度.md)「階段03 技術選型」原處，不重複搬移

## 5.9 歸集目的地地址正確性驗證：TronWeb 可用 API

**背景**：需求書 5.9「地址正確性防呆機制」原本寫了「前端即時呼叫 TronWeb `isAddress()`（內部含 Base58Check checksum 驗證）」這種點名具體函式的寫法，經討論後認為這個技術細節程度不該留在需求書（需求書只需寫「系統須驗證地址格式合法性」這種WHAT層級敘述），故將完整技術調查結果搬來這裡保存，需求書已改回抽象敘述。

### Tron 地址編碼機制

- Tron 地址是 **Base58Check** 編碼，結構：`0x41`（前綴 byte）+ 20 bytes 帳戶識別碼 + **4 bytes checksum**，總 25 bytes 再做 Base58 編碼成 34 字元、`T` 開頭的字串。
- Checksum 算法：對前 21 bytes 做兩次 SHA256（`SHA256(SHA256(payload))`），取結果前 4 bytes 附加在後面再編碼——與 Bitcoin Base58Check 同一套機制。
- 理論抓錯率：約 **1 - 1/2³²**（43億分之一漏檢率），能擋掉幾乎所有打錯字/漏字/貼漏段類手誤。
- 來源：[TRON 官方開發文件](https://developers.tron.network/docs/account)、[Base58Check encoding](https://en.bitcoin.it/wiki/Base58Check_encoding)、[OneKey TRC20地址格式說明](https://onekey.so/blog/ecosystem/trc20-address-format-and-verification/)

### TronWeb SDK 可直接使用的驗證 API（讀官方原始碼確認）

| 函式 | 語意 |
|---|---|
| `tronWeb.isAddress(address)` | 綜合驗證入口，接受 hex（42碼，`41`開頭）或 Base58（34碼，`T`開頭）格式，內部走 checksum 驗證路徑，回傳 `boolean`。**前端表單驗證應直接呼叫此函式。** |
| `tronWeb.utils.crypto.decodeBase58Address(base58Str)` | 解碼並驗證 checksum，checksum 不合法時 **throw Error**，適合 try/catch 包住做嚴格驗證 |
| `tronWeb.utils.crypto.decode58Check(addressStr)` | 同樣做 checksum 驗證，但不合法時**回傳 `false`**（非 throw），適合直接用在 `if` 判斷 |
| `tronWeb.utils.crypto.getBase58CheckAddress(addressBytes)` | 反向：從原始 bytes 產生帶 checksum 的 Base58 地址字串（產生地址時用，非驗證時） |
| `tronWeb.address.fromHex()` / `toHex()` | 格式互轉（Base58 ↔ Hex），內部同樣經過 checksum 驗證的解碼路徑 |
| 節點端 RPC `wallet/validateaddress` | 前端驗證完後想再對節點做一次伺服器端二次確認可呼叫此 API |

來源：[TronWeb GitHub 原始碼](https://github.com/tronprotocol/tronweb)（`src/utils/crypto.ts`）、[isAddress 官方文件](https://tronweb.network/docu/docs/API%20List/utils/isAddress/)、[address 工具官方文件](https://tronweb.network/docu/docs/API%20List/utils/address/)、[validateaddress API文件](https://developers.tron.network/reference/validateaddress)

### checksum 抓不到的錯誤類型（架構設計時仍要留意，不是靠 API 呼叫就能解決）

- **Address Poisoning（地址下毒）攻擊**：Tron/USDT-TRC20 生態已知的真實攻擊手法，攻擊者用頭尾相似的假地址零元轉帳污染交易紀錄，誘使受害者之後複製到錯誤地址。已有 5000萬美元真實損失案例。來源：[TRM Labs 分析](https://www.trmlabs.com/resources/blog/understanding-address-poisoning-on-the-tron-blockchain)、[PlasBit 案例分析](https://plasbit.com/research/address-poisoning-attack)
- 這類錯誤 checksum 完全抓不到，需求書已定案的因應方式（UI完整地址分段顯示、要求核對全字串、小額測試操作建議）維持在需求書層級，屬於WHAT，不受本次搬移影響。

## 【待處理】確認數（confirmations_required）改為固定值，不再是商戶可調參數

**狀態：使用者已口頭確認要調整這個需求，但尚未寫回任何正式文件（需求書/技術架構設計都還是舊版）。下一個 session 要做的第一件事，就是把這裡的決策落實寫回去。**

### 討論脈絡（為什麼會有這個決定）

技術架構設計討論「模組5：訂單狀態機」時，審查模組4（鏈上監控）已定案的「確認數達標後再加一段安全緩衝期才停止追蹤reorg」這個設計，發現一個邏輯漏洞：

- 這個緩衝期設計把「商戶自己填的 confirmations_required」跟「Tron 協定自己的 solidified（不可逆，約19個區塊，27個超級代表2/3+1=19）」當成同一件事，但兩者其實不同——如果商戶把確認數設得很淺（例如3、5），達到這個數字完全不代表 Tron 協定意義上的最終確定，緩衝期原本就是想補這個差距。
- 但緩衝期「該加多久」講不出一個有根據的數字，這正是模組4 Gate 卡住的「reorg延伸緩衝期具體數字確定前不得進入開發」那一條。

討論出的解法：**與其發明一個講不出道理的緩衝期數字，不如把「商戶可調確認數」這個參數本身拿掉，改成固定沿用 Tron 協定自己的 solidified 狀態**（技術上就是直接用 TronGrid `only_confirmed=true`，我們驗證項目2已經實測驗證過這個機制），完成判斷不用我們自己再算一次「19 or 20」。

### 決策後果

- **需求書 5.2**：「確認數」要從「可調參數」清單移除，狀態機敘述改成 CONFIRMING→COMPLETED/OVERPAID 由 Tron 協定自身的 solidified 狀態觸發，不是商戶設定值。
- **需求書 5.5**：後台「參數設定頁」移除「確認數」這一項；連帶那句「『確認數』對非技術背景商戶屬陌生術語，UI須輔以白話說明文字...並提供建議預設值」也一併移除（商戶根本不會看到這個設定）。
- **需求書變更紀錄.md**：需新增一筆版本紀錄（緊接 v0.35 之後），完整記錄上面的討論脈絡與拍板理由（沿用本文件既有的寫法慣例）。
- **技術架構設計模組4（鏈上監控）**：拿掉「確認數達標後緩衝期」那段設計；Gate 的兩個卡點（checkpoint安全緩衝N值、reorg延伸緩衝期）簡化成只剩前者，後者已隨這個決策消失。任務3改成直接查 `only_confirmed=true`，不用自己算「目前區塊高度－交易區塊高度」再跟商戶設定的N比較。
- **技術架構設計模組5（訂單狀態機，尚未寫入正式文件，草稿見下）**：拿掉 COMPLETED/OVERPAID → CONFIRMATION_STALLED 這條 reorg 觸發的邊（原因隨緩衝期一起消失）；CONFIRMING→COMPLETED/OVERPAID 判斷條件從「confirmations>=confirmations_required」改成「only_confirmed=true」。
- **技術架構設計模組2（schema）**：`orders` 表「四個參數快照欄位」現在只剩三個（訂單有效期、金額容許誤差百分比、確認等待逾時時間），`confirmations_required` 移除。
- **不受影響、維持不變**：驗證項目9（TronGrid歷史資料保留期限/分頁）仍待執行，跟這個決策無關；金額容許誤差的 `amount_lower_bound`/`amount_upper_bound` 兩個BIGINT快照欄位設計不受影響，仍需補進模組2 schema。

### 模組5：訂單狀態機（internal/order）—— 草稿，已含本次討論修正，尚未寫入正式技術架構設計文件

**這份草稿已經套用審查中發現的另一個獨立 bug 修正**（跟上面的確認數決策無關，是原設計本身的邏輯錯誤）：PENDING→CONFIRMING 的觸發條件原本寫「落在 `[amount_lower_bound, amount_upper_bound]` 即觸發」，會導致付款人一次匯超過金額上限時卡死在 PENDING 直到轉 EXPIRED（跟需求書5.2 EXPIRED「金額仍未達標」的語意矛盾，超額付款明明已達標）。**修正：這裡只看下界 `amount >= amount_lower_bound`，不卡上界**；上界判斷留在 CONFIRMING→COMPLETED/OVERPAID 那一步分流即可。

原始寫入的完整內容（供下個 session 直接引用，動筆寫入正式文件時記得套用上面兩處修正——PENDING→CONFIRMING改下界判斷、拿掉reorg觸發的STALLED邊、confirmations_required改用only_confirmed=true）：

> **原子性做法**：`SELECT ... FOR UPDATE` 交易，不把業務邏輯塞進SQL。放棄「把金額判斷寫進UPDATE的WHERE子句」這個方向（會踩SQL型別/MVCC細節、誤傷手動改判）。改用標準模式：同一個DB transaction內，先 `SELECT * FROM orders WHERE id=? FOR UPDATE` 鎖定該筆訂單列，在Go程式碼內用鎖定期間讀到的一致資料做判斷、決定toStatus，最後在同一交易內UPDATE並COMMIT。
>
> **自動路徑**（task1/task3呼叫）：鎖定後檢查業務條件，條件不成立就直接ROLLBACK不寫入。
> **手動改判路徑**（後台呼叫）：鎖定後只檢查狀態白名單（來源狀態是否允許改判到目標狀態），不重新檢查金額子查詢——操作者的人工查證本來就是要覆蓋系統判斷。兩條路徑共用同一個鎖定/CAS骨架，差別只在要不要多檢查業務條件。
>
> **回傳契約**：鎖定後若狀態不符白名單來源，或（自動路徑）業務條件不成立，一律ROLLBACK並回傳明確原因，不是含糊的「跳過」。自動任務對「狀態衝突」視為正常冪等情況靜默略過；手動路徑一律把任何失敗轉譯成明確錯誤訊息回給操作者。非法轉換嘗試（不在白名單內）記錄到獨立稽核日誌，不混進 `order_state_transitions`。
>
> **容許誤差用預先算好的BIGINT快照欄位**：建立訂單當下（跟其餘參數快照同一時機），直接算出 `amount_lower_bound`／`amount_upper_bound` 兩個BIGINT欄位（USDT最小單位）寫死存證，運算在Go端用int64一次做好。判斷時只需要單純的BETWEEN比較，不重算百分比。（模組2 schema需要小幅補充這兩個欄位。）
>
> **累加金額判斷拆兩條查詢**：
> - PENDING→CONFIRMING：confirmations>=0（只要偵測到、未被判reorg）的原始到帳金額，**≥ amount_lower_bound 即觸發**（修正版：不卡上界），同時寫入 `confirming_at`。
> - CONFIRMING→COMPLETED/OVERPAID：~~confirmations>=confirmations_required~~ **改為 only_confirmed=true** 的已確認金額，落在範圍內轉COMPLETED，超過上限轉OVERPAID。
>
> ~~COMPLETED/OVERPAID → CONFIRMATION_STALLED（reorg觸發，新增邊）~~ **整段移除**：confirmations_required改固定沿用Tron協定solidified狀態後，達標即等同協定最終確定，不再需要這條邊、也不需要 `decision_snapshot`/Webhook payload 的 `previous_status`/`reason` 欄位（原本是為了區分「首次進入STALLED」跟「COMPLETED被reorg打回」，這個情境已經不存在）。
>
> **手動改判寫回資料一致性**：「手動重新檢查此地址」查到的鏈上最新資料寫回 `incoming_transactions`（`(tx_hash, log_index)` 唯一鍵防重複），確保改判後兩張表對得起來。
>
> **稽核可追溯性**：`order_state_transitions` 新增 `decision_snapshot`（JSONB）欄位，記錄觸發轉換當下的聚合金額、目標值、上下界——這點維持不變，跟reorg邊無關，一般稽核用途仍然需要。
>
> **驗收要求**（記錄，供進入階段05開發時的驗收依據）：這些原子交易（尤其容許誤差邊界）需要真實Postgres的整合測試，不能只靠Go單元測試打勾——容許誤差的整數除法bug正是審查才抓到的例子，Go端mock測試永遠測不出這類問題。task3需要「反應式觸發」+「低頻全量重掃」並存（此為模組4文件的小幅補充待辦）。
