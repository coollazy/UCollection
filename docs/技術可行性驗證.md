# 技術可行性驗證（階段 02）

- 對應：[開發流程框架](開發流程框架.html) 階段 02
- 目的：在寫技術架構文件之前，用最小、可丟棄的程式碼驗證架構將要依賴的關鍵假設，避免架構蓋在沒驗證過的猜測上。
- 本文件只定義「驗證什麼、怎樣算通過」，不是設計文件；驗證用的程式碼可丟棄，不必是產品程式碼。
- 這兩項驗證彼此獨立，可分開、依序在不同 session 執行。**風險等級：高**（依 [開發流程框架] 的風險分級，高風險項目的人工核對步驟不可省略——結果需要人親自看過，不能只憑「跑過了」就採信）。

## 驗證項目 1：HD 地址衍生正確性

### 背景

需求書 5.1 節：系統依 BIP32/44 規則，針對商戶提供的 xpub 衍生收款地址，索引只增不減、不重複使用。地址算錯 = 資金可能發到系統認不出的地方，錯誤不會有任何警告或報錯，屬於「靜默失敗」風險。

### 範圍

1. 選定一套用於 Tron 位址衍生的函式庫（例如 TronWeb，或其他確認支援 Tron 位址格式的 HD 衍生函式庫）。
2. 使用 Tron 慣用的衍生路徑 `m/44'/195'/0'/0/{index}`。
3. 用同一組測試 xpub，依序衍生至少 5 個地址（index 0～4）。
4. 對每一個衍生出來的地址，**用第二套獨立工具或方法重新算一次**（例如：換一套不同的函式庫，或用線上已知可信的 Tron HD 錢包工具做交叉核對），確認兩邊結果一致。
5. 確認地址格式正確（Base58Check，以 `T` 開頭）。

### 通過條件（Pass / Fail）

- [ ] 同一組 xpub + index，兩套獨立方法算出的地址**完全一致**（全部 5 組都要對，任一組不一致視為失敗，須查明原因才能算過）。
- [ ] 地址格式驗證通過（可用 Tron 官方位址校驗規則或函式庫內建的校驗函式確認，不是肉眼看格式像不像）。
- [ ] 索引遞增時，衍生出的地址彼此不重複。

### 產出要求

- 驗證用的程式碼（可放在暫存/scratch 目錄，不進正式專案結構）。
- 一份簡短結論：使用的函式庫與版本、測試 xpub 來源（測試用，非真實商戶資料）、5 組 index → 地址的完整對照表、兩套方法是否一致、最終判定通過或失敗。

## 驗證項目 2：TronGrid 測試網事件掃描

### 背景

需求書 5.3 節：主要監控須採區塊/事件掃描（掃描 USDT 合約的 Transfer 事件，比對是否命中系統中的訂單地址），不得逐一輪詢地址。技術選型階段已查證 TronGrid 提供現成的事件索引 API：`GET https://api.trongrid.io/v1/contracts/:address/events`，可用 `event_name=Transfer` 搭配區塊/時間範圍過濾。此次驗證目的是確認這個 API 在測試網環境下真的能可靠抓到轉帳事件，而不是只停留在文件查證階段。

### 範圍

1. 申請 TronGrid 測試用 API Key（免費）。
2. 於 Tron 測試網（Nile 或 Shasta，二擇一，一致即可）取得測試用 TRX（透過官方水龍頭）。
3. 找一個測試網上可用的 TRC20 測試代幣合約（若無現成可用合約，可自行部署一個最簡單的 TRC20 測試代幣，僅供驗證事件掃描用，不需要跟正式 USDT 合約邏輯一致）。
4. 用測試錢包對一個目標地址發送一筆該 TRC20 代幣的轉帳。
5. 呼叫 TronGrid 的 `GET /v1/contracts/:address/events`（`address` 為代幣合約地址），加上 `event_name=Transfer` 過濾，確認能查到剛剛那筆轉帳。
6. 記錄從送出交易到能透過 API 查到事件，實際間隔多久（用來評估之後系統輪詢頻率該怎麼設）。

### 通過條件（Pass / Fail）

- [ ] API 呼叫成功，回傳資料中包含剛才發送的那筆轉帳事件。
- [ ] 事件內容（from、to、金額、合約地址、交易雜湊）與實際發送的交易一致。
- [ ] 記錄到「交易上鏈」到「事件可被查到」的實際延遲時間。
- [ ] 確認 `only_confirmed` 等參數的行為符合預期（例如設為 `true` 時，未達確認數的交易不會出現）。

### 產出要求

- 驗證用的程式碼/腳本（可丟棄）。
- 一份簡短結論：使用的測試網（Nile/Shasta）、測試代幣合約地址、測試交易雜湊、API 回傳的關鍵欄位截圖或原始 JSON、實際延遲時間、最終判定通過或失敗。

## 執行提醒（給接手驗證的 session）

- 這份文件應該足夠自包含，不需要回頭翻對話紀錄即可開始動手。
- 兩項驗證彼此獨立，建議 `/clear` 後開新 session、一次只做一項，避免長對話後期上下文失焦。
- 過程中如果遇到本文件沒預期到的狀況（例如函式庫版本落差、API 行為跟查證時不同），照實記錄下來，不要為了讓結果「看起來通過」而調整判準。
- 完成後把結論回報給使用者，由使用者親自確認再進入下一步（技術架構設計，階段 03）。
