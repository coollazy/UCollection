## 過程

### 1. 瀏覽器衍生私鑰/地址，比對驗證結論-03

在真實 Chrome 分頁用 `hdkey` 衍生 index 0 的私鑰與地址，與驗證結論-03（Node.js/Go 版本）記錄的私鑰、地址完全一致（私鑰不在此處明列，比對邏輯內建在瀏覽器頁面內執行，結果為布林值 `true`，不經過我這邊手動轉抄，降低抄錯風險）。

### 2. 組交易（TriggerSmartContract）

呼叫 TronGrid `POST /wallet/triggersmartcontract`，`function_selector: "transfer(address,uint256)"`，`parameter` 為手動 ABI 編碼的 `(收款方 20-byte 位址左補零至 32 bytes, 轉帳金額 32 bytes)`，金額固定取 **1234567**（6 位小數＝1.234567 USDT，沿用驗證項目 2 刻意取獨特數字方便辨識的做法）。

### 3. 本地重算 txID，核對伺服器回傳值

TronGrid 回傳的 `transaction.txID` 理論上就是 `SHA256(raw_data_hex)`；本次**沒有直接信任伺服器回傳值**，而是用 `@noble/hashes` 的 `sha256` 在瀏覽器本地把 `raw_data_hex` 重新算一次雜湊，逐一比對與伺服器回傳的 `txID` 是否一致——三次執行皆 **完全一致**，簽名前的關鍵人工可核對點通過。

### 4. 本地簽名（SHA256，非 Keccak256）

用衍生出的私鑰，對 `txID`（32 bytes 雜湊）做 ECDSA 簽名，組出 tronweb 內部 `ECKeySign` 用的同一種格式：`r(32 bytes) || s(32 bytes) || v(1 byte, v = recovery + 27)`。

### 5. 簽名後自我核對：反推公鑰/地址

廣播前，用簽名 + txID 反推出簽名者的公鑰、算出對應 Tron 位址，確認等於付款方位址 `TUEZSdKsoDHQMeZwihtdoBiN46zxhGWYdH`——三次執行皆 **完全一致**，證明簽名不只是格式對、確實是用對的私鑰簽出能通過驗證的簽名。

### 6. 廣播 + 鏈上查詢 + 餘額核對

## 過程中的觀察 / 沒有預期到的狀況（本項目踩到的地雷，如實記錄）

驗證項目 6 的背景已經預告「同一個雷區換到瀏覽器 JS 環境很可能重踩一次」，實際執行下來，確實一路踩了好幾個沒預期到的坑，且**每一個都完全符合本文件開頭定義的「靜默失敗」風險模式**——程式碼不會報型別錯誤、簽名函式正常回傳一個看起來格式正確的值，但簽出來的東西是錯的：

1. **`@noble/curves` 2.x 的 `secp256k1.sign()` 預設回傳值不是帶 `.r`/`.s`/`.recovery` 屬性的物件，而是一個 compact 格式的 `Uint8Array`。** 第一版程式碼直接假設回傳值有 `.r.toString(16)`，執行時直接拋出 `TypeError: Cannot read properties of undefined`——這個錯誤至少「有報錯」，容易發現。
2. **要拿到 recovery id，必須明確傳 `{ format: 'recovered' }`，但這個格式的位元組佈局是 `recovery(1 byte) || r(32 bytes) || s(32 bytes)`——recovery byte 在最前面，不是最後面。** 第一直覺（沿用 tronweb 內部 `r||s||v` 的排列方式）會把陣列最後一個 byte 誤當成 recovery id，這裡踩到的後果**不是本地報錯**，而是組出一個 65 bytes、格式上「看起來沒錯」的簽名，實際送去 TronGrid 廣播後才被 Java 全節點的簽名驗證拒絕（`SIGERROR: Header byte out of range: 92`）——直到交易被鏈上節點退回才發現簽名邏輯錯了，這正是「跑得過本地邏輯、簽名格式正確、但簽的東西是錯的」這種靜默失敗風險的具體案例，也是本項目存在的意義：只驗證到「衍生數學正確」（驗證項目 3、4）完全不會發現這一層地雷，只有真的走完整條組交易＋簽名＋廣播路徑才會踩到。
3. **`secp256k1.sign()` 的 `prehash` 選項預設為 `true`**（會對傳入的 message 自動先做一次 SHA256 再簽名）。因為傳入的 `txID` 本身已經是 TronGrid 算好的 `SHA256(raw_data)`，若不明確傳 `{ prehash: false }`，會被再雜湊一次，簽出的是 `SHA256(SHA256(raw_data))` 的簽名——同樣是「簽名函式正常執行、回傳格式正確，但簽錯雜湊」的靜默失敗模式，跟驗證項目 2 的 Go 重驗過程中記錄的 Keccak256/SHA256 混淆是同一類地雷（雜湊演算法選錯/次數用錯，都不會讓程式報錯，只會讓簽名內容不對）。
4. **廣播步驟：瀏覽器 `fetch()` 回報 `TypeError: Failed to fetch`（用戶端網路層失敗），不代表交易真的沒有廣播成功。** 其中一次執行在廣播呼叫時遇到 `fetch` 失敗、程式判定為失敗並中止，但事後用交易雜湊查詢 `wallet/gettransactioninfobyid` 才發現該筆交易其實已經被節點接受並執行成功（`receipt.result: "SUCCESS"`，區塊 `67881786`）——換句話說，**用戶端拿不到 HTTP 回應，不代表伺服器端沒有處理這個請求**，交易可能已經送達、被打包進區塊，只是回應沒有傳回瀏覽器。這一點與交易組建/簽名的正確性無關，但對正式系統的**手動歸集廣播流程設計是重要提醒**：不能把「`fetch` 失敗」直接當成「交易沒發生」去做重試或提示使用者重新操作，否則有可能造成同一筆歸集被重複廣播兩次（本次驗證過程中就因為這個誤判重跑了一次，實際上鏈上多轉了一筆 1.234567 USDT，兩筆交易雜湊都可在 Shasta 鏈上查證：`88871117e98a495a8e589374d6b6acf521da3001fcbf4e02b327eff067688017`、`e10afdcfa93cef133696b708b7c3761b3fd8b41106fdfe61b324d034f9de21b2`）。正式系統的廣播流程必須先用交易雜湊查鏈上狀態確認「真的沒發生」，才能允許重新簽名/重新廣播。
5. **TronGrid 的 `/v1/accounts/{address}` 端點查到的 TRC20 餘額，在交易剛廣播成功、`gettransactioninfobyid` 已回報 `SUCCESS` 的當下立刻查詢，可能還沒反映最新餘額**（本次觀察到廣播後立即查詢，餘額欄位跟廣播前完全相同，等待約 15 秒後重新查詢才反映變化）。這與驗證結論-02 記錄的「事件掃描」延遲是不同層面的問題（那邊是 Transfer 事件索引延遲，這邊是帳戶餘額聚合欄位的索引延遲），若正式系統要在廣播完成後立刻顯示/核對最新餘額，需要把這個延遲也算進等待邏輯裡，不能廣播成功就假設餘額欄位已經同步更新。

## 最終判定：**PASS**

三項通過條件全部符合，且過程中額外用「本地重算 txID」「簽名反推地址自我核對」「獨立 curl 重查鏈上事件與餘額」三層交叉核對，確認瀏覽器端能夠正確完成「助記詞 → 私鑰衍生 → 組建 TRC20 轉帳交易 → 本地 SHA256 簽名 → 廣播上鏈 → 鏈上正確執行」這條完整技術路徑。過程中踩到的地雷（recovery byte 位元組順序、`prehash` 預設值、廣播網路層失敗不代表交易未發生）都已如實記錄在上方，可作為階段 03 技術架構設計中「手動歸集」（5.9）功能簽名/廣播邏輯的直接依據與提醒清單。

## 對階段 03 的提醒

- 正式開發若直接使用 tronweb 而非手刻簽名邏輯，可以避開本次記錄的 1～3 項函式庫 API 地雷（tronweb 內部已經處理好 recovery byte 佈局、prehash 等細節），但**務必先用本項目的方式做一次「反推地址自我核對」再廣播**，不要只信任函式庫回傳「簽名成功」就直接廣播——這是本項目證明有效、成本很低的額外防呆層。
- 手動歸集頁面的廣播失敗處理邏輯，**不能把用戶端網路層錯誤（`fetch` 失敗、逾時）直接等同於「交易未發生」**，必須先用交易雜湊查詢鏈上狀態，確認真的沒有上鏈成功記錄，才能允許使用者重新簽名廣播，否則有重複轉出資金的風險（見上方觀察 4，本次驗證過程中真實發生了一次非預期的重複廣播）。
- 若歸集流程的 UI 需要在廣播後立即顯示「餘額已更新」，需另外處理 TronGrid 帳戶餘額查詢的索引延遲（見上方觀察 5），不能廣播成功後立刻查詢餘額就假設數字已經同步。
