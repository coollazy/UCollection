## 1. 產品定位

UCollection 是一套 **USDT(TRC20) 代收服務套件**，以 Docker image 形式交付給個別商家/企業買家自行部署運行，而非由開發方營運的雲端服務。

商戶需將 UCollection 與自身既有的訂單系統整合（透過對外 API 建單、接收 Webhook 通知），由 UCollection 專責處理代收流程本身（收款地址生成、鏈上入帳監控、訂單狀態判定）；商戶自己的商品/交易邏輯不在 UCollection 範圍內。

核心設計原則：

- **僅負責代收功能面**：UCollection 不是完整的訂單/交易系統，而是嵌入商戶既有系統的代收服務，透過 API 建單、Webhook 通知結果。
- **不經手資金、不儲存私鑰**：系統僅使用商戶提供的錢包 **xpub（擴充公鑰）**，以 HD（分層確定性）方式為每筆訂單衍生獨立收款地址，全程無法動用商戶資金；助記詞/私鑰全程不經過系統內部。
- **單租戶架構**：一套部署對應一個商戶，不做多租戶/子商戶管理。
- **純軟體工具定位**：不內建 KYC/AML、不代為處理法幣結算，合規責任由使用本軟體的商戶自行承擔（見第 9 節免責事項）。

## 2. 名詞定義

| 名詞 | 定義 |
|---|---|
| 商戶 | 購買並自行部署本軟體的企業/個人買家，本系統的後台操作者 |
| 付款人 | 商戶的終端客戶，實際完成 USDT 轉帳的人 |
| 代收主錢包 | 商戶於後台設定、用來衍生每筆訂單收款地址的錢包（技術上即一組 xpub）；系統僅保存其公鑰，不接觸對應私鑰／助記詞；同一時間僅一個「使用中」，可變更/恢復（見 5.1） |
| xpub | 代收主錢包對應的擴充公鑰（BIP32/44 標準），系統依此衍生收款地址；本身無法反推出對應私鑰，僅作為需求書內部技術說明用詞，不對商戶顯示（見 5.1） |
| 歸集錢包 | 商戶手動歸集時指定的資金最終目的地地址，是系統外部、不受代收主錢包 HD 衍生樹管轄的地址，與代收主錢包是否為同一組錢包由商戶自行決定（見 5.9） |
| 歸集地址簿 | 後台維護的歸集錢包地址清單（含商戶自訂名稱），供商戶重複選用、避免每次手動輸入產生手誤（見 5.9） |
| 訂單 | 一次收款請求，對應一個獨立衍生地址、一個目標金額與一個生命週期 |
| 前台 | 付款人看到的收銀頁面（顯示收款地址/QR code/倒數/狀態） |
| 後台 | 商戶登入使用的管理介面 |

## 3. 系統範圍

**In scope**

- USDT-TRC20 單一鏈別的收款地址生成、鏈上入帳監控、訂單狀態判定
- 對外 API（供商戶自身系統整合建單）＋ 後台手動建單
- Webhook 通知（含簽章、重試、查詢、手動重發）
- 前台收銀頁、後台管理介面（單一帳號 + 2FA）
- 報表、CSV/Excel 匯出、操作審計日誌
- Docker/docker-compose 一鍵部署
- **手動歸集功能**：瀏覽器端簽名協助商戶將分散於各衍生地址的 USDT 集中到歸集錢包（詳見 5.9），伺服器全程不接觸私鑰

**Out of scope（本版不做）**

- 多租戶/子商戶架構
- **伺服器端私鑰託管、自動化背景歸集**（歸集僅限手動觸發＋瀏覽器端簽名，見 5.9）
- **代商戶對外之出款/提領/代付功能**：即代商戶將資金付給非商戶自己所有之第三方錢包。（商戶將收款地址資金歸集回自己歸集錢包的手動操作，受益人始終是商戶本人，性質為內部資金管理，**不屬於此排除項**，已於 5.9 列為 in-scope）
- 法幣金額換算、匯率風控
- KYC/AML 身分驗證、風控名單篩查
- License Key 防盜版機制（已確認不做，若未來銷售量變大、盜版轉賣成為實際問題，可留作 Phase 2 待辦重新評估）
- 除 TRC20 以外的鏈別
- **系統監控告警**：鏈上監控中斷、輪詢異常、Webhook 持續失敗等情況本版不做自動偵測與主動通知，商戶需自行透過後台查看狀態（已確認不做，可留作 Phase 2 待辦）
- **資料備份與復原機制**：本版不內建備份/還原工具，資料保護（含防止硬碟損毀導致地址-訂單對應遺失）由商戶自行於部署環境負責（已確認不做，可留作 Phase 2 待辦）
- **手動歸集之能量委託/租賃機制**：5.9 手續費處理本版僅提供直接支付 TRX（見 5.9 選項 A），委託能量或第三方租賃能量（見 5.9 選項 B）已確認不做，可留作 Phase 2 待辦

## 4. 使用者與角色

- **商戶（單一管理帳號）**：登入後台，可設定代收主錢包、查看/建立訂單、調整參數、查通知紀錄、匯出報表、查審計日誌。登入需 2FA（TOTP）。
- **商戶的外部系統**：透過 API Key + HMAC 簽章呼叫建單/查詢 API，接收 Webhook 通知。
- **付款人**：無帳號，透過前台收銀頁完成付款，不接觸後台。

> 本版不設多角色權限分級（無老闆/財務/客服之分），單一管理帳號即可。

## 5. 功能需求

### 5.1 收款地址管理
- 商戶於後台設定**一個代收主錢包**（技術上即一組 xpub，用來衍生每筆訂單的收款地址；下稱「代收主錢包」，UI 與商戶溝通一律用此名稱，不直接顯示 xpub 字樣）。
- 系統依 BIP32/44 規則，針對代收主錢包的下一個索引衍生新地址；索引**只增不減、不重複使用**。**此規則的計數範圍是單一代收主錢包，不同代收主錢包各自獨立維護自己的索引序列**（因為不同代收主錢包是不同 xpub、不同 HD 樹的根，同樣的索引在不同代收主錢包底下衍生出的地址本來就完全不同，不需要、也不應該共用同一個全域序號）：全新（從未用過）的代收主錢包，索引從自己的 1 開始算；一個原本用過、後來停用、又被「恢復使用中」的代收主錢包（見下方「代收主錢包變更」），接續它自己原本用到的地方繼續往上加，不會重設回 1，也不會接續其他代收主錢包的序號。
- **索引從 1 開始分配給訂單，index 0 永遠不分配給任何訂單，不論代收主錢包是透過下方哪一種方式取得。** 因為 index 0（`.../0/0`）是業界慣例上任何標準錢包工具匯入同一組助記詞都會顯示的「預設地址」——對方式 1（商戶既有助記詞）而言，這個地址很可能是商戶原本就在使用、已有真實餘額與交易紀錄的日常地址；對方式 2（系統產生新錢包）而言，這個地址則是任何工具事後查詢都會顯示的預設位置。若拿去當某張訂單的收款地址，會與商戶原有的資金活動混淆，或造成不同工具看到的地址身分衝突。**index 0 保留、系統不賦予任何用途**（不分配訂單、不作系統內部用途、後台也不特別顯示）：方式 1（商戶既有助記詞）的 index 0 可能已是商戶日常在用的地址；方式 2（系統產生新錢包）雖然助記詞是系統產生，但商戶取得後可自行拿去匯入其他錢包工具當一般錢包使用，屆時 index 0 一樣會是那些工具顯示出來的預設地址——兩種方式都無法排除 index 0 與商戶自身其他資金活動的關聯，因此一律不賦予任何系統用途，單純跳過。
- 地址與訂單為**永久一對一綁定**，即使訂單已結束/逾時，該地址永遠不會分配給其他訂單。

#### 代收主錢包取得方式

取得代收主錢包（xpub）的方式受限於一項技術背景：Tron 是帳戶模型鏈，主流 Tron 錢包普遍不支援匯出帳戶層級 xpub（這點與 Bitcoin 生態不同，Trezor/Ledger/Electrum 等 Bitcoin 錢包普遍支援匯出 xpub）；地址、一般格式的私鑰皆無法反推出 xpub（缺少 xpub 必需的 chain code），能穩定推出可用 xpub 的來源是**助記詞（或風險等級相同的擴充私鑰 xprv／原始 seed，實務上商戶僅會操作助記詞）**。市場上查無「商戶直接輸入既有 xpub」的實務可行取得管道（詳見 [進度.md](進度.md)），因此後台的「新增代收主錢包」功能僅提供以下兩種方式：

1. **商戶於瀏覽器端輸入既有助記詞**：由系統前端在瀏覽器本地計算出對應 xpub，助記詞**不上傳、不經過後端、不落地**。輸入後系統先驗證**助記詞格式合法性**（字數符合 BIP39 規範、每個字皆在 BIP39 字典內、checksum 位元正確），驗證不過則拒絕並顯示明確錯誤，不繼續衍生；商戶可直接修改後**重新送出再次驗證**，次數不限。
2. **商戶使用系統提供的「產生錢包」功能**：瀏覽器端隨機產生一組新助記詞，顯示一次供商戶抄下。顯示後，比照 TronLink 做法，要求商戶依序點選重建完整助記詞以驗證備份正確；驗證通過才計算 xpub 送給後端，助記詞同樣**不上傳、不落地**；驗證不通過可返回重新查看助記詞再試一次。

> 商戶完成上述設定後，**需妥善保管所使用的助記詞**：5.9 手動歸集時，系統會要求商戶重新輸入同一組助記詞以還原各子地址私鑰、簽署歸集交易。助記詞遺失不影響鏈上資金安全，但商戶將永久喪失對該代收主錢包底下已收款、尚未歸集餘額的存取能力。

**安全規格**（方式 1、2 共用，與 5.9 手動歸集頁面相同等級，非獨立另訂規則）：
- 此頁面不引入任何第三方腳本/CDN/分析工具。
- 使用的助記詞/xpub 衍生函式庫需離線打包隨系統一併部署，不於執行時從外部來源載入。
- 套用嚴格 CSP，限制頁面可執行的腳本來源。
- 選擇方式 1（輸入既有助記詞）時，需先顯示明確風險提示：「此助記詞的安全性將與本系統綁定，建議使用專門的收款用助記詞，避免使用日常錢包的助記詞」，商戶確認後才可繼續輸入。

#### 代收主錢包變更

商戶可於後台變更代收主錢包（見 5.5）。變更語意採**「舊代收主錢包停止分配新訂單，但不代表舊地址／資金失效」**（市調 BTCPay Server、Blockonomics 皆採此語意：換 xpub 是解除追蹤關係，非讓舊地址作廢，詳見 [進度.md](進度.md) 市場調查筆記）：

**資料模型**
- 系統記錄商戶每一個曾經設定過的代收主錢包（xpub 值、狀態：使用中／已停用、啟用/停用時間）。同一時間只有一個「使用中」，新訂單一律綁定使用中的那個。**代收主錢包與商戶的「歸集錢包」（歸集目的地帳戶，見 5.9）是不同概念，不可混用**：代收主錢包是「系統依何組公鑰衍生訂單地址」的來源，歸集錢包是「歸集後資金最終去向」。
- 每張訂單記錄其收款地址衍生自哪一個代收主錢包。

**變更行為**
- 商戶送出新代收主錢包後，原本使用中的那個轉為「已停用」，但**已停用代收主錢包底下已分配的地址持續受 5.3 鏈上監控**，直到其下所有訂單皆走到終態（COMPLETED／OVERPAID／CONFIRMATION_STALLED／EXPIRED，見 5.2）為止，確保變更當下的進行中訂單不受影響。
- 已停用代收主錢包底下地址若仍有餘額，商戶仍可透過 5.9 手動歸集取回，不因停用而失去存取能力（只要商戶保留對應助記詞）。
- 提供**「恢復使用中」**操作：商戶可將任一已停用的代收主錢包重新設回「使用中」（系統已儲存其 xpub，**不需重新輸入助記詞**）；恢復後，原本「使用中」的那個依上述規則自動轉為「已停用」（同一時間僅一個使用中的規則不變），新訂單自此改綁定被恢復的那個。

**防呆機制**
- **重複 xpub 阻擋**：商戶送出新代收主錢包時，系統須比對算出的 xpub 是否與任一歷史代收主錢包（不論使用中或已停用）完全相同；若相同，**拒絕送出**並提示商戶改用「恢復使用中」重新啟用該筆既有紀錄，不需要（也不允許）重新輸入同一組助記詞建立成一筆新紀錄，避免衍生地址空間重疊、造成兩筆代收主錢包紀錄實際指向同一組公私鑰的混亂狀態。
- **確認提示**：「送出新代收主錢包」與「恢復使用中」這兩個操作，因為都會讓目前使用中的代收主錢包自動轉為已停用、後續新訂單改綁到別的代收主錢包，屬於影響全系統的重大設定變更，送出前需彈出確認對話框，明確告知「目前使用中的代收主錢包將轉為已停用，此後新訂單將改用另一個代收主錢包衍生地址」，商戶按下確認後才正式生效。

**與手動歸集的關聯**
- 5.9 手動歸集操作**一次只能對應一個代收主錢包**（不論使用中或已停用）：商戶先選擇要歸集哪一個代收主錢包底下的地址，輸入對應助記詞後，系統驗證衍生出的 xpub 與該代收主錢包相符才放行，避免混淆助記詞或跨代收主錢包混合歸集（降低多組助記詞同時暴露於同一瀏覽器 session 的風險）。

### 5.2 訂單管理

**建立方式**
- 商戶外部系統可呼叫建單 API（金額以 USDT 直接指定，不做法幣換算；須提供商戶訂單編號，見 5.6）。
- 後台亦提供手動建單功能，方便測試與人工收款情境。

**訂單狀態機**

```
PENDING（等待付款，全速監控）
  → CONFIRMING（累計入帳金額達目標容許誤差範圍，等待達到確認數）
    → COMPLETED（達確認數，金額在容許誤差內）
    → OVERPAID（達確認數，金額超過容許誤差上限 → 人工處理）
    → CONFIRMATION_STALLED（超過「確認等待逾時時間」仍未達確認數 → 標記異常，通知商戶，人工處理）
  → EXPIRED（訂單有效期到期，累計入帳金額仍未達標，不論是 0 元或部分金額 → 停止自動監控，人工處理）
```

**可調參數與快照**
- **確認數、訂單有效期（逾時時間）、金額容許誤差百分比、確認等待逾時時間**皆為可調參數，商戶後台有獨立的參數設定頁，可設全域預設值。
- **參數快照**：訂單建立當下，將當時生效的上述四項參數值各自記錄成該筆訂單專屬的快照。商戶之後在參數設定頁調整全域預設值，**只影響之後新建立的訂單**，不會回頭改變任何已經建立、正在監控中的舊訂單所使用的數值。

**金額判斷（累加制）**
- **金額判斷採累加制**：同一收款地址在該筆訂單監控期間內，可能收到不只一筆入帳交易（例如付款人分批匯款）。系統持續累加該地址**所有已達確認數**的入帳交易金額，以累計總額判斷是否達標，不是只看單一筆交易的金額。

**CONFIRMING 階段規則**
- 訂單一旦進入 **CONFIRMING**（累計金額已達目標容許誤差範圍），即**不再受訂單有效期（逾時時間）限制轉為 EXPIRED**：即使等待確認的時間已超過原訂單有效期，訂單仍留在 CONFIRMING、持續等待確認數達標，直到達標進入 COMPLETED/OVERPAID 為止，或觸發下方的確認逾時規則。
- **確認等待逾時**：CONFIRMING 另有獨立的可調參數「確認等待逾時時間」；**商戶未特別設定時，預設值與「訂單有效期（逾時時間）」相同**。若訂單進入 CONFIRMING 後，超過此時間仍未達到目標確認數，系統將其標記為 **CONFIRMATION_STALLED**（確認逾時異常），停止自動等待、透過 Webhook 通知商戶，交由商戶於後台人工處理（例如透過「手動重新檢查此地址」功能查詢鏈上最新狀態，確認交易其實是否已達標、或該交易已從鏈上消失需等待付款人重新付款）。此規則涵蓋確認數設定過高、鏈上資料來源異常延遲、交易因鏈上因素消失等各種造成 CONFIRMING 無法收斂的情況；系統不主動判斷根本原因，一律先標記異常交由商戶決定後續處置，具體技術判斷邏輯留待階段03架構設計。

**EXPIRED 規則**
- **訂單有效期到期時，若累計金額仍未達到目標容許誤差範圍（不論是完全沒收到任何入帳，還是收到部分金額），一律轉為 EXPIRED**：不因「有無收到部分款項」而區分成不同狀態，商戶可從訂單明細直接看到實際已收金額。
- **本版不設寬限期低頻監控**：訂單一到期即為終態，系統停止自動輪詢；後台**永久保留「手動重新檢查此地址」功能**（因區塊鏈地址本身永久有效，隨時可能收到延遲到帳的款項），商戶可隨時自行查詢鏈上最新狀態並決定後續操作。

**手動改判**
- 商戶可依「手動重新檢查此地址」查得的鏈上最新狀態，將 CONFIRMATION_STALLED 或 EXPIRED 手動改判為 COMPLETED 或 OVERPAID（依實際入帳金額決定改判目標）。改判視為訂單進入新狀態，依 5.7 規則觸發對應 Webhook 通知；**訂單曾經歷過的狀態（例如曾經 EXPIRED）須完整保留於審計日誌，不因後續改判而覆蓋或刪除**，確保商戶事後可回溯這筆訂單完整的狀態變更歷程（見 5.5）。
- OVERPAID、CONFIRMATION_STALLED、EXPIRED 皆**不自動退款或補收**，系統僅標記狀態並保證通知商戶（見 5.7），由商戶自行於後台人工處理（可透過「手動重新檢查此地址」查證後手動改判，見上方說明）。

**不提供訂單取消**
- **訂單不提供主動取消/作廢功能**：訂單僅能透過訂單有效期到期自然轉為 EXPIRED 結束，系統不提供商戶手動關閉一筆 PENDING 訂單的操作。理由：訂單有效期通常設定不長，逾時即直接進入終態，等待自然到期的成本很低；且區塊鏈收款沒有信用卡「預先授權後取消」的概念，付款人不轉帳，訂單本來就不會有任何資金異動，沒有主動取消的實質必要。商戶若手動建錯單，等待自然逾時即可，不影響其他訂單或功能運作。

### 5.3 鏈上監控
- 資料來源：**Tron 官方維運的公開閘道（如 TronGrid）為主，可搭配 TronScan 等獨立第三方 API 作為備援**，不提供自架全節點選項（降低商戶部署門檻）。
- 監控頻率：訂單有效期內全速輪詢；到期後（轉 EXPIRED，見 5.2）停止自動輪詢，改為後台「手動重新檢查此地址」功能觸發。
- **主要監控**須採**區塊/事件掃描**（掃描 USDT 合約的轉帳事件，比對是否命中系統中的訂單地址），**不得**採「逐一輪詢每個地址」的方式。原因：後者的 API 呼叫量會隨監控中地址數量線性增加，訂單量一大就容易超出第三方 API 的免費/速率額度，前者的呼叫量只跟區塊產生速度有關，與地址數量無關，具備規模化能力。
- 此限制僅適用於主要監控（即時、持續、覆蓋所有進行中訂單）。**備援/降級監控情境不在此限**，因當下需輪詢的僅為進行中訂單（有界集合），且可接受降頻，逐一查詢地址並非不可行，實際方式屬技術設計階段決定。

### 5.4 前台（付款人收銀頁）
- 顯示：收款地址、對應 QR code、應付 USDT 金額、剩餘有效時間倒數、目前訂單狀態。
- 無需付款人登入或提供個資。

### 5.5 後台（商戶管理介面）

**儀表板與訂單**
- 儀表板：總收款金額、待處理訂單數、異常訂單數等統計。
- 訂單列表：**建立**、查詢、篩選、明細檢視（手動建單見 5.2）。

**代收主錢包設定**
- 代收主錢包設定：設定/變更/**恢復使用中**代收主錢包，並可查看歷史所有代收主錢包與其狀態（使用中／已停用；狀態旁需輔以說明文字，避免商戶誤解「已停用」代表資金不安全或無法取回——變更語意見 5.1）。
- **商戶首次登入且尚未設定任何代收主錢包時**，後台需引導其優先完成本項設定；在此之前，依賴代收主錢包的功能（建立訂單、手動歸集等）不可用，具體引導畫面留待介面設計階段處理。

**手動歸集相關**
- **手動歸集操作**：執行一次歸集（代收主錢包/地址選擇、歸集地址簿選擇或手動輸入目的地地址、助記詞輸入與簽署、廣播與結果追蹤，見 5.9）。
- **TRX 手續費工具**：將 TRX 轉入待歸集子地址供其支付手續費，可選用代收主錢包或商戶指定的任意錢包簽名轉出（見 5.9 選項 A；能量委託/租賃本版不做，見第3節 Out of scope）。
- 歸集地址簿管理：新增/編輯（僅限改名）/刪除歸集目的地地址，上限 30 筆（見 5.9）。

**對外整合設定**
- **API Key 管理**：查看/重新產生供 5.6 API 認證使用的 API Key。
- **Webhook 端點設定**：設定/測試 5.7 通知要推送的目標網址與簽章密鑰。

**參數設定**
- 參數設定頁：確認數、訂單有效期（逾時時間）、金額容許誤差百分比、**確認等待逾時時間**（可留空，留空時預設沿用「訂單有效期（逾時時間）」的數值，見 5.2）。
- **「確認數」對非技術背景商戶屬陌生術語，UI須輔以白話說明文字（例如「區塊確認數：數字越高越安全但等待入帳時間越長」）並提供建議預設值**，其餘各項為商戶熟悉的一般業務概念，無此疑慮。

**通知、稽核與匯出**
- 通知紀錄查詢與手動重發（見 5.7）。
- 操作審計日誌：記錄商戶所有操作歷程，**含設定變更與歸集等交易性操作**（見 5.9），以及**訂單完整狀態變更歷史**（含手動改判前曾經歷過的狀態，見 5.2，不因後續改判而覆蓋或遺失）。
- 交易明細 CSV/Excel 匯出。

**帳號安全**
- 單一管理帳號登入，強制 2FA（TOTP）。

### 5.6 API（供商戶外部系統整合）
- **建單 API**：商戶外部系統呼叫建立訂單，**須提供「商戶訂單編號」（必填，商戶自己系統的訂單參照字串）**，用於後續對帳與查詢。此欄位同時具備**冪等性**：同一個商戶訂單編號重複呼叫，系統不建立新訂單，直接回傳原本已建立的那筆訂單；若同一編號重複呼叫但夾帶的其他參數（例如金額）與原本不同，視為衝突，拒絕請求並回傳錯誤，避免商戶因網路逾時重試而不小心建出多筆訂單、各自佔用一個收款地址。
- **訂單查詢 API**：可用系統自己產生的訂單 ID，或商戶提供的「商戶訂單編號」查詢訂單狀態與明細（若建單當下網路異常導致商戶未收到系統回傳的訂單 ID，仍可用自己的編號查得到）。
- 認證方式：**API Key + HMAC 簽章**（與 Webhook 簽章機制一致）。

### 5.7 Webhook 通知
- **每次訂單進入 COMPLETED、OVERPAID、CONFIRMATION_STALLED、EXPIRED 這四個終態（見 5.2）的任何一個，都會主動推送一次通知**給商戶指定端點，不因終態原因不同而省略。多數訂單一輩子只會進入其中一個終態，因此只收到一次通知；但若商戶後續透過「手動重新檢查此地址」將 CONFIRMATION_STALLED 或 EXPIRED 改判為 COMPLETED 或 OVERPAID（見 5.2「手動改判」），改判視為新一次的終態進入，會再觸發一次通知。CONFIRMING（等待確認中）**不觸發**通知。
- 通知內容須包含**商戶訂單編號**（見 5.6），供商戶比對其系統內部的訂單記錄。
- 使用 **HMAC 簽章**讓商戶端可驗證來源真偽。
- 推送失敗時**自動重試（exponential backoff）**。
- 後台提供**通知歷史查詢**與**手動重發**功能，商戶可自行排查串接問題，不需依賴開發方協助。

### 5.8 報表與稽核
- 儀表板統計、CSV/Excel 交易明細匯出、操作審計日誌（見 5.5）。

### 5.9 手動歸集（Manual Fund Consolidation）

由於各訂單地址皆為獨立衍生地址，USDT 會分散在大量地址中，商戶需要一個方式將其集中到自己的歸集錢包。設計原則：**伺服器端全程不接觸、不儲存私鑰**，簽名動作在商戶自己的瀏覽器內完成。

**流程**
1. 商戶先選擇要歸集哪一個代收主錢包底下的地址（使用中或已停用皆可，見 5.1 代收主錢包變更；若系統僅有一個代收主錢包可省略此步驟直接帶入）。
2. 後台顯示該代收主錢包底下「待歸集地址列表」：列出有餘額的衍生地址、對應索引、餘額金額、**該地址對應訂單的原定目標金額**。若某地址對應訂單已是 COMPLETED，但查得的實際餘額超過原定目標金額，需額外標示提醒（例如「餘額超出訂單原定金額」），供商戶自行判斷是否為訂單完成後才發生的額外入帳。
   > **已知風險與限制（不主動偵測）**：本機制只能發現「尚未歸集過」的地址上有異常餘額。**一個地址若已完成過歸集（餘額歸零），系統之後不會再持續監控該地址**；若之後又有新的入帳進入這個已歸集完成的地址，系統不會主動偵測、不會標示、也不會通知商戶，該地址也不會因此重新出現在「待歸集地址列表」中。這筆資金仍安全存在於鏈上、並未遺失，但商戶需自行透過區塊鏈瀏覽器或其他工具查證才會發現。之所以不做主動偵測：持續監控所有歷史地址（不論是否已歸集過）需要對商戶名下曾經衍生過的全部地址反覆查詢餘額，隨著訂單量累積，查詢量會失去規模化能力（不同於 5.3 主要監控依賴的事件掃描機制），本版評估後不採用，列為已知限制。
3. 商戶勾選欲歸集的地址（支援批次多選，僅限同一個代收主錢包底下的地址）。
4. 商戶決定**歸集目的地地址**（即歸集錢包地址）：可從**歸集地址簿**（見下方）選擇既有地址，或手動輸入一個新地址。**地址正確性防呆機制**：
   - 系統須於前端即時驗證地址**格式合法性**，不合法立即拒絕並提示，不允許送出（可用技術手段擋掉絕大多數打錯字/漏字/貼漏段類手誤，具體技術方案留待階段03架構設計，見 [階段03技術細節暫存.md](階段03技術細節暫存.md)）。此機制無法辨別「格式合法但不是商戶真正想要的地址」（例如貼錯剪貼簿內容、Address Poisoning 誘騙式假地址攻擊，詳見 [進度.md](進度.md) 調查筆記）。
   - UI 顯示完整地址並**分段呈現**（例如每 4～5 碼加空格），要求商戶核對**全字串**，而非僅頭尾幾碼（僅核對頭尾容易被 Address Poisoning 這類頭尾相似的誘騙地址欺騙）。
   - **操作建議（UI 文案引導，非系統強制流程）**：若使用從未歸集過的新地址，建議商戶先在步驟3**只勾選一個小額地址**單獨完成一次歸集，自行至區塊鏈瀏覽器或自己的錢包確認實際入帳無誤後，再另外發起一次歸集操作、勾選其餘地址批次送出。此建議直接沿用步驟2、3既有的「顯示所有可歸集地址與金額、商戶自由勾選單選/多選」能力達成，不需要系統另外設計分階段簽名/廣播機制。
5. 商戶於同一頁面**輸入助記詞/私鑰**，由前端 JavaScript（如 TronWeb SDK）在瀏覽器記憶體中衍生出 xpub，系統先驗證是否與步驟 1 選擇的代收主錢包相符，不符則拒絕並提示重新輸入；相符後才依相同的衍生路徑逐一還原私鑰並完成交易簽名——助記詞/私鑰**不傳送至後端伺服器**，後端資料庫與日誌都不會出現此資料。
6. 瀏覽器將已簽名的交易（可一次多筆）送給後端，後端**僅負責透過第三方 API 廣播上鏈**，並追蹤每筆廣播結果、更新歸集狀態。
7. 每次歸集操作（含選取的代收主錢包、地址、目的地地址、金額、結果）皆記入操作審計日誌。

**歸集地址簿**
- 後台提供獨立管理頁面（見 5.5），商戶可自行**新增／編輯（僅限改名，地址值本身建立後不可修改）／刪除**歸集地址簿裡的項目；如需更換地址，刪除該筆後重新新增。此為 v0.10 決策的修正：v0.10 原定案「歸集目的地地址不預先於後台設定/儲存」，經重新考量操作便利性與降低重複輸入的手誤風險後，改為提供地址簿——但商戶仍可選擇每次都手動輸入新地址，系統不強制使用地址簿。
- **地址不可重複**：手動新增時若地址已存在地址簿中，拒絕新增並提示「此地址已存在」；商戶於步驟4**手動輸入的新地址**，只要該次歸集**廣播成功**，系統即自動將該地址存入地址簿（若該地址已存在則不重複新增，保留原有名稱），**預設給一個系統產生的名稱，須帶有可辨識資訊**（例如「2026-08-30 新增（...末4碼）」，結合建立日期與地址末幾碼，避免商戶事後在一長串「地址簿#1、#2、#3」之類的清單中無法分辨對應哪次操作），商戶可事後至地址簿管理頁面重新命名，不要求歸集當下立即命名。
- **地址簿數量上限 30 筆**：達上限後，新增（含歸集成功後的自動存檔）皆會被跳過，但**不影響歸集操作本身**——商戶仍可正常對任一地址完成歸集，只是該地址不會被存進地址簿；商戶需先刪除既有項目才能再新增。
- 地址簿項目被刪除或改名，**不影響過去已完成歸集的審計日誌**：日誌保留當次歸集送出當下的地址原文與（若有）當時的名稱快照，不因地址簿事後異動而回溯改變歷史紀錄。

**助記詞是否留存於瀏覽器**
- 預設**不留存**：每次歸集皆需重新輸入，用畢即由該分頁記憶體清除，將本系統自身程式碼的風險暴露面降到最低。
- 提供商戶**可自行選擇**的「本機加密儲存」選項，UI 以 **checkbox** 呈現（例如「記住此裝置上的助記詞（加密儲存）」），**預設不勾選**；勾選前需彈出明確風險提示（等同將長期金鑰存放責任留在商戶自己的裝置上），商戶確認後才會以自訂密碼加密存於瀏覽器 IndexedDB。

**TRX 手續費（能量/頻寬）處理**
USDT 為 TRC20 智能合約代幣，轉出需消耗「能量」，而各衍生地址預設僅收過 USDT、沒有 TRX 可支付手續費。商戶於歸集操作時，須選擇手續費支付來源，並可**每次歸集操作各自重新選擇**（不綁定帳號層級固定一種）：

- **A. 支付 TRX**（本版交付範圍）：由指定錢包直接轉一筆 TRX 進待歸集的子地址，供其自行支付手續費。
  - **A1　用代收主錢包內的 TRX 支付**：商戶需自行先將 TRX 轉入代收主錢包，由代收主錢包簽名批次轉出至待儲值的子地址。
  - **A2　商戶提供任意錢包支付**：商戶指定另一個內有 TRX 餘額的錢包（不限代收主錢包或歸集錢包），由該錢包簽名批次轉出至待儲值的子地址。
- **B. 支付能量**（已確認不做，留作 Phase 2 待辦）：由能量來源委託能量給待歸集的子地址，子地址轉帳時消耗被委託的能量、不需自行持有 TRX。本版不開發，待 Phase 2 視需求再評估以下三個方向：
  - B1　代收主錢包委託能量（需質押 TRX 換取可委託能量）
  - B2　輸入專用能量委託錢包
  - B3　第三方能量租賃服務

A1、A2 採用同一套瀏覽器端簽名原則：私鑰/助記詞不留存於伺服器，留存選項與風險提示邏輯同「助記詞是否留存於瀏覽器」一節。

> 免責提醒：本功能僅為「輔助簽名與廣播」的工具性設計，商戶助記詞/私鑰之保管、瀏覽器與裝置的資安（防毒、防惡意擴充套件、防釣魚頁面）皆為商戶自身責任，不在本系統防護範圍內（見第 7 節）。

**輸入助記詞頁面的強化要求**
由於此頁面是全系統風險最高的單一頁面（助記詞會直接輸入其中），需盡可能降低頁面本身被植入惡意程式碼的機率：
- 不引入任何第三方腳本、分析工具、CDN 資源。
- 簽名函式庫（如 TronWeb）採離線打包隨系統一併部署，不於執行時從外部來源載入。
- 套用嚴格的 CSP（Content Security Policy），限制頁面可執行的腳本來源。

> 說明：此為降低風險機率的強化措施，無法做到「完全不可能被攻破」，商戶裝置本身的資安仍是其自身責任（見上方免責提醒）。

## 6. 非功能需求

| 項目 | 需求 |
|---|---|
| 部署方式 | Docker / docker-compose 一鍵部署，附完整部署文件 |
| 介面語言 | 雙語（繁體中文 / 英文），可切換 |
| 登入安全 | 單一管理帳號 + 強制 2FA（TOTP） |
| 授權機制 | 不做 License Key，交付原始碼與部署包 |
| 資料保存 | 訂單、地址對應、審計日誌需永久保存，不可刪除歷史地址對應關係 |
| 架構彈性 | 鏈上資料來源需做成可替換的介面層，為未來擴充留餘地（本版仍固定串接第三方 API） |
| 私鑰處理 | 歸集簽名僅於前端瀏覽器記憶體中瞬時使用；預設不持久化，商戶可自行選擇啟用本機加密儲存（見 5.9） |
