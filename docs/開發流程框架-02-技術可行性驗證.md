# 技術可行性驗證（階段 02）

- 對應：[開發流程框架](開發流程框架.html) 階段 02
- 目的：在寫技術架構文件之前，用最小、可丟棄的程式碼驗證架構將要依賴的關鍵假設，避免架構蓋在沒驗證過的猜測上。
- 本文件只定義「驗證什麼、怎樣算通過」，不是設計文件；驗證用的程式碼可丟棄，不必是產品程式碼。
- 這些驗證項目彼此獨立，可分開、依序在不同 session 執行。**風險等級：高**（依 [開發流程框架] 的風險分級，高風險項目的人工核對步驟不可省略——結果需要人親自看過，不能只憑「跑過了」就採信）。
- 驗證項目 4、5 是階段 03 架構設計期間發現需求書 5.1 缺少「商戶如何取得 xpub」的定義後，回頭補上的驗證項目，對應需求書新增的「xpub 取得方式」小節。
- 驗證項目 6 是討論 5.9 手動歸集功能時發現的驗證缺口：驗證項目 3、4 只驗證過衍生數學（私鑰衍生、xpub 衍生），從未驗證過「瀏覽器端組建真實 TRC20 交易＋簽名＋廣播上鏈執行」這條完整路徑。
- 驗證項目 7 是階段 01 需求書完整度獨立審查時發現的驗證缺口：需求書 5.9「本機加密儲存」（商戶可選擇將助記詞以自訂密碼加密存於瀏覽器 IndexedDB）這段邏輯，風險等級與已驗證的項目 4、5（瀏覽器端衍生、離線打包＋嚴格 CSP）同類，卻從未被任何驗證項目觸碰過。
- 驗證項目 8 是階段 01/02 完整度再次回頭審查時發現的驗證缺口：驗證項目 6（組交易＋簽名＋廣播）從未套用過驗證項目 5/7 要求的嚴格 CSP，而需求書 5.9 明文要求歸集簽名頁面也要套用同等級 CSP。
- 驗證項目 9 是階段 03 技術架構設計討論「鏈上監控模組」時發現的驗證缺口：原本設計假設 process 重啟後能用 checkpoint（最後處理區塊高度）從任意久以前補齊漏掃的事件，但驗證項目 2 只驗證過「即時查詢剛發生的交易」，從未測試查詢很久以前的區塊範圍是否仍有資料、也從未測試單次查詢結果超過200筆時的 `fingerprint` 分頁行為是否正確銜接。

## 驗證項目 1：HD 地址衍生正確性

### 背景

需求書 5.1 節：系統依 BIP32/44 規則，針對商戶提供的 xpub 衍生收款地址，索引只增不減、不重複使用。地址算錯 = 資金可能發到系統認不出的地方，錯誤不會有任何警告或報錯，屬於「靜默失敗」風險。

### 範圍

1. 選定一套用於 Tron 位址衍生的函式庫（例如 TronWeb，或其他確認支援 Tron 位址格式的 HD 衍生函式庫）。
2. 使用 Tron 慣用的衍生路徑 `m/44'/195'/0'/0/{index}`。
3. 用同一組測試 xpub，依序衍生至少 5 個地址（index 0～4）。
4. 對每一個衍生出來的地址，**用第二套獨立工具或方法重新算一次**（例如：換一套不同的函式庫，或用線上已知可信的 Tron HD 錢包工具做交叉核對），確認兩邊結果一致。
5. 確認地址格式正確（Base58Check，以 `T` 開頭）。

### 通過條件（Pass / Fail）

- [ ] 同一組 xpub + index，兩套獨立方法算出的地址**完全一致**（全部 5 組都要對，任一組不一致視為失敗，須查明原因才能算過）。
- [ ] 地址格式驗證通過（可用 Tron 官方位址校驗規則或函式庫內建的校驗函式確認，不是肉眼看格式像不像）。
- [ ] 索引遞增時，衍生出的地址彼此不重複。

### 產出要求

- 驗證用的程式碼（可放在暫存/scratch 目錄，不進正式專案結構）。
- 一份簡短結論：使用的函式庫與版本、測試 xpub 來源（測試用，非真實商戶資料）、5 組 index → 地址的完整對照表、兩套方法是否一致、最終判定通過或失敗。

## 驗證項目 2：TronGrid 測試網事件掃描

### 背景

需求書 5.3 節：主要監控須採區塊/事件掃描（掃描 USDT 合約的 Transfer 事件，比對是否命中系統中的訂單地址），不得逐一輪詢地址。技術選型階段已查證 TronGrid 提供現成的事件索引 API：`GET https://api.trongrid.io/v1/contracts/:address/events`，可用 `event_name=Transfer` 搭配區塊/時間範圍過濾。此次驗證目的是確認這個 API 在測試網環境下真的能可靠抓到轉帳事件，而不是只停留在文件查證階段。

### 範圍

1. 申請 TronGrid 測試用 API Key（免費）。
2. 於 Tron 測試網（Nile 或 Shasta，二擇一，一致即可）取得測試用 TRX（透過官方水龍頭）。
3. 找一個測試網上可用的 TRC20 測試代幣合約（若無現成可用合約，可自行部署一個最簡單的 TRC20 測試代幣，僅供驗證事件掃描用，不需要跟正式 USDT 合約邏輯一致）。
4. 用測試錢包對一個目標地址發送一筆該 TRC20 代幣的轉帳。
5. 呼叫 TronGrid 的 `GET /v1/contracts/:address/events`（`address` 為代幣合約地址），加上 `event_name=Transfer` 過濾，確認能查到剛剛那筆轉帳。
6. 記錄從送出交易到能透過 API 查到事件，實際間隔多久（用來評估之後系統輪詢頻率該怎麼設）。

### 通過條件（Pass / Fail）

- [ ] API 呼叫成功，回傳資料中包含剛才發送的那筆轉帳事件。
- [ ] 事件內容（from、to、金額、合約地址、交易雜湊）與實際發送的交易一致。
- [ ] 記錄到「交易上鏈」到「事件可被查到」的實際延遲時間。
- [ ] 確認 `only_confirmed` 等參數的行為符合預期（例如設為 `true` 時，未達確認數的交易不會出現）。

### 產出要求

- 驗證用的程式碼/腳本（可丟棄）。
- 一份簡短結論：使用的測試網（Nile/Shasta）、測試代幣合約地址、測試交易雜湊、API 回傳的關鍵欄位截圖或原始 JSON、實際延遲時間、最終判定通過或失敗。

## 驗證項目 3：助記詞/私鑰硬化衍生正確性（手動歸集用）

### 背景

需求書 5.9 節：手動歸集功能由商戶在瀏覽器輸入助記詞/私鑰，前端依「相同的衍生路徑」逐一還原私鑰並簽名，私鑰不傳送至後端。需求書原文明白指出：**「此頁面是全系統風險最高的單一頁面」**。

這跟驗證項目 1 看似相似，實則是不同的技術假設：
- 驗證項目 1 驗證的是系統正常收款流程唯一會用到的路徑——`xpub → 非硬化公鑰衍生 → 地址`（後台只握有 xpub，不握有私鑰）。
- 手動歸集需要的是 `助記詞（seed）→ 硬化路徑衍生 → 非硬化路徑衍生 → 子私鑰 → 簽名`，完整路徑為 `m/44'/195'/0'/0/{index}`（前三段硬化，後兩段非硬化）。這條路徑的數學運算完全沒驗證過。

若這段衍生算錯，後果是「歸集頁面簽出的私鑰，控制的其實不是商戶以為要歸集的那個地址」——簽名本身可能不會報錯，只是簽對了一把「錯的」私鑰，屬於典型的靜默失敗風險。

### 範圍

1. 使用**跟驗證項目 1 完全相同**的 BIP39 測試助記詞與衍生路徑帳戶（`m/44'/195'/0'`），確保兩項驗證的結果可以直接比對。
2. 用兩套**互相獨立**的函式庫組合，各自從助記詞出發，完整走過硬化＋非硬化路徑，衍生出 index 0～4 的子私鑰與對應 Tron 地址。
3. 交叉核對兩條路線算出的私鑰與地址是否一致。
4. **關鍵橋接檢查**：把這裡衍生出的 5 個地址，逐一比對驗證結論-01 用「xpub 衍生」算出的 5 個地址（同一組助記詞、同一個帳戶層級 xpub）。系統實際運作時，後台用 xpub 算收款地址、歸集頁面用助記詞算簽名私鑰，這兩條路徑**必須收斂到完全相同的地址**，否則歸集頁面簽出來的私鑰所控制的地址，會跟商戶以為要操作的收款地址對不上。
5. 驗證衍生出的私鑰確實能產生有效簽名（例如簽一筆訊息/交易，並確認簽名可還原回對應的公鑰/地址），證明不只是地址字串巧合對上，私鑰本身真的可用於簽名。

### 通過條件（Pass / Fail）

- [ ] 同一組助記詞 + index，兩套獨立方法算出的私鑰與地址**完全一致**（index 0～4 全部要對，任一組不一致視為失敗）。
- [ ] 上述 5 個地址與**驗證結論-01** 用 xpub 衍生出的 5 個地址**逐一相同**（這是本項目最關鍵的通過條件）。
- [ ] 衍生出的私鑰能產生有效簽名，簽名可正確還原對應公鑰/地址。

### 產出要求

- 驗證用的程式碼（可放在暫存/scratch 目錄，不進正式專案結構）。
- 一份簡短結論：使用的函式庫與版本、測試助記詞來源（沿用驗證項目 1 的測試助記詞）、5 組 index → 私鑰/地址對照表、與驗證結論-01 的比對結果、簽名驗證結果、最終判定通過或失敗。

## 驗證項目 4：瀏覽器端助記詞 → xpub 衍生正確性

### 背景

需求書 5.1「xpub 取得方式」新增了兩種需要瀏覽器端運算的取得方式：方式 2（商戶輸入既有助記詞，前端算出 xpub）、方式 3（系統於瀏覽器端產生新助記詞，算出 xpub）。兩者背後是同一個技術假設：**瀏覽器 JavaScript 環境能否正確完成助記詞到帳戶層級 xpub 的硬化衍生**。

驗證項目 1、2、3 全部是在 Node.js 或 Go 這種伺服器端/命令列環境執行，從未在真實瀏覽器裡跑過這段運算。瀏覽器 JS 生態的加密函式庫實作方式、大數運算效能、API 限制都與伺服器端環境不同，不能假設 Node.js/Go 版本驗證過就代表瀏覽器版一定得到相同結果——驗證項目 2 已經證明過「換一套函式庫/環境就踩到沒預期到的坑」這種事真實會發生（Keccak256 vs SHA256 誤用）。

### 範圍

1. 選定瀏覽器可用的 BIP39/BIP32 JavaScript 函式庫（例如 `bip39` + `bitcoinjs-lib` 的 `hdkey` 模組，或確認 TronWeb 本身是否有現成支援），需能離線打包、不依賴 Node.js 專屬 API。
2. 在**真實瀏覽器環境**（不是 Node.js 或 jsdom 等模擬環境）建立一個測試頁面，用**跟驗證項目 3 完全相同**的測試助記詞，衍生出 `m/44'/195'/0'` 帳戶層級的 xpub。
3. 用這個瀏覽器算出的 xpub，衍生 index 0～4 的地址。
4. 額外驗證方式 3 的情境：在瀏覽器用函式庫隨機產生一組全新助記詞，確認格式合法（符合 BIP39 規則，可被其他標準工具還原），並用第二套獨立方法交叉核對這組新助記詞算出的 xpub 是否一致。

### 通過條件（Pass / Fail）

- [x] 瀏覽器算出的 xpub 與**驗證結論-03**（Node.js/Go 版本）完全一致。
- [x] 用該 xpub 衍生的 5 個地址（index 0～4）與**驗證結論-01** 的地址逐一一致。
- [x] 瀏覽器隨機產生的新助記詞格式合法，且用第二套獨立方法交叉核對算出的 xpub 一致。

**結論：PASS**，詳見 [驗證結論-04-瀏覽器端xpub衍生.md](驗證結論-04-瀏覽器端xpub衍生.md)。

### 產出要求

- 驗證用的程式碼/測試頁面（可放在暫存/scratch 目錄，不進正式專案結構）。
- 一份簡短結論：使用的 JS 函式庫與版本、測試瀏覽器與版本、與驗證結論-01/03 的比對結果、最終判定通過或失敗。

## 驗證項目 5：xpub 衍生函式庫離線打包 + 嚴格 CSP 相容性

### 背景

需求書 5.1／5.9 明確要求 xpub 取得頁面與歸集頁面**不引入任何第三方腳本/CDN/分析工具**、簽名/衍生函式庫**需離線打包隨系統部署**、並**套用嚴格 CSP**。這是「建置/部署」層面的驗證，跟「算得對不對」（驗證項目 4）是兩件獨立的事——函式庫邏輯正確，不代表離線打包後在嚴格 CSP 環境下還能正常執行，部分函式庫內部可能用到 `eval`、動態 `import`、WASM 等機制，容易被嚴格 CSP 擋下。

### 範圍

1. 把驗證項目 4 選定的函式庫，用實際的離線打包流程（例如 bundler 打包成單一靜態檔案，不透過 CDN 引入）打包進一個測試頁面。
2. 套用需求書等級的嚴格 CSP 設定（例如限制 `script-src` 僅允許自身來源，不允許 `unsafe-eval`/`unsafe-inline`）。
3. 在瀏覽器實際開啟此頁面，執行驗證項目 4 的衍生運算。
4. 檢查瀏覽器 console 是否出現 CSP violation 錯誤。

### 通過條件（Pass / Fail）

- [x] 函式庫離線打包成功，頁面不依賴任何外部網路請求即可完整運作。
- [x] 在套用嚴格 CSP 的情況下，衍生運算結果仍然正確（與驗證項目 4 一致）。
- [x] 瀏覽器 console 沒有任何 CSP violation 錯誤。

**結論：PASS**，詳見 [驗證結論-05-離線打包與嚴格CSP相容性.md](驗證結論-05-離線打包與嚴格CSP相容性.md)。

### 產出要求

- 打包設定與測試頁面（含實際套用的 CSP header/meta tag 內容，可放在暫存/scratch 目錄）。
- 一份簡短結論：使用的打包工具、實際套用的 CSP 規則、是否有踩到任何函式庫與嚴格 CSP 衝突的狀況（若有，記錄如何解決或是否無解需要換函式庫）、最終判定通過或失敗。

## 驗證項目 6：瀏覽器端 TRC20 轉帳交易組建 + 簽名 + 測試網廣播執行

### 背景

5.9 手動歸集功能要求：商戶在瀏覽器輸入助記詞/私鑰，由前端 JavaScript 還原私鑰、組出一筆 TRC20（USDT）轉帳交易並完成簽名，送給後端廣播上鏈，伺服器全程不接觸私鑰。這是歸集功能唯一可行的簽名方式（見與使用者的討論：地址資金要轉出，必須有對應私鑰簽名，而私鑰只能從助記詞在瀏覽器端衍生，伺服器架構上永遠不會拿到私鑰，這點無法繞開）。

但目前為止的驗證還沒把這條路徑走完整：
- 驗證項目 3 驗證了「助記詞→私鑰」的衍生數學，簽名驗證也只是**簽一段測試訊息的雜湊、本地驗章**，不是真正格式的 Tron 交易，且全程在 Node.js/Go 執行，從未進真實瀏覽器。
- 驗證項目 4 驗證了瀏覽器環境的衍生數學，但只到**公鑰/xpub**這一層，沒有衍生私鑰、沒有簽名、沒有組交易。
- 驗證項目 2 的 Go 重驗過程中，已經在「交易簽名」這個環節踩到一個真實的坑：Tron 交易簽名雜湊該用 SHA256，但位址衍生用的是 Keccak256，兩者容易混淆搞錯（詳見 [評估-Go打包Docker可行性.md](評估-Go打包Docker可行性.md)）。歸集功能要做的正是「組交易＋簽名」，同一個雷區換到瀏覽器 JS 環境很可能重踩一次。

「瀏覽器端能否正確組出一筆真實的 TRC20 轉帳交易、簽名、廣播上鏈並被鏈上正確執行」這個技術假設，目前完全沒驗證過，是 5.9 架構設計前必須補上的缺口。

### 範圍

1. 沿用驗證項目 3、4 完全相同的測試助記詞與路徑（`m/44'/195'/0'/0/{index}`），在真實瀏覽器環境衍生出 index 0 的私鑰與對應地址。
2. 透過 Shasta 測試網水龍頭，讓該地址取得少量測試 TRX（付手續費用）與測試 USDT（延續驗證項目 2 用過的測試代幣或官方測試網 USDT，若無現成可用，發一筆到此地址）。
3. 在瀏覽器用選定的函式庫（延續驗證項目 4/5 的組合，或視 TRC20 交易組建需求另選）組出一筆呼叫 USDT 合約 `transfer` 函式的 TRC20 轉帳交易（`TriggerSmartContract`），對指定目標地址轉出一筆小額測試 USDT。

## 驗證項目 7：本機加密儲存（助記詞加密存入 IndexedDB）正確性

### 背景

需求書 5.9：商戶可選擇「本機加密儲存」，以自訂密碼將助記詞加密後存於瀏覽器 IndexedDB，下次歸集時不需重新輸入助記詞。這段邏輯從未驗證過，若加密方案本身有問題（例如弱金鑰衍生、加解密邏輯錯誤導致解不回原文、或多次存取後資料損毀），輕則商戶誤以為助記詞有妥善保護、實際保護強度不足，重則直接影響歸集功能能否正常運作（存進去的助記詞讀不回來，等同遺失）。

這件事風險等級與已驗證的項目 4（瀏覽器端衍生）、項目 5（離線打包＋嚴格 CSP）同類——都是「瀏覽器端處理助記詞」的關鍵路徑——但技術上可以完全用瀏覽器原生 WebCrypto API（`window.crypto.subtle`）完成，不需要引入任何第三方加密函式庫：PBKDF2 做金鑰衍生、AES-GCM 做加解密，兩者都是瀏覽器標準內建功能。

### 範圍

1. 使用 WebCrypto 的 `PBKDF2`，將一組測試密碼衍生成加密金鑰（記錄使用的迭代次數、鹽值產生方式）。
2. 用 `AES-GCM` 加密一組測試助記詞（沿用先前驗證項目使用過的測試助記詞），將加密結果（含 IV、鹽值等還原所需參數）存入 IndexedDB。
3. **模擬跨 session 存取**：關閉分頁或重新整理頁面後（不能在同一次記憶體狀態下直接解密，要驗證真的能跨瀏覽器 session 存取），重新從 IndexedDB 讀出加密資料。
4. 用同一組測試密碼重新衍生金鑰、解密，確認還原出的助記詞與原文**逐字一致**。
5. 用還原出的助記詞重新走一次 xpub/地址衍生，與驗證結論-01/03/04 的結果比對，確認完全一致（不只字串對得上，衍生結果也要對得上）。
6. **反向測試**：故意用錯誤密碼嘗試解密，確認解密會明確失敗（AES-GCM 具備完整性驗證，錯誤金鑰應該直接報錯，而不是悄悄解出錯誤內容）。
7. 套用驗證項目5等級的嚴格 CSP，確認 WebCrypto 與 IndexedDB 呼叫皆不受影響、無 CSP violation。

### 通過條件（Pass / Fail）

- [x] 加密後存入 IndexedDB、跨 session 讀出、正確密碼解密，還原助記詞與原文完全一致。
- [x] 還原助記詞衍生出的 xpub/地址與驗證結論-01/03/04 逐一相同。
- [x] 錯誤密碼解密**明確失敗**（不會靜默解出錯誤內容）。
- [x] 嚴格 CSP 下，WebCrypto／IndexedDB 相關呼叫皆無 violation。

**結論：PASS**，詳見 [驗證結論-07-本機加密儲存IndexedDB.md](驗證結論-07-本機加密儲存IndexedDB.md)。

### 產出要求

- 驗證用的程式碼/測試頁面（可放在暫存/scratch 目錄，不進正式專案結構）。
- 一份簡短結論：使用的 KDF 參數（演算法、迭代次數）、加密演算法、測試瀏覽器與版本、與驗證結論-01/03/04 的比對結果、錯誤密碼測試結果、CSP 相容性結果、最終判定通過或失敗。

## 驗證項目 8：手動歸集「組交易＋簽名＋廣播」程式碼在嚴格 CSP 下的相容性

### 背景

需求書 5.9「輸入助記詞頁面的強化要求」明文要求歸集簽名頁面（含 TRX 手續費 A1/A2 簽名頁面，見 5.9「A1、A2 採用同一套瀏覽器端簽名原則」）不引入第三方腳本/CDN、簽名函式庫離線打包、套用嚴格 CSP——這條要求與需求書 5.1「代收主錢包取得方式」的安全規格文字幾乎一致，且驗證項目 5 已確認「助記詞→xpub 衍生」這組函式庫在嚴格 CSP 下相容。

但完整度回頭檢查發現：驗證項目 6（組交易＋簽名＋廣播）**從未套用過嚴格 CSP、也從未檢查 console 是否有 CSP violation**。驗證項目 6 額外引入的「手刻 ECDSA 簽名」（`secp256k1.sign()` 特定參數）、ABI 編碼邏輯，以及驗證用的 `fetch` 直接呼叫外部 TronGrid 網域（而非需求書 5.9 步驟 6 規定的「瀏覽器只送簽名結果給自己後端、後端負責廣播」架構），這些都不在驗證項目 5 的測試範圍內。風險等級與已驗證的項目 4/5/7 同類（瀏覽器端處理助記詞/私鑰的關鍵路徑），卻從未被驗證項目觸碰過，屬於階段 01/02 完整度審查的同一種缺口模式。

### 範圍

1. 沿用驗證項目 6 完全相同的衍生/簽名邏輯（`bip39`+`hdkey` 衍生私鑰、`@noble/curves` 手刻 ECDSA 簽名、`prehash:false`、簽名反推地址自我核對），程式碼不重寫，只重新包裝執行環境。
2. 架設一個同源測試伺服器：對「組交易」「廣播」這兩個需要呼叫 TronGrid 的步驟，改為呼叫伺服器自己的同源 API 路徑（例如 `/tron-proxy/...`），由伺服器**在瀏覽器之外**（Python/Go 等後端程式碼，不受瀏覽器 CSP 限制）代為呼叫 TronGrid，貼近需求書 5.9 步驟 6「瀏覽器只跟自己後端溝通、後端負責對外呼叫第三方 API」的架構，而不是像驗證項目 6 那樣讓瀏覽器直接打外部網域。
3. 套用驗證項目 5/7 同等級的嚴格 CSP（`script-src 'self'`、**`connect-src 'self'`**、無 `unsafe-eval`/`unsafe-inline`）於此測試頁面。
4. 在 Shasta 測試網，用此頁面走完整「衍生私鑰→組交易→本地簽名→簽名自我核對→廣播→鏈上查詢確認」流程（可沿用驗證項目 6 已驗證過的地址與代幣合約，若餘額/能量不足需另外取得測試 TRX/USDT）。
5. 用 `read_console_messages` 過濾整段執行過程的 console，確認無任何 CSP violation。

### 通過條件（Pass / Fail）

- [x] 在套用嚴格 CSP（含 `connect-src 'self'`）且所有 TronGrid 呼叫皆改走同源代理的情況下，組交易＋簽名＋廣播整條流程仍可正常執行，功能結果與驗證項目 6 一致（簽名自我核對通過、廣播成功、鏈上查詢執行成功）。

## 驗證項目 9：TronGrid 事件掃描資料保留期限與斷點續掃行為

### 背景

階段03討論「鏈上監控模組」時發現的缺口：原本規劃 process 重啟（含長時間停機）後，用持久化 checkpoint（最後處理成功的區塊高度）從斷點繼續補齊事件，靠的是一個從未驗證過的假設——TronGrid 的 `/v1/contracts/{合約}/events` 端點對「查詢很久以前的區塊範圍」是否仍有資料。查證官方文件（[TronGrid V1 API 文件](https://developers.tron.network/reference/trongrid-v1-api-overview)、[Rate limits](https://developers.tron.network/reference/rate-limits)）沒有找到任何關於保留期限的明文說明。

這個假設若錯，後果不是「補得慢」，而是**補不回來，而且不會報錯**——查詢一段已超過保留期限的區塊範圍，API 大機率仍回傳 200 成功、只是資料本來就是空的，系統會誤以為「已補齊」，實際上該時段的入帳事件永久漏記，商戶不會收到任何錯誤提示，等同於靜默漏收款項。

另外，驗證項目2也從未測試過單次查詢結果超過200筆（TronGrid `limit` 上限）時的 `fingerprint` 分頁機制是否真的能銜接完整不漏不重——實務上單一區塊掃描窗若命中高於200筆事件（例如熱門合約短時間大量轉帳），這是掃描迴圈必然會遇到的情況。

### 範圍

1. 選定一個交易量夠大、上線夠久的 TRC20 合約（例如 Tron 主網真實 USDT 合約 `TR7NHqjeKQxGTCi8q8ZY4pL8otSzgjLj6t`）作為查詢對象。**本項目只做查詢，不需要簽名/廣播交易**，與驗證項目1~8性質不同。
2. 用 `min_block_timestamp`/`max_block_timestamp` 分別查詢當下、7天前、30天前、90天前、1年前、更久（依實測結果調整級距）的區塊範圍，記錄從哪個級距開始查不到資料；查不到時記錄回傳的是空陣列還是錯誤訊息，藉此判斷是「保留期限」還是其他原因（例如參數格式錯誤）。
3. 找一個已知交易量在短時間窗內會超過200筆事件的區間，實測 `fingerprint` 分頁：第一頁查完後用回傳 `meta` 內的 `fingerprint` 查下一頁，用 `block_number`+`event_index`（或`transaction_id`）比對前後兩頁邊界，確認資料無重複、無遺漏。
4. 額外測試 `/v1/accounts/{address}/transactions/trc20`（單一帳戶歷史交易端點——5.2 EXPIRED訂單「手動重新檢查此地址」功能可能改走此端點，作為長時間停機的獨立保底手段，見階段03鏈上監控模組討論）的保留期限，選一個已知很久以前就有交易紀錄的地址，測試同樣的歷史範圍級距，與步驟2的contract-wide events端點結果對照，確認是否比較寬鬆。

### 通過條件（Pass / Fail）

- [ ] 確認 `/v1/contracts/{合約}/events` 端點對歷史事件查詢是否存在保留期限，若有，記錄明確的期限級距（例如「30天內可查，90天前查不到」）。
- [ ] 確認 `fingerprint` 分頁在單一查詢結果超過200筆時，能否正確銜接（無重複、無遺漏）。
- [ ] 確認 `/v1/accounts/{address}/transactions/trc20` 端點的歷史保留範圍，並與步驟2結果對照，是否比 contract-wide events 端點更寬鬆。

### 產出要求

- 一份簡短結論：各級距的查詢結果（查得到/查不到，若查不到是空陣列還是錯誤）、fingerprint 分頁銜接驗證結果、兩個端點保留期限對照表、對階段03「鏈上監控模組」checkpoint 設計與長時間停機補救機制的具體建議（例如是否需要限制「允許補齊的最長停機時間」、超過此時間的處理方式）。
