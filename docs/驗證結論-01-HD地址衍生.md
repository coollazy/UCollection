## 過程中的觀察 / 沒有預期到的狀況

- `bs58check`（4.0.0）與 `bip32`/`bip32` 套件（5.0.1）目前主線版本改用 ESM `exports` 限制，`require('pkg/package.json')` 和 `require('bs58check').encode` 這類舊寫法會直接噴錯（`ERR_PACKAGE_PATH_NOT_EXPORTED`、`encode is not a function`），必須改成讀檔取版本號、以及讀 `.default` 取函式。這與部分教學文章/舊範例程式碼的寫法不同，如果正式開發時沿用網路上舊教學程式碼，可能會直接卡在這一步。
- `tronweb`（6.5.0）目前主線版本已不是舊版常見的 `new TronWeb(...)` 全域 class 掛載模式，位址工具要從模組頂層 `require('tronweb').utils.crypto` 取用，`TronWeb.utils` 這個路徑（class 靜態屬性）行不通。
- 其餘沒有出現版本落差或行為跟預期不符的狀況。

## 最終判定：**PASS**

三項通過條件全部符合。HD 地址衍生（xpub → 非硬化子公鑰 → Tron Base58Check 地址）這個技術假設，在兩套完全獨立的函式庫組合下驗證一致，可以作為階段 03 技術架構設計的依據。

## 對階段 03 的提醒

- 選型時要留意上述套件版本差異（ESM exports、tronweb API 路徑變化），正式架構文件/程式碼撰寫時直接針對目前安裝到的版本（見上表）寫，不要照抄可能過時的網路範例。
- 本次驗證只涵蓋「xpub → 地址」這一段數學/編碼正確性，尚未涵蓋：xpub 如何從商戶端安全取得與保存、地址索引在系統內如何持久化並保證「只增不減、不重複使用」（本次驗證的「不重複」只證明了衍生數學不會撞地址，不等於系統流程保證索引不重用）。這兩點需要在架構設計階段另行處理。
