# ADR-0010：API Key 與 Webhook secret 明碼存資料庫

- Status: Accepted
- Date: 2026-09-02

## 背景

對外 API（第7節）與 Webhook（第8節）皆用 API Key/secret + HMAC-SHA256 簽章做認證。草案初版把 `api_keys` 的秘密欄位命名為 `secret_hash`，隱含「應該雜湊存」的假設，但這與 HMAC 機制本身的運作方式矛盾。

## 決策

**`api_keys.secret` 與 `webhook_secret` 明碼存資料庫**（非雜湊）。反之，session token（`admin_sessions.token_hash`）與 API Key 本身的 `key`（供 `X-API-Key` 查找比對用）一律只存 hash。

## 理由

- HMAC 驗簽的運作方式是「伺服器用同一把 secret 重新計算簽章、比對計算結果」，不是單純比對雜湊值。這跟密碼驗證不同：密碼驗證是「使用者輸入雜湊後比對」不需要伺服器重算，可以只存雜湊；但 HMAC 需要重算，雜湊過的 secret 無法逆推重算，伺服器必須持有明碼 secret 才能驗證——本質上做不到雜湊存。
- 比照 AWS/Stripe/GitHub Webhook 等業界慣例明碼存 DB，安全性依賴資料庫存取權限控管。
- 曾考慮應用層加密（用 master key 加密 secret 再入庫）增加防禦深度，但 master key 仍須放在伺服器啟動時可自動讀取的環境變數，形式意義大於實質防護，且與手動歸集（人工每次輸入密碼解密助記詞）的加密情境本質不同（那裡的密碼只存在商戶腦中，這裡的 master key 必然存在伺服器可讀取的地方），不套用同一套邏輯，故不加此層。

## 後台呈現層的緩解設計

即使 `secret` 技術上可從 DB 明碼撈回，後台列表頁**仍不常態明碼顯示**——API Key 與 Webhook secret 皆採「產生/重新產生當下的 HTTP 回應中明碼回傳一次，之後遮罩」的一次性顯示原則，降低螢幕外流/瀏覽器快取風險。這是呈現層的緩解，不影響底層明碼存的必要性。

## 常見誤解，不要「修正」

看到 `secret` 欄位明碼存資料庫，直覺會覺得是安全疏漏想改成雜湊存——**這是刻意決策，不是疏漏**。改成雜湊存會讓 HMAC 驗簽機制整個失效（伺服器再也無法重算簽章比對）。
