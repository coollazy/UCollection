# ADR-0019：API Key/Webhook secret 後台顯示前4+後4碼識別片段

- Status: Accepted
- Date: 2026-09-16

## 背景

後台 `/admin/api-keys` 列表頁原本只顯示建立時間與狀態（使用中/已作廢），`key`/`secret` 明碼只在產生當下的 HTTP 回應顯示一次、之後完全不可見（見 [ADR-0010](0010-API-Key與Webhook-secret明碼存.md)「後台呈現層的緩解設計」）。使用者反映這樣商戶無法核對「目前使用中的是不是我串接的那把」——尤其重新產生過幾次之後，列表上多筆記錄只有時間差異，無從辨識。Webhook 設定頁也有同樣問題，只顯示「已設定/未設定」。

## 決策

後台列表/設定頁補上「前4碼...後4碼」的明碼識別片段（例如 `AbCd...wxyz`），不需要完整明碼即可核對身分。依三種欄位目前的儲存狀態，做法不同：

| 欄位 | 儲存狀態 | 本次改動 |
|---|---|---|
| `api_keys.key`（供 `X-API-Key` 查找比對） | 只存 `key_hash`，原始明碼建立後即消失 | **新增欄位 `api_keys.key_hint`**，建立當下與 `key_hash` 一起算出存入 |
| `api_keys.secret`（HMAC用） | 已明碼存（ADR-0010既有決策） | 不新增欄位，渲染列表時從既有明碼欄位現算片段 |
| `system_params.webhook_secret` | 已明碼存（ADR-0010既有決策） | 不新增欄位，渲染設定頁時現算片段 |

共用格式函式（`internal/admin/api_keys.go` 的 `keyHint`）：字串長度 > 8 時回傳 `前4碼...後4碼`；長度 ≤ 8（Webhook secret 允許手動輸入，可能很短）時整串回傳原樣。

`key_hint` 為 `TEXT NULL`（見 `internal/store/migrations/0010_api_key_hint.up.sql`）：本次上線前已存在的舊記錄沒有機會回填（原始明碼早已不可逆取得），列表頁對 `NULL` 顯示「建立於此功能新增前，無法回溯顯示片段」，不偽造假資料。

## 理由

- **熵損失可忽略**：`key`/系統產生的 `secret` 皆是 32 bytes（256 bits）crypto/rand 經 base64 URL-safe 編碼，字串長度 43 碼。曝露前4+後4共8碼（約 48 bits）之後，中間仍有 35 碼（約 210 bits）未知，遠遠超過任何實務上可行的暴力破解量級，不構成「可重建金鑰」或「可用片段冒充完整金鑰通過驗證」的風險。
- **`key`/`secret`/`webhook_secret` 三者原本的機密性等級本來就不同**，不需要用同一套「完全不存明碼」規則硬套：`secret`/`webhook_secret` 依 ADR-0010 本來就明碼存在 DB（HMAC 重算需要），列表頁現算片段顯示不增加任何新的資料庫層曝露面；只有 `key` 本身的儲存原則有實質改變（多存了8碼），所以只有它需要新增欄位、新增決策。
- **與既有設計先例一致**：代收主錢包列表「`xpub` 僅顯示末幾碼＋建立日期」（技術架構設計第11節「代收主錢包設定」）本來就是同一套「不需要完整明碼即可識別」的呈現層設計哲學，這次是同一哲學延伸到 API Key/Webhook，不是新概念。

## 與 ADR-0010 的關係

本決策**延伸、不推翻** ADR-0010：`secret`/`webhook_secret` 明碼存 DB 的理由（HMAC重算）完全不變；`key` 本身「主要用 hash 查找比對」的原則也不變，只是額外多存一個無法逆推出完整金鑰的識別片段。ADR-0010「後台呈現層的緩解設計」一節所述「一次性顯示原則」的精神（降低螢幕外流/瀏覽器快取風險）延續：列表頁仍然只有片段，不是常態明碼全文顯示。
