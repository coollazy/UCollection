# ADR-0001：語言與執行環境選型：Go 單一 binary

- Status: Accepted
- Date: 2026-09-01

## 背景

階段02技術可行性驗證需要選定一個語言/執行環境，能同時滿足：HD 地址衍生（BIP32/44）、Keccak256/SHA256 簽章雜湊、打包成容易部署的 docker image。曾用 Swift 與 Go 兩種語言各自把驗證項目1（HD地址衍生）、2（簽名+廣播）、3（助記詞/私鑰硬化衍生）重做一次，實測比較兩者的可行性與部署成本。

## 決策

**採用 Go**，單一 binary，內部以常駐 goroutine 執行鏈上監控背景任務，不拆分多 process、不引入 message queue。

## 理由（實測數據）

- 三項驗證項目用 Go 重做，**全部一次通過**：項目1、3 第一次執行就 PASS（image 均 ~11MB、完全靜態連結）；項目2 過程中踩到一個真實的坑（簽名雜湊函式選錯——Tron 位址衍生用 Keccak256、但交易簽名雜湊其實是 SHA256，兩者容易混淆），修正後成功（image 26.1MB，因引入 go-ethereum + grpc 依賴）。
- 相較之下，Swift 打包 Docker 雖然技術上可行（PASS），但踩了兩個 Linux 相容性坑，image 體積達 378MB，遠大於 Go 版本。
- 單一 binary + goroutine 而非多 process/message queue：需求書為單租戶架構、無多副本/高可用要求，docker-compose 一鍵部署精神下越簡單越好，引入 message queue 是不必要的複雜度。

## 否決的替代方案

- **Swift**：技術可行，但 Linux 相容性成本明顯高於 Go（image 體積、踩坑數量），對單租戶自架軟體而言不划算。
- **拆分多 process/message queue**：需求書本身沒有高可用/多副本需求，拆分只會增加部署複雜度，不符合「docker-compose 一鍵部署」的產品定位。

## 殘留風險

amd64 架構下的三項驗證都還沒測過（既有驗證皆在 arm64 環境完成），若正式環境非 arm64，建議在階段04骨架建置前補驗。
