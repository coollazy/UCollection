# ADR-0015：已歸集地址晚到入帳改為可見度標示（推翻舊決策）

- Status: Accepted
- Date: 2026-09-07

## 背景

需求書 v0.24（5.9「已知風險與限制」）原本拍板：地址一旦完成歸集（餘額歸零），系統之後不再持續監控該地址；若之後又收到新入帳，系統不主動偵測、不標示、不通知商戶。理由是持續監控所有歷史地址（不論是否已歸集過）需要反覆查詢商戶名下曾經衍生過的全部地址餘額，隨訂單量累積會失去規模化能力。

階段06整合試跑「情境E」發現一個不相關的問題：訂單鎖定 COMPLETED 後，若鏈上晚到一筆 confirmed 金額，`EvaluateFinal` 的狀態機白名單會把它靜默擋下（`ErrInvalidTransition`），商戶端 Webhook 因此少報金額。修正方式（`internal/scanner/status.go` 的 `logLateFinalityConfirmation`）是把這類「已到終態、又收到晚到金額」的情況寫入 `ILLEGAL_STATE_TRANSITION` 稽核紀錄，並反映在 dashboard 異常訂單數。

階段07全系統審查橫向核對 CLAUDE.md 業務鐵律時發現：`internal/scanner` 的事件比對邏輯（`task_events.go`/`task_finality.go`）本來就是單純 `WHERE address = $1` 比對 `orders` 表，從不檢查 `consolidation_status`。這代表情境E的可見度機制是**無差別**的——一個已歸集地址（`consolidation_status='consolidated'`，訂單必然已是 COMPLETED）若收到晚到入帳，一樣會走到 `EvaluateFinal` → `ErrInvalidTransition` → `logLateFinalityConfirmation`，跟 v0.24 想要的「完全不可見」直接衝突。

## 決策

**推翻 v0.24「系統不主動偵測/通知」的部分**：已歸集地址收到的晚到入帳，比照 COMPLETED 訂單晚到 confirmed 金額的既有機制，一律寫入 `ILLEGAL_STATE_TRANSITION` 稽核紀錄並反映在 dashboard 異常訂單數，供商戶查證。

**保留 v0.24 更核心的部分**：系統不會因此把該地址重新排入「待歸集地址列表」，也**不會自動轉出、不會自動改判任何訂單狀態**——這部分沒有變。晚到入帳只是「被看見」，不會觸發任何自動處置動作，一律由商戶人工查證後自行決定怎麼處理。

## 理由

- 入帳是真實發生在鏈上的資金事件，沒有正當理由讓系統刻意對商戶隱藏——「不主動偵測」原本的動機是「持續監控所有歷史地址查詢量太大」，但情境E機制的實作方式（比對「本來就會發生」的事件掃描結果，而非額外去查詢每個歷史地址的餘額）並沒有這個規模化問題，兩個決策的技術前提其實不一樣，沒有理由讓舊決策的顧慮繼續適用在新機制上。
- 情境E機制已經證明「異常可見但不自動處置」這個模式是安全的：稽核紀錄與 dashboard 標示都只是唯讀查詢，不會觸發任何轉出/改判，維持 CLAUDE.md 安全鐵律「伺服器全程不接觸私鑰」「系統不主動判斷改判方向」的精神。
- 與其為了維持 v0.24 的「不可見」而回頭修改情境E機制（額外排除 `consolidation_status='consolidated'` 的情況），不如讓行為前後一致：COMPLETED 訂單的晚到金額異常，不論該地址是否已歸集，處理方式都相同，減少一種特例分支。
