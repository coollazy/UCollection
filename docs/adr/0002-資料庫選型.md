# ADR-0002：資料庫選型：PostgreSQL

- Status: Accepted
- Date: 2026-09-01

## 背景

系統需要一個資料庫承載訂單、地址分配、審計日誌、鏈上監控 checkpoint 等資料，且地址分配（依 xpub 衍生下一個索引）在高併發建單情境下必須保證不重複分配。

## 決策

**採用 PostgreSQL**。

## 理由

比較 PostgreSQL／MySQL／SQLite 後定案，關鍵考量：

- **地址分配的併發安全**：用 `pg_advisory_xact_lock(master_wallet_id)` 包住「讀取 `last_derived_index` → +1 → 寫回 → 建立訂單列」這段，是這類問題最直觀的解法，MySQL/SQLite 沒有對等的輕量 advisory lock 機制。
- **JSONB**：適合審計日誌明細（`audit_logs.detail`）與訂單狀態轉換快照（`order_state_transitions.decision_snapshot`）這類結構不完全固定的資料。
- **長期報表擴充性**：交易明細匯出、儀表板統計等查詢，PostgreSQL 的查詢優化與擴充性優於 SQLite。

## 否決的替代方案

- **SQLite**：部署最簡單（單檔案、無需獨立 container），但沒有 advisory lock 對等機制，且商戶自架情境下報表/稽核查詢量體成長後容易碰到限制。
- **MySQL**：可行，但同樣缺乏 PostgreSQL advisory lock 的直觀併發控制手段，JSONB 支援也不如 PostgreSQL 成熟。

## 後果

docker-compose 服務組成因此固定為 `app`（Go binary）+ `db`（PostgreSQL）兩個 container（見 [ADR-0001](0001-語言與執行環境選型.md)）。
