# ADR-0016：高風險操作每次要求TOTP驗證碼，取消15分鐘新鮮度窗口（推翻ADR-0011部分決策）

- Status: Accepted
- Date: 2026-09-07
- 部分修訂：批次寬限窗值（`batchStepUpWindow`）針對手動歸集編排流程延長至 30 分鐘（僅限該流程，不影響其他 `/tron-proxy/...` 端點的 15 分鐘），見 [ADR-0017](0017-手動歸集流程重構自動編排與精省手續費.md)。

## 背景

[ADR-0011](0011-兩階段登入與step-up驗證.md) 拍板高風險操作（`/tron-proxy/...`、手動改判、代收主錢包切換、API Key重新產生、Webhook URL/secret變更、金額容許誤差百分比設定）疊加 `RequireFreshTOTP(15分鐘)`：距上次TOTP驗證15分鐘內免重複輸入，超過才需重新輸入。

本機部署測試（2026-09-07）實測「金額容許誤差百分比」設定流程時發現：15分鐘視窗過期後，系統把已攔截的請求導向 `/admin/reverify-totp`，驗證通過後再用 HTTP 303 轉址「帶回」原本被攔截的操作——但303轉址一律變成瀏覽器 `GET`，若原始請求是只註冊 `POST` 的寫入端點（例如 `/admin/params/tolerance`），轉址回去就會撞 `405 Method Not Allowed`；且原始表單內容在第一次被攔截時就已遺失，即使方法對了也無法悄悄用舊資料重送，操作者必須重新填寫整張表單再送出一次。

過程中討論修法方向時，使用者反問「為什麼不直接在每個高風險欄位頁面要求輸入驗證碼、後端驗證完直接寫入資料，不需要共用一個獨立的驗證碼頁面？」，並進一步確認：既然這類操作本來就需要TOTP驗證碼，那就每次都要求輸入，不要用「距上次驗證是否超過15分鐘」這種時效判斷。

查證需求書後確認：**需求書 5.5 完全沒有規定登入後的高風險操作要不要重新驗證、要不要有時效**，需求書只要求「登入需2FA」。15分鐘新鮮度窗口是 ADR-0011 在需求書字面之外主動加上的防禦深度，屬於可以重新評估的技術決策，不受需求書字面拘束。

## 決策

**取消15分鐘新鮮度窗口，高風險操作每次送出都要求當下輸入TOTP驗證碼**：

1. `admin_sessions.last_totp_verified_at` 不再用於「距今是否在15分鐘內」的gating判斷，改為單純記錄「最近一次成功完成TOTP驗證的時間」供稽核參考。
2. **GET頁面**（代收主錢包新增頁、手動歸集簽名頁、修改密碼頁）：每次造訪都導向 `/admin/reverify-totp`，驗證通過才能看到頁面內容（不再有「15分鐘內免驗證」的例外）。
3. **POST/DELETE寫入端點**：驗證碼欄位直接內建在觸發該操作的表單／請求本身裡，與其他欄位一起在同一次送出中一併驗證。驗證通過就在同一次請求內直接完成操作，不需要額外跳轉頁面、不會遺失已填寫的資料。只有在驗證碼缺漏或錯誤時，才會被導回原頁面重新操作（此時本來就需要重新確認資料，不算額外損失）。
4. **ADR-0011 其餘部分維持不變**：兩階段登入（密碼→TOTP）、`admin_sessions` session模型（12小時絕對過期+30分鐘閒置）、IP層級與per-session層級雙重暴力破解防禦、TOTP重放防護（`last_totp_step`），這些都跟「新鮮度窗口」是獨立的機制，不受本次決策影響。

## 理由

- **需求書未規定，屬於可調整的技術決策**：ADR-0011 本文自己也寫明這是「需求書字面之外主動加上的防禦深度」，既非需求硬性規定，使用者作為最終決策者可以依實測體驗重新評估取捨。
- **安全性不降反升**：每次都要求驗證碼，把「session cookie外洩但2FA裝置未同時外洩」這類攻擊者的可乘之機，從15分鐘窗口壓縮到0——移除的是「窗口內免驗證」這個便利性，不是移除驗證本身。
- **同時解掉了405 bug，且是更乾淨的解法**：與其修補「轉址帶回原操作」這個機制本身固有的「303必變GET」「原始表單內容會遺失」兩個結構性問題，不如讓驗證碼欄位直接跟資料欄位在同一次送出裡，从根本上不再需要「驗證完之後再想辦法接續執行原操作」這一步，二者一次到位。
- **已知取捨（使用者知情後接受）**：連續操作多筆高風險項目時（例如一次改判好幾張訂單），每一動作都要重新輸入驗證碼，比15分鐘窗口內連續操作免驗證更繁瑣。使用者評估後認為，比起先前踩到的「跳轉遺失資料」問題，這個取捨可以接受。

## 批次寬限修訂（同日）

實作到手動歸集簽名頁（`/admin/consolidation/sign`）的JS（`page.js`）時發現：一次簽名頁操作可能處理一整批多筆項目（例如一次歸集10筆訂單），`page.js`對每一筆項目都各自呼叫一次組交易（`prepare`）與一次廣播（`broadcast`），兩個都是`/tron-proxy/...`端點。若比照本ADR上方決策「每次都要求」字面套用，一批N筆就要輸入2N次驗證碼——這在操作上不可行，跟一般表單「一個動作=一次送出=一次驗證碼」的情境不同。

**追加決策**：僅這4條`/tron-proxy/...`端點（`consolidation`/`fee-topup`各自的`prepare`/`broadcast`）改用新增的`RequireTOTPCodeOrRecentStepUp`：批次內**第一次**呼叫仍要求當下輸入新鮮、未重放的驗證碼；驗證成功後`admin_sessions.last_totp_verified_at`被更新，同一session在`batchStepUpWindow`（15分鐘）內的後續呼叫免驗證碼即可通過。

**與上方主決策的界線**：這不是恢復ADR-0011被推翻的舊機制——舊機制是「全部13條高風險路由、不分是否處於同一次操作，15分鐘內一律免驗證」；這裡範圍窄得多：只適用這4條路由（GET頁面與其餘9條`RequireTOTPCode`路由不受影響，每次仍要求驗證碼)，且窗口存在的目的明確限定為「處理同一批次的合理時間」，不是通用的操作便利性寬限。攻擊者僅取得session cookie（未取得2FA裝置）時，仍然完全無法觸發任何一次歸集/手續費組交易或廣播——這個核心防線沒有被削弱，只是同一次已驗證身分的批次操作內，不用為每一個項目重打一次驗證碼。

前端做法：`page.js`只在整批第一個`postJSON`呼叫送出驗證碼（透過`X-Totp-Code` header，因為這幾個端點吃JSON body而非表單），之後的呼叫不帶驗證碼欄位，讓後端的批次寬限機制放行。
