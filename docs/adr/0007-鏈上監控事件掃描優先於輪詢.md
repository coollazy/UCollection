# ADR-0007：主要監控用事件掃描，不逐一輪詢地址

- Status: Accepted
- Date: 2026-09-01

## 背景

系統需要持續判斷「哪個地址收到了 USDT」。最直覺的做法是對每個進行中訂單的地址逐一查詢餘額/交易紀錄，但這個做法的 API 呼叫量會隨監控中地址數量線性增加，訂單量一大就容易超出第三方 API（TronGrid）的免費/速率額度。

技術架構設計第一版草案曾讓事件掃描迴圈依「是否有進行中訂單」啟停以節省 API 呼叫成本，但 subagent 審查指出這個方向本身是錯的：需求書5.3自己說事件掃描的 API 呼叫成本只跟區塊產生速度有關、不隨地址/訂單數量增加，為了省一個固定成本而啟停，換來一整組冷啟動/尾端漏記的窗口期風險，不划算。

## 決策

**主要監控（即時、持續、覆蓋所有進行中訂單）一律採區塊/事件掃描**（`GET /v1/contracts/{USDT合約}/events?event_name=Transfer`），比對事件 `to` 欄位是否命中訂單地址；**不逐一輪詢地址列表**。三個背景任務永遠常駐（不依「是否有進行中訂單」啟停），無進行中訂單時任務2（事件掃描）僅降頻，不停止，checkpoint 持續推進。

**此限制僅適用於主要監控**。備援/降級情境（事件掃描持續失敗時）不在此限，範圍限定當下 PENDING/CONFIRMING 訂單（有界集合），可接受降頻，逐一查詢地址並非不可行。

## 理由

- 事件掃描的 API 呼叫量只跟區塊產生速度有關，具備規模化能力；逐一輪詢的呼叫量隨地址數量線性增加，不具規模化能力，是需求書 5.3 明文排除的做法。
- 永遠常駐 + 降頻，而非啟停：省下的固定成本遠小於窗口期漏記的風險（漏收款是「補不回來、還不會報錯」的靜默風險，見 [驗證項目9](../驗證結論-09-TronGrid事件掃描保留期限與斷點續掃.md) 的既有查證動機）。

## 曾經的誤解與修正

早期草擬 CLAUDE.md 內容時曾寫成「禁止逐一輪詢地址列表」，範圍寫過頭了——這條限制只適用於「主要監控」，備援/降級情境不在此限。正確寫法是「主要監控以事件掃描為主，備援/降級情境可接受輪詢」，不是絕對禁止。
