# ADR-0014：後台手動改判疊加 RequireFreshTOTP

- Status: Accepted
- Date: 2026-09-02

## 背景

第11節（後台管理介面模組）第二輪 subagent 審查發現：草案初版把手動改判（`POST /admin/orders/{id}/override-status`）僅掛一般 `RequireSession`，理由是「不涉及身分劫持」。但模組5「手動改判路徑」設計本就刻意不重查金額子查詢（操作者的人工查證本來就是要覆蓋系統判斷），代表這條路徑沒有任何伺服器端金額驗證防線。

## 決策

**手動改判（`POST /admin/orders/{id}/override-status`）疊加 `RequireFreshTOTP(15分鐘)`**，比照代收主錢包切換、API Key重新產生、Webhook secret變更等已定案的高風險操作。

## 理由

若攻擊者僅取得 session cookie（未取得2FA裝置，見 [ADR-0011](0011-兩階段登入與step-up驗證.md) 既有威脅模型），可直接呼叫此端點把任一 EXPIRED/STALLED 訂單改判為 COMPLETED，觸發**真實**（非偽造，走系統正常路徑產生的）`ORDER_COMPLETED` Webhook，效果等同「偽造終態通知詐騙商戶誤判已收款」——且不需要額外竊得任何密鑰即可達成，只需要一次已認證的 POST 呼叫，風險量級與代收主錢包切換同類。

## 權限分級判準（供後續新增端點參考）

後台寫入操作是否要疊加 `RequireFreshTOTP`，判準有三（第11節「權限分級理由」定案）：

1. 操作本身即構成身分劫持（代收主錢包切換、API Key重新產生、Webhook URL/secret變更）
2. 頁面本身處理高風險輸入，即使是唯讀GET也納入（比照歸集簽名頁先例）
3. **操作能觸發真實的終態Webhook通知、且該路徑本身無伺服器端金額驗證防線**（本決策新增的第三判準）

新增任何後台寫入端點時，先用這三個判準檢查是否該疊加，不要預設「非資金移動操作」就一定只需要一般session。
