# ADR-0005：代收主錢包（xpub）取得方式

- Status: Accepted
- Date: 2026-08-31（需求書 v0.5 廢除方式1）／2026-09-01（技術架構設計第3節定案衍生邏輯）

## 背景

系統需要一組 xpub 為每筆訂單衍生獨立收款地址，且設計原則是「伺服器全程不接觸、不儲存私鑰」。但 Tron 是帳戶模型鏈，**主流 Tron 錢包普遍不支援匯出帳戶層級 xpub**（這點與 Bitcoin 生態不同，Trezor/Ledger/Electrum 等 Bitcoin 錢包普遍支援）；地址、一般格式私鑰皆無法反推出 xpub（缺少 chain code）。市場調查也確認查無「商戶直接輸入既有 xpub」的實務可行取得管道。

## 決策

代收主錢包只提供兩種取得方式，皆在**瀏覽器本地**計算出 xpub，助記詞不上傳、不經過後端、不落地：

1. **商戶輸入既有助記詞**：前端本地驗證 BIP39 格式合法性後衍生 xpub。
2. **商戶使用系統提供的「產生錢包」功能**：瀏覽器端隨機產生新助記詞，比照 TronLink 做法要求商戶依序點選重建完整助記詞驗證備份，驗證通過才計算 xpub 送給後端。

兩種方式共用同一套安全規格：不引入第三方腳本/CDN、函式庫離線打包、嚴格 CSP；方式1額外要求先顯示風險提示（此助記詞的安全性將與本系統綁定）。

## 否決的替代方案

1. **伺服器端一次性生成 xpub**（後端生成助記詞、算完 xpub 就從記憶體清除、不落地）——即使不落地，助記詞仍短暫進過伺服器記憶體，違反「伺服器全程不接觸私鑰」原則，風險面（crash dump、swap、日誌框架意外印出）比瀏覽器端生成大。
2. **商戶自行在既有錢包「新增帳戶」產生一批地址、匯出清單匯入系統**（不透過 xpub/HD 即時衍生）——可行但地址是有限批次不是無限衍生，商戶要記得補；未採用，若之後 xpub 方案在實務上卡關可重新拿出來討論。
3. **固定地址 + 金額尾數區分訂單**——直接牴觸需求書5.1「地址與訂單永久一對一綁定」，屬於要重新打開需求書範圍的討論，不是單純技術選型。
4. **方式1（商戶直接輸入既有 xpub）**——曾是 v0.3 需求書列的三種方式之一，v0.5 廢除：市調發現查無任何主流 Tron 錢包支援匯出帳戶層級 xpub，實務上無法使用。
5. **智能合約（CREATE2/Forwarder 模式）批次生成收款地址**——參考 PayRam 對 Tron/EVM 鏈的架構評估後未採用，理由：(1) 合約需要常駐 operator 私鑰觸發 sweep，私鑰曝險頻率比「助記詞僅手動歸集時瀏覽器端短暫現形」更高；(2) 歸集需額外「部署+自毀合約」開銷，成本更高；(3) 完全沒解決歸集需要 TRX/能量的問題，只是換簽名者；(4) 增加 reentrancy、合約升級、稽核等純 HD 衍生不用面對的複雜度。且業界逆向訊號：Kraken 近期反而把 EVM 存款從智能合約地址改回標準 EOA 地址。
6. **商戶端「送出前驗證xpub是否正確」的UX機制**（例如顯示地址預覽供商戶自行核對）——商戶現實中不會真的去核對，且若問題出在衍生邏輯本身有 bug，商戶也無從比對出「正確答案」。改用工程手段（驗證項目4已用雙函式庫交叉比對確認結果一致），階段04開發時須搭配自動化測試持續守住這件事，不做成商戶端功能。

## 市場調查完整脈絡（討論需求書5.1時查證，供之後參考避免重查）

- **xpub 衍生地址這個架構本身有市場先例，但 PayRam 對 Tron/EVM 鏈其實走的是不同技術路線**：商業自架收款閘道 **PayRam**（UAE 公司，閉源）的行銷文案「PayRam uses a read-only xPub」一度被誤讀為通用做法，經查官方 onboarding 文件（[Wallet Integration](https://docs.payram.com/onboarding-guide/wallet-integration)）後發現這句話**只適用於 Bitcoin**：Bitcoin 流程是商戶把助記詞貼進 PayRam 提供的獨立工具算出 xpub（工具端「generate addresses」後助記詞即丟棄，貼近本決策方式1/2的精神，但流程是先在獨立工具算好、再把 xpub 貼進 `config.yaml`，非即時串接的後台表單）。**Tron/EVM 鏈完全是另一套架構**：商戶用瀏覽器錢包（TronLink/MetaMask）連接一個自己握私鑰的「主錢包」帳戶，輸入歸集目的地後在錢包簽名確認一筆鏈上交易——**主錢包部署一個智能合約，由合約負責批次生成充值地址**，主錢包需持有 TRX 支付部署與後續交易手續費。也就是說 PayRam 用**智能合約**繞開「帳戶模型鏈不支援匯出xpub」的限制，而不是像本決策一樣用 BIP44 標準路徑做 HD 衍生。這是促成後續深入市調、最終否決「方式1直接輸入既有xpub」（見上方否決方案4）的第一條線索。
  - 注意：這只是從官方文件片段查到的架構線索，CREATE2/deterministic address、合約掃清（sweep）機制、gas精確處理方式、合約升級/重放風險等技術細節都沒有深入驗證，不能當作可以直接照搬的完整方案，僅供架構方向參考（見上方否決方案5的完整評估）。
- **開源圈子裡沒找到跟本決策完全一樣做法的**：實際翻原始碼確認——**SHKeeper**（`vsys-host/tron-shkeeper`）每個地址是伺服器生成的全新隨機私鑰，加密後存資料庫，付款/歸集時解密使用，私鑰會經過伺服器，跟「伺服器全程不碰私鑰」是不同等級的安全設計；**UPay**（`UPay-USDT/USDT-Payment-Gateway`）用固定地址池輪詢分配給訂單，不是 xpub 無限衍生，正是上方否決方案2/3的替代做法，證實市場上確實有人這樣做。結論：本決策的 xpub-only 架構比市場上查到的開源方案都更嚴格，可能因為「這件事本身很難做對」+「不是 Tron 生態原生慣例」+「多數開源專案圖省事」三個原因疊加，不代表這條路有問題（六項技術驗證已用真實測試網廣播＋獨立查鏈證實可行，見[驗證結論-01](../驗證結論-01-HD地址衍生.md)/[03](../驗證結論-03-助記詞私鑰硬化衍生.md)/[04](../驗證結論-04-瀏覽器端xpub衍生.md)）。
- **Tron 官方原生的多帳戶衍生慣例（TIP-01：`m/44'/195'/x'`）三層全硬化**，沒有非硬化 change/index 層，無法只靠 xpub 衍生多個地址——這解釋了為什麼主流 Tron 錢包普遍不支援匯出可用 xpub，不是市場剛好沒做，是原生慣例的技術模型跟「xpub衍生」這件事本身不相容。Tron 官方自己有提案想做這件事（[TIP-102](https://github.com/tronprotocol/tips/blob/master/tip-102.md)，路徑刻意設計成非硬化change/index層），但2019年提出至今仍是"Last Call"狀態、無任何錢包或交易所實作。業界標準表述是「帳戶模型鏈（Tron/EVM）只需要地址，UTXO鏈才需要xpub」。系統採用標準 BIP44 五層路徑（`m/44'/195'/0'/0/n`）是滿足「伺服器不碰私鑰」需求唯一可行的選擇，不是選錯。
- **帳戶模型鏈（Ethereum、Tron）普遍不支援匯出 xpub，UTXO 鏈（Bitcoin）普遍支援**：查證 MetaMask（以太坊最主流錢包）也不支援匯出 xpub，跟 Tron 錢包狀況一致，是整個帳戶模型鏈家族的通例，不是 Tron 特例。
- **市場上唯一真實存在過的「Tron xpub HD衍生收款」實例已停運5年，且用非標準路徑**：`go-faast/tron-payments`（已停運交易所Faast的自用套件，GitHub已封存）用Bitcore實作BIP32/44，路徑`m/44'/195'/0'/0/n`（非硬化change/index層），架構與本決策規劃的完全一致。但這條路徑跟TronLink、imToken等官方錢包走的TIP-01（全硬化）路徑不相容——商戶若拿官方錢包助記詞給這套邏輯衍生，算出的地址官方錢包自己看不到、對不上帳，這正是此類方案在市場上幾乎絕跡的原因：不是密碼學做不到，是跟主流錢包生態兜不起來。
- **BIP32 非硬化衍生有已知的私鑰洩露理論風險，但這是整個 BIP32/44 生態的通例，非本架構特有**：BIP32 官方規範明文警告「知道父層xpub加上任何一個非硬化衍生的私鑰，等同於知道父層完整的xprv（因此該父層底下過去和未來所有的公私鑰都會曝光）」，這是純橢圓曲線代數性質，跟鏈是UTXO還是帳戶模型無關；Tron官方TIP-01全硬化路徑正是在落實這條BIP32官方建議。但**這個風險不構成放棄xpub衍生架構的理由**——Bitcoin主流硬體/軟體錢包（Ledger、Trezor、Electrum）同樣是「帳戶層以上全硬化、change/index層非硬化」的結構，全球用戶每天都活在同一個風險假設下。光有xpub推不出任何私鑰，要出事必須**另外**發生一次子私鑰外洩的獨立事故（簽名環境中毒、惡意腳本、備份外流），不是正常操作會自動觸發的事。真正值得留意的是「歸集簽名環境的資安等級」——手動歸集是在商戶一般瀏覽器裡衍生私鑰簽名，風險等級接近Electrum這類軟體錢包（而非Ledger/Trezor等硬體錢包，私鑰衍生在晶片內完成、外洩面更小），但這仍是非託管錢包生態普遍接受的等級，不算特例。既有的「離線打包、嚴格CSP、無第三方腳本」規格正是在對這個風險做緩解。
- **沒有現成的瀏覽器插件能做掉「助記詞→xpub」這件事**：查證TronLink等錢包插件注入API（`window.tronLink`/`tronWeb`），只暴露「地址+簽名」方法，沒有任何方法能建立帳戶或匯出xpub/公鑰，協定設計上就不開放，程式化呼叫也繞不過去（[TronLink Docs](https://docs.tronlink.org/plugin-wallet/active-requests/)）。WalletConnect類協定規格同樣沒有xpub這個概念，本質是「請求簽名」不是「請求金鑰資料」（[WalletConnect Specs](https://specs.walletconnect.com/2.0/specs/clients/sign/namespaces)）。唯一「有機會」的路是Ledger硬體錢包WebUSB/WebHID直連瀏覽器，`@ledgerhq/hw-app-trx`在特定參數下會回傳`publicKey`+`chainCode`（私鑰不離開裝置），理論上可自行拼出xpub，但仍要自己寫BIP32序列化邏輯，且前提是商戶要有Ledger硬體，商業上不能取代現有方案。結論：維持自建離線頁面路線，沒有插件可以省下來。
- **iancoleman/bip39 這類獨立 BIP39/BIP32 開發者工具，不建議讓商戶跳轉過去操作再貼回來，但可以引用其 MIT 授權的衍生邏輯**：查證 iancoleman/bip39（純前端單一HTML+JS檔案，MIT授權，內建Tron/coin type 195選項，可直接輸出xpub，功能上完全符合需求）。但這工具因知名度高，**多次被釣魚仿冒**（GitHub issue [#437](https://github.com/iancoleman/bip39/issues/437)、[#556](https://github.com/iancoleman/bip39/issues/556)、[#444](https://github.com/iancoleman/bip39/issues/444)、[#269](https://github.com/iancoleman/bip39/issues/269)，假網域透過廣告排名超前真站，已有使用者助記詞被盜的真實案例）；若讓商戶跳轉到外部網站操作，等於把「商戶會不會跑錯網域」這個風險完全交給商戶自己判斷，比自建「離線打包+嚴格CSP」（助記詞永遠只在商戶已信任的自家系統網域下運作）安全等級明顯更差；且xpub是100+字元字串，複製貼上容易出錯，商戶也可能選錯幣別。**MIT授權允許自由修改再散布商用**，系統已直接把 iancoleman/bip39 處理 BIP32/Tron xpub衍生的核心邏輯引入自建的離線打包+CSP頁面，同時拿到「被廣泛驗證過的程式碼」與「網域自主可控」兩個優點。
- **市場背景（USDT-TRC20 選型佐證，非本決策直接依據，但說明選對了市場切角）**：USDT 在 Tron 上是主流中的主流，市值約 890 億美元、佔全體 USDT 市值 47%（所有鏈最高），小額（<$1000）零售支付市佔更高達 52%。Binance Pay/Bitfinex Pay 主要走內部帳本（off-chain ledger），跟「開放式接受任何外部錢包付款」是不同題目，不適合拿來比對本系統的收款地址設計。
